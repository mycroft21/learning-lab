## 브라우저 주소창을 보면 토큰이 안 보인다

로그인이 끝나고 우리 앱으로 돌아오는 순간의 URL을 살펴보자.

```
https://app.example.com/callback?code=a1b2c3d4&state=xyz
```

`access_token`이 아니라 `code`라는 짧은 값 하나만 보인다. 이 URL은 브라우저 주소창에 남고, 브라우저 히스토리에 저장되고, 외부 링크를 클릭하면 `Referer` 헤더로 다른 사이트에 넘어갈 수도 있고, 서버 접근 로그에도 그대로 찍힌다. 그런데 거기 찍힌 게 토큰이 아니라 "토큰과 교환할 수 있는 일회용 영수증"뿐이라면, 저 노출 경로들이 전부 토큰 유출 경로가 되지는 않는다.

## 브라우저가 지나가는 길과 서버끼리 통하는 길을 분리한다

인가 코드 흐름(authorization code flow)이 하는 일은 하나다. **토큰 자체는 브라우저가 보는 어떤 경로에도 절대 실리지 않게 만든다.**

> 인가 코드는 브라우저를 거쳐 전달되는 "교환권"일 뿐이고, 실제 토큰은 **서버와 서버가 직접 통신하는 별도의 요청**으로만 오간다. 이 흐름이 지키려는 건 "토큰이 거쳐야 하는 곳의 수를 최소화한다"는 원칙이다.

두 단계로 나뉜다.

- **앞단(front channel)** — 사용자의 브라우저가 인가 서버로 리다이렉트되고, 로그인·동의 후 우리 앱으로 다시 리다이렉트된다. 이 구간에서 오가는 건 **인가 코드뿐**이다. 코드는 보통 수십 초 안에 만료되고, 한 번만 쓸 수 있다.
- **뒷단(back channel)** — 우리 앱의 서버가 인가 서버에 **직접** HTTPS POST를 보내 그 코드를 토큰으로 바꾼다. 이 통신은 브라우저를 거치지 않으므로 히스토리에도, `Referer`에도, 프런트엔드 로그에도 남지 않는다.

과거에 쓰이던 암묵적 흐름(implicit flow)은 이 구분이 없어서 토큰을 URL 프래그먼트에 직접 실어 돌려줬고, 그래서 OAuth 보안 권고에서 더 이상 권장하지 않는 방식이 됐다. 인가 코드 흐름이 사실상 기본값이 된 이유가 이 구조적 차이다.

## 그런데 코드도 가로채일 수 있다

여기서 한 가지가 빠졌다. 뒷단 요청을 인가 서버가 **우리 앱이 보낸 게 맞는지** 어떻게 확신할까. 서버를 갖춘 전통적인 웹 앱이라면 `client_secret`으로 증명한다. 그런데 모바일 앱이나 SPA처럼 **비밀을 안전하게 보관할 서버가 없는 클라이언트**는 이 방법을 못 쓴다. 그리고 이런 클라이언트에서는 리다이렉트 URI를 가로채는 공격(예: 모바일에서 같은 커스텀 URL 스킴을 등록한 악성 앱)으로 인가 코드 자체가 탈취될 가능성이 실제로 존재한다.

PKCE(Proof Key for Code Exchange)가 메우는 게 이 틈이다.

1. 클라이언트가 무작위 문자열 `code_verifier`를 만든다.
2. 그걸 해시한 `code_challenge`를 **인가 요청에** 실어 보낸다. (`code_verifier` 자체는 보내지 않는다.)
3. 나중에 코드를 토큰으로 바꾸는 **뒷단 요청에** 원본 `code_verifier`를 실어 보낸다.
4. 인가 서버는 그 `code_verifier`를 해시해서 2번에서 받아둔 `code_challenge`와 같은지 검증한다.

> 공격자가 인가 코드를 가로채더라도, `code_verifier`는 클라이언트 메모리 안에만 있었으므로 공격자는 그 코드를 토큰으로 바꿀 수 없다. PKCE는 코드를 못 훔치게 막는 장치가 아니라, **훔친 코드를 쓸모없게 만드는 자물쇠**다.

`client_secret`을 못 가진 클라이언트에서 특히 중요했던 이유가 여기 있다 — 비밀이 없는 자리를, 매번 새로 만드는 1회용 비밀(`code_verifier`)로 대신 채운 것이다. OAuth 2.1 초안에서는 이 보호를 비밀을 가진 전통적인 서버 클라이언트에도 확장해 **모든 클라이언트에 PKCE를 요구**하는 방향으로 가고 있다 — 코드 가로채기는 클라이언트 종류와 무관하게 일어날 수 있는 공격이기 때문이다.

## 인터뷰에서 이렇게 나온다

**"인가 코드 흐름은 암묵적 흐름과 비교해 무엇이 다른가요?"**

<details markdown="1">
<summary>답 확인</summary>

암묵적 흐름은 토큰을 브라우저 리다이렉트에 직접 실어 반환해 히스토리·`Referer`·프런트엔드 로그에 노출될 여지가 있다. 인가 코드 흐름은 브라우저를 거치는 구간에는 일회용 코드만 실어 보내고, 실제 토큰 교환은 서버 간 직접 통신(뒷단)으로만 이뤄지므로 토큰이 거치는 경로 자체가 줄어든다.

</details>

**"PKCE는 어떤 공격을 막기 위한 장치인가요?"**

<details markdown="1">
<summary>답 확인</summary>

인가 코드 가로채기 공격이다. `client_secret`을 안전하게 보관할 수 없는 클라이언트(모바일, SPA)에서 인가 코드가 탈취될 수 있는데, PKCE는 요청 시점에만 존재하는 무작위 `code_verifier`와 그 해시값을 대조해, 코드를 훔쳐도 원본 `code_verifier` 없이는 토큰으로 바꿀 수 없게 만든다.

</details>

## 한 줄 요약

> 인가 코드 흐름은 토큰을 브라우저가 보는 어떤 경로에도 절대 싣지 않으려는 설계이고, PKCE는 그렇게 대신 흐르는 인가 코드가 가로채이더라도 요청 시점에만 존재하는 비밀과 대조해야만 토큰으로 바뀌게 만드는 자물쇠다.
