## 정렬 기준을 파라미터로 받는 목록 API

JPA와 파라미터 바인딩을 쓰고 있으니 SQL 인젝션은 끝난 이야기라고 생각하기 쉽다. 그런데 목록 API에 정렬 옵션을 붙이는 순간 이런 코드가 들어간다.

```java
String sql = "select * from orders where member_id = ? order by " + sortColumn;
```

`member_id`는 얌전히 바인딩했는데 `sortColumn`은 문자열로 붙었다. 왜 이렇게 됐는지 직접 해보면 알 수 있다 — `order by ?`로 바꾸고 컬럼명을 바인딩하면 **동작하지 않는다.** 정렬 기준이 상수 문자열로 취급돼 아무 효과가 없거나 오류가 난다.

## 바인딩은 값만 보호한다

파라미터 바인딩이 안전한 이유는 입력을 이스케이프해주기 때문이 아니다. DB가 **쿼리 구조를 먼저 확정한 뒤** 값을 따로 받기 때문이다. 구조가 이미 정해졌으니 값에 무엇이 들어오든 구조를 바꿀 수 없다.

> 바인딩이 지켜주는 범위는 정확히 "값이 들어갈 자리"까지다. **쿼리의 구조에 해당하는 입력은 애초에 바인딩할 수 없고**, 남은 구멍은 전부 거기다.

구조에 해당하는 것들은 정해져 있다.

- 정렬 컬럼과 정렬 방향(`ORDER BY`, `ASC`/`DESC`)
- 테이블명과 컬럼명
- `IN` 절의 항목 개수처럼 쿼리 모양이 달라지는 부분
- 동적으로 붙는 검색 조건절 자체

이 자리들은 ORM을 쓰든 안 쓰든 똑같이 열려 있다. "JPA를 쓰니 안전하다"가 반만 맞는 이유다.

## 구조 입력은 허용목록으로만 막는다

이스케이프나 특수문자 제거로 막으려는 시도가 가장 흔한 오답이다. 구조에 들어갈 수 있는 값은 애초에 **유한하게 정해져 있으므로**, 그 목록에 있는지 확인하는 쪽이 간단하고 확실하다.

```java
private static final Map<String, String> SORTABLE = Map.of(
        "createdAt", "created_at",
        "amount", "total_amount");

String column = SORTABLE.get(sortKey);
if (column == null) {
    throw new IllegalArgumentException("지원하지 않는 정렬 기준");
}
```

사용자 입력이 SQL에 직접 닿지 않고, **미리 정의된 값 중 하나로 교체**된다는 점이 중요하다. 정렬 방향도 마찬가지로 `ASC`/`DESC` 두 값 중 하나로만 매핑한다. 스프링 데이터의 `Sort`를 쓰더라도 정렬 필드명이 검증 없이 들어오면 같은 문제가 생기므로, 허용 목록은 그대로 필요하다.

## ORM 안에서도 결합하면 똑같다

JPA를 쓰고 있어도 문자열을 이어 붙이는 순간 보호가 사라진다.

```java
@Query(value = "select * from orders where status = '" + status + "'", nativeQuery = true)
```

JPQL도 예외가 아니다. 엔티티 이름으로 쓰이긴 하지만 결합된 문자열이 그대로 쿼리가 되므로, 조건을 동적으로 만들 때는 `Criteria` API나 QueryDSL처럼 **구조를 코드로 조립하는 방식**을 쓰거나 `@Param` 바인딩을 유지해야 한다.

`LIKE` 검색에도 사소한 함정이 있다. 값 자체는 바인딩되더라도 사용자가 `%`를 넣으면 의도보다 훨씬 넓은 범위를 긁어간다. 인젝션은 아니지만 전체 테이블 스캔을 유발해 사실상 서비스 거부가 될 수 있으므로, 와일드카드 문자는 이스케이프하거나 제거하는 편이 안전하다.

## 인터뷰에서 이렇게 나온다

**"파라미터 바인딩을 쓰는데도 SQL 인젝션이 가능한 경우가 있나요?"**

<details markdown="1">
<summary>답 확인</summary>

있다. 바인딩은 DB가 쿼리 구조를 먼저 확정한 뒤 값을 받기 때문에 안전한 것이므로, 구조 자체에 해당하는 입력은 보호 대상이 아니다. 정렬 컬럼·정렬 방향·테이블명·동적 조건절은 바인딩할 수 없어 문자열로 결합되기 쉽고, 거기가 남은 공격면이다. 이런 입력은 허용 목록으로 미리 정의된 값에 매핑해야 한다.

</details>

**"정렬 컬럼을 안전하게 받으려면?"**

<details markdown="1">
<summary>답 확인</summary>

이스케이프가 아니라 허용 목록을 쓴다. 정렬 가능한 키와 실제 컬럼명을 매핑해두고 입력이 그 목록에 있을 때만 대응하는 컬럼명으로 교체하며, 없으면 거절한다. 사용자 입력이 SQL에 직접 닿지 않고 미리 정의된 값으로 바뀌므로 구조가 훼손될 여지가 없다.

</details>

## 한 줄 요약

> 파라미터 바인딩은 DB가 쿼리 구조를 먼저 확정하기 때문에 안전한 것이라 보호 범위가 "값이 들어갈 자리"까지이고, 정렬 컬럼이나 테이블명처럼 구조로 들어가는 입력은 바인딩 자체가 불가능해 허용 목록으로만 막을 수 있다.
