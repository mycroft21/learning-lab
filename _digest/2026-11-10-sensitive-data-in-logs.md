## 카드번호로 로그를 검색해보면 나온다

DB 컬럼은 암호화했고, 전송 구간은 TLS로 감쌌고, 접근 권한도 좁혀뒀다. 그런데 로그 검색창에 카드번호 형태의 패턴을 넣어보면 결과가 나온다.

```bash
grep -rE '[0-9]{13,16}' /var/log/app/ | head
```

```
2026-11-01 10:12:33 INFO  PaymentRequest(cardNumber=4111111111111111, cvc=123, ...)
```

롬복이 만들어준 `toString()`이 모든 필드를 찍었고, 로깅 코드는 그 객체를 그대로 넘겼다. 암호화는 DB에 **들어간 다음**부터 적용됐는데, 로그는 그 앞에서 찍혔다.

## 유출은 뒷문이 아니라 정문으로 나간다

보안 설계는 대개 "누가 침입하는가"를 중심으로 짜인다. 그런데 실제 유출 경로에는 침입이 없는 경우가 많다. 민감정보가 **정상적인 기능을 타고 평문으로 걸어 나가는** 것이다.

> 공격자가 DB를 뚫어야만 유출이 아니다. 로그·에러 응답·모니터링 도구는 **애초에 밖으로 내보내려고 만든 통로**이고, 민감정보는 거기에 섞여 나간다.

나가는 자리는 몇 군데로 정해져 있다.

- **객체를 통째로 찍는 로그.** `toString()` 자동 생성이 가장 흔한 원인이다. 필드가 추가될 때마다 로그 노출 범위도 같이 늘어나는데, 그걸 아무도 리뷰하지 않는다.
- **요청·응답 전체 로깅 필터.** 디버깅용으로 넣었다가 운영에 남은 경우가 많다. 결제 요청 본문이 통째로 적힌다.
- **예외 메시지와 스택 트레이스.** 바인딩 파라미터가 포함된 쿼리 로그, 실패한 요청 본문이 그대로 들어간다. 이게 에러 응답으로 클라이언트에게 반환되면 외부 노출이 된다.
- **모니터링·에러 추적 도구.** 예외가 발생하면 컨텍스트를 함께 수집해 외부 서비스로 보낸다. 우리 시스템에서는 지웠어도 그쪽에 남는다.
- **로그 수집 파이프라인.** 중앙 로그 저장소는 보통 접근 권한이 넓고 보존 기간이 길다. DB보다 훨씬 많은 사람이 본다.

## 지우는 대신 애초에 담기지 않게 한다

로그를 찍는 쪽에서 매번 가리는 방식은 오래 못 간다. 새 코드가 추가될 때마다 같은 주의를 반복해야 하고, 한 번 빠뜨리면 그대로 나간다. **민감한 값이 평범한 문자열로 돌아다니지 않게** 만드는 쪽이 유지된다.

```java
public record CardNumber(String value) {
    @Override
    public String toString() {
        return "CardNumber(****" + value.substring(value.length() - 4) + ")";
    }
}
```

타입으로 감싸두면 어디서 찍히든 마스킹된 형태만 나온다. 로깅하는 사람이 주의하지 않아도 되고, 실수가 한 곳에서 막힌다. 같은 이유로 `@ToString.Exclude`처럼 제외를 명시하는 방법보다 **애초에 그 값을 담는 타입을 따로 두는 쪽**이 견고하다.

구조적으로 함께 둘 것들이 있다.

- **요청·응답 전체 로깅은 운영에서 끈다.** 필요하면 샘플링하고, 본문은 지정한 필드만 남긴다.
- **에러 응답에 내부 정보를 싣지 않는다.** 클라이언트에는 식별자와 일반적인 메시지만 주고, 상세는 서버 로그에만 남긴다. 에러 응답 포맷을 표준화하는 방법 자체는 [ProblemDetail 편](/learning-lab/digest/2026-09-18-problem-detail-rfc9457/)에서 다뤘다 — 그 표준 필드에 무엇을 담을지가 여기의 문제다.
- **수집 파이프라인에 마스킹 규칙을 한 겹 더 둔다.** 애플리케이션이 실수해도 저장 직전에 걸러지도록 한다.
- **정기적으로 직접 검색해본다.** 위에서 한 것처럼 카드번호·주민번호 패턴으로 로그를 훑는 점검을 주기적으로 돌리면, 새로 생긴 노출을 빨리 찾는다.

## 인터뷰에서 이렇게 나온다

**"민감정보가 로그로 유출되는 경로에는 어떤 것이 있나요?"**

<details markdown="1">
<summary>답 확인</summary>

자동 생성된 `toString()`으로 객체를 통째로 찍는 로그, 디버깅용으로 넣었다가 남은 요청·응답 전체 로깅, 파라미터가 포함된 쿼리 로그와 스택 트레이스, 그리고 예외 컨텍스트를 외부로 전송하는 에러 추적 도구가 대표적이다. 중앙 로그 저장소는 접근 권한이 넓고 보존 기간이 길어 DB보다 노출 범위가 큰 경우도 많다.

</details>

**"로그 마스킹을 어디에 구현하는 게 좋나요?"**

<details markdown="1">
<summary>답 확인</summary>

로그를 찍는 지점마다 가리는 방식은 새 코드가 추가될 때마다 누락될 수 있다. 민감한 값을 전용 타입으로 감싸고 그 타입의 `toString()`이 마스킹된 형태만 반환하게 하면 어디서 출력되든 안전하다. 여기에 수집 파이프라인 단계의 마스킹 규칙을 한 겹 더 두어 애플리케이션의 실수를 받아내는 구성이 견고하다.

</details>

## 한 줄 요약

> 유출은 DB가 뚫려야만 일어나는 게 아니라 로그·에러 응답·모니터링 도구라는 정상 통로로 평문이 걸어 나가는 일이므로, 찍는 지점마다 가리는 대신 민감한 값을 전용 타입으로 감싸 어디서 출력되든 마스킹되게 만들어야 한다.
