## CPU가 바쁜데 HPA가 꿈쩍도 안 한다

`averageUtilization: 70`으로 HPA를 걸어뒀다. 노드 모니터링에서는 파드가 CPU를 상당히 쓰고 있는데 레플리카는 그대로다. 반대 사례도 있다 — 별로 안 바쁜 것 같은데 계속 파드를 늘린다.

HPA가 실제로 무엇을 보고 있는지 확인해보면 갈린다.

```bash
kubectl get hpa my-app
```

```
NAME     REFERENCE           TARGETS        REPLICAS
my-app   Deployment/my-app   18%/70%        3
```

`18%`는 노드 CPU에 대한 비율이 아니다. **`requests`에 대한 비율**이다.

## 기준점은 사용량이 아니라 `requests`다

HPA의 `averageUtilization`은 절대 사용량이 아니라 **`resources.requests`를 100%로 놓은 비율**이다.

```
utilization = 실제 사용량 / requests
```

그래서 같은 부하라도 `requests`를 어떻게 잡았느냐에 따라 숫자가 완전히 달라진다.

- **`requests`를 넉넉하게 잡았다면** — 실제로 꽤 쓰고 있어도 비율은 낮게 계산된다. 바쁜데 안 늘어나는 이유가 대개 이것이다.
- **`requests`를 빠듯하게 잡았다면** — 조금만 써도 100%를 넘어 계속 늘어난다.

> `requests`는 스케줄링 값이면서 동시에 **HPA의 기준점**이다. 둘은 따로 조정할 수 있는 값이 아니라 한쪽을 바꾸면 다른 쪽 동작이 같이 바뀌는 한 쌍이다.

여기서 바로 따라오는 결론이 하나 더 있다. **`requests`가 아예 없으면 CPU 기반 HPA는 동작하지 않는다.** 나눌 기준이 없으니 비율을 계산할 수가 없다. HPA를 걸었는데 `TARGETS` 열이 unknown으로 뜬다면 이것부터 확인해야 한다. `requests`가 스케줄러에게 하는 말이고 `limits`와 역할이 어떻게 다른지는 [requests/limits 편](/learning-lab/digest/2026-10-23-requests-limits-oomkilled/)에서 다뤘다.

## 레플리카 수는 비례식으로 정해진다

HPA는 복잡한 판단을 하지 않는다. 현재 레플리카 수에 비율을 곱해 올림한다.

```
목표 레플리카 = ceil( 현재 레플리카 × (현재 비율 / 목표 비율) )
```

3개가 돌고 있고 현재 90%, 목표가 70%라면 `ceil(3 × 90/70) = ceil(3.86) = 4`가 된다.

여기에 **약 10%의 허용 범위**가 붙는다. 현재 비율과 목표 비율의 비가 1에 가까우면(대략 0.9~1.1) 아무것도 하지 않는다. 목표가 70%인데 73%에서 안 늘어나는 건 고장이 아니라 이 허용 범위 안이기 때문이다. 미세한 변동마다 레플리카가 출렁이는 것을 막는 장치다.

## 반응이 느린 건 설정이 아니라 누적된 지연이다

트래픽이 급증했을 때 HPA가 즉시 대응하지 못하는 이유는 여러 지연이 순서대로 쌓이기 때문이다.

- 메트릭이 수집되고 집계되기까지 걸리는 시간
- HPA 컨트롤러가 주기적으로 평가하기까지의 간격
- 새 파드가 스케줄링되고 이미지를 받고 **기동을 마쳐 Ready가 될 때까지의 시간**

JVM 애플리케이션이라면 마지막 항목이 특히 길다. 이미 부하가 걸린 뒤에 늘리기 시작하므로, 급증 패턴이 분명한 서비스라면 HPA만으로 막기보다 최소 레플리카를 올려 여유를 두는 편이 현실적이다.

줄이는 쪽은 반대로 일부러 느리게 설계돼 있다. 기본적으로 **5분의 안정화 구간** 동안 관측된 값 중 가장 높은 권고를 택해, 순간적으로 한가해졌다고 파드를 줄였다가 다시 늘리는 왕복을 막는다. 늘리는 건 즉시, 줄이는 건 천천히가 기본값이다.

## 인터뷰에서 이렇게 나온다

**"HPA의 targetAverageUtilization 70%는 무엇에 대한 70%인가요?"**

<details markdown="1">
<summary>답 확인</summary>

노드 자원이나 `limits`가 아니라 `resources.requests`에 대한 비율이다. 따라서 `requests`를 크게 잡으면 실제로 바빠도 비율이 낮게 계산돼 확장이 안 되고, 작게 잡으면 과도하게 확장된다. `requests`가 없으면 기준값이 없어 CPU 기반 HPA 자체가 동작하지 않는다.

</details>

**"목표치를 넘겼는데도 HPA가 레플리카를 안 늘리는 경우는?"**

<details markdown="1">
<summary>답 확인</summary>

현재 비율과 목표 비율의 비가 약 10% 허용 범위 안이면 아무 동작도 하지 않는다. 목표 70%에 현재 73% 같은 경우가 여기 해당한다. 미세한 변동으로 레플리카가 출렁이는 것을 막기 위한 장치이고, 고장이 아니다.

</details>

## 한 줄 요약

> HPA는 사용량의 절대값이 아니라 `requests`를 100%로 놓은 비율로 판단하므로 `requests`를 어떻게 잡았는지가 스케일링 기준 자체를 정하고, `requests`가 없으면 비율을 계산할 수 없어 CPU 기반 HPA는 아예 동작하지 않는다.
