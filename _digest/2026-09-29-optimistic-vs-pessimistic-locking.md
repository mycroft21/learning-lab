## `@Version`을 걸면 그 행이 잠긴다는 착각

이름에 "락"이 들어가니 `@Version`을 붙이면 DB가 그 행을 어떻게든 잠가줄 것 같다. 실제로 나가는 SQL을 보면 잠그는 구문이 하나도 없다.

```sql
update product set name=?, stock=?, version=?
 where id=? and version=?
```

`where` 절에 버전이 하나 더 붙었을 뿐이다. 다른 트랜잭션이 먼저 커밋해서 버전이 올라가 있으면 이 `UPDATE`는 **0행을 갱신**하고, JPA는 영향 행이 0이라는 사실로부터 "누가 먼저 바꿨다"를 추론해 `OptimisticLockException`(Spring에서는 `ObjectOptimisticLockingFailureException`)을 던진다.

즉 낙관적 락은 잠그지 않는다. **아무도 막지 않은 채로 진행시키고, 커밋 시점에 어긋났는지를 확인할 뿐이다.**

## 고르는 것은 잠그는 방식이 아니라 충돌을 알아채는 시점이다

두 방식의 차이를 "락을 거느냐 안 거느냐"로 정리하면 선택 기준이 안 나온다. 정확한 축은 **충돌을 언제 알아채는가** 하나다.

- **낙관적 락 — 커밋 순간의 사후 감지.** 읽을 때 아무것도 막지 않는다. 대기가 없으니 처리량이 높지만, 충돌은 이미 작업을 다 한 뒤에 알게 된다. 그래서 실패를 되돌릴 방법, 즉 **재시도가 설계에 반드시 포함돼야 한다.**
- **비관적 락 — 읽는 순간의 사전 차단.** `select ... for update`로 DB 행 락을 잡고 시작하므로 충돌 자체가 발생하지 않는다. 대신 다른 트랜잭션은 그 자리에서 대기하고, 대기가 길어지면 타임아웃, 잠그는 순서가 엇갈리면 데드락이 된다.

여기서 선택 기준이 바로 따라 나온다. **충돌이 드물면 낙관적**(대부분의 요청이 대기 없이 통과하고 가끔만 재시도), **충돌이 잦으면 비관적**(실패와 재시도를 반복하는 비용이 대기 비용보다 커지는 지점부터)이다. 인기 상품 재고 차감처럼 같은 행에 경합이 몰리는 경로가 후자의 전형이다.

## 낙관적 락의 재시도는 자주 잘못 만들어진다

재시도를 붙일 때 흔히 나오는 형태가 이것이다.

```java
@Transactional
void decrease(Long id) {
    Product p = repository.findById(id).orElseThrow();
    try {
        p.decreaseStock();
    } catch (ObjectOptimisticLockingFailureException e) {
        decrease(id);   // 같은 트랜잭션 안에서 다시 시도
    }
}
```

동작하지 않는다. 충돌은 커밋 시점에 드러나므로 메서드 안에서는 잡히지도 않고, 설령 잡더라도 **같은 영속성 컨텍스트가 들고 있는 건 여전히 낡은 버전의 엔티티**라 다시 시도해도 같은 이유로 실패한다.

> 재시도는 트랜잭션 **바깥**에서, 엔티티를 **처음부터 다시 읽는 것**까지 포함해야 성립한다. 낡은 컨텍스트를 그대로 둔 재시도는 실패를 반복할 뿐이다.

한 가지 더, 벌크 연산으로 값을 바꾸면 `@Version`은 자동으로 올라가지 않는다. 버전 컬럼을 쿼리에서 직접 증가시키지 않으면 다른 트랜잭션이 충돌을 감지할 근거 자체가 사라진다. 벌크 연산이 영속성 컨텍스트를 건너뛰는 구조 자체는 [벌크 연산과 영속성 컨텍스트 불일치 편](/learning-lab/digest/2026-09-28-bulk-operation-persistence-context-mismatch/)에서 다뤘다.

## 비관적 락에서 실제로 부딪히는 것

- **잠그는 순서를 통일하지 않으면 데드락이 난다.** A가 1번→2번, B가 2번→1번 순서로 잠그면 서로를 기다린다. 여러 행을 잠가야 한다면 식별자 정렬처럼 **항상 같은 순서**를 강제하는 것이 예방책이다.
- **대기 시간을 방치하면 커넥션이 묶인다.** 락을 기다리는 동안 그 트랜잭션은 DB 커넥션을 쥐고 있다. 타임아웃(`jakarta.persistence.lock.timeout` 힌트)을 걸어 기다림의 상한을 정해두는 편이 낫다.
- **`PESSIMISTIC_READ`와 `PESSIMISTIC_WRITE`가 갈린다.** 전자는 다른 트랜잭션의 읽기를 허용하고 쓰기만 막으며, 후자는 배타적으로 잠근다. 읽고 나서 반드시 갱신할 거라면 후자를 잡아야 중간에 끼어드는 갱신이 막힌다.

## 인터뷰에서 이렇게 나온다

**"@Version 기반 낙관적 락은 어떤 원리로 충돌을 감지하나요?"**

<details markdown="1">
<summary>답 확인</summary>

DB에 락을 걸지 않는다. `UPDATE ... WHERE id = ? AND version = ?` 형태로 쿼리를 보내고, 다른 트랜잭션이 먼저 커밋해 버전이 올라가 있으면 영향 행이 0이 되는데 JPA는 그 사실로부터 충돌을 판정해 `OptimisticLockException`을 던진다. 커밋 시점의 사후 감지라서 재시도 설계가 반드시 따라와야 한다.

</details>

**"낙관적 락과 비관적 락 중 무엇을 고를지 어떤 기준으로 판단하나요?"**

<details markdown="1">
<summary>답 확인</summary>

같은 행에 대한 충돌 빈도로 판단한다. 충돌이 드물면 낙관적 락이 대기 없이 처리량을 확보하고 가끔의 재시도로 해결되지만, 인기 상품 재고 차감처럼 경합이 몰리면 실패와 재시도를 반복하는 비용이 대기 비용을 넘어서므로 비관적 락으로 순서를 강제하는 편이 낫다.

</details>

## 한 줄 요약

> 낙관적 락과 비관적 락의 진짜 차이는 잠그는 방식이 아니라 충돌을 알아채는 시점이며, 낙관적 락이 잠그지 않고 `where version = ?`의 영향 행 수로 사후 판정한다는 사실에서 재시도가 필수라는 것도 비관적 락이 대기·데드락을 떠안는다는 것도 전부 따라 나온다.
