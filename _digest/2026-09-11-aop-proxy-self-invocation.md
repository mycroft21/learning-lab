## 동료가 @Transactional 걸어놓고도 왜 안먹었냐고 물어봤을 때

신규 입사자가 서비스 클래스 안에서 `save()`가 같은 클래스의 `internalSave()`를 `this.internalSave()`로 호출했는데, 거기 붙인 `@Transactional`이 전혀 동작하지 않았다며 버그 리포트를 올렸다. 원인은 코드 오타가 아니라 **AOP 프록시의 구조적 한계**다.

자문자답: "프록시가 다 처리해주는 거 아니었어?" → 프록시는 **외부에서 들어오는 호출**만 가로챌 수 있다. 객체 내부에서 `this`로 자기 자신을 부르면 프록시를 거치지 않고 원본 메서드가 그대로 실행된다.

## Spring AOP는 프록시 기반이지 바이트코드 위빙이 아니다

Spring AOP는 기본적으로 **런타임 프록시** 방식이다. 대상 빈을 감싸는 프록시 객체를 만들어 빈 등록 시점에 원본 대신 컨테이너에 등록한다. AspectJ처럼 컴파일/로드 타임에 바이트코드 자체를 조작하는 위빙 방식과는 다르다.

| 구분 | 생성 조건 | self-invocation 영향 |
| --- | --- | --- |
| JDK 동적 프록시 | 대상이 인터페이스 구현 | 영향 받음 |
| CGLIB 프록시 | 인터페이스 없거나 proxyTargetClass=true | 영향 받음 |
| AspectJ 위빙 | 컴파일/로드타임 바이트코드 조작 | 영향 없음 |

Spring Boot는 2.x부터 `spring.aop.proxy-target-class` 기본값을 `true`로 바꿔서, 인터페이스가 있어도 기본적으로 **CGLIB**(서브클래스 상속 방식) 프록시를 만든다는 점도 인터뷰에서 자주 나온다.

## self-invocation이 실제로 깨뜨리는 기능들

- `@Transactional` - 내부 호출 시 트랜잭션 시작/커밋 안 됨
- `@Cacheable`/`@CacheEvict` - 캐시 저장/무효화 스킵됨
- `@Async` - 별도 쓰레드 실행 안 되고 동기 실행됨
- `@Retryable` - 재시도 로직 미적용

> 프록시가 걸린 애노테이션은 "메서드를 어떻게 호출했는가"에 따라 동작 여부가 갈린다 — 같은 클래스 안이면 무조건 의심하라.

## 그럼 어떻게 피하나

<details markdown="1">
<summary>흔한 해결책들과 트레이드오프</summary>

가장 널리 쓰이는 방법은 자기 자신을 `ApplicationContext`나 `@Lazy` 자기 참조 필드 주입으로 프록시 참조를 얻어 호출하는 것이다. 더 근본적인 방법은 내부 호출용 로직을 별도 빈(클래스)으로 분리해 외부에서 프록시를 거쳐 호출하도록 구조를 바꾸는 것이다. AspectJ 컴파일 타임 위빙을 쓰면 self-invocation 문제 자체가 사라지지만, 빌드 복잡도가 올라간다.
</details>

## 인터뷰 단골 질문

1. "@Transactional이 안 먹는 이유가 뭘 수 있나요?" → self-invocation으로 프록시를 우회했을 가능성을 먼저 의심한다고 답한다
2. "JDK 동적 프록시와 CGLIB의 차이는?" → 인터페이스 기반이냐 서브클래싱이냐, 그리고 Boot는 기본이 CGLIB라는 점을 짚는다

## 한 줄 요약

> Spring AOP는 프록시를 거쳐야만 동작하므로, 같은 클래스 안에서 this로 호출하면 @Transactional/@Cacheable/@Async 같은 애노테이션이 조용히 무시된다.

## 코드 리뷰에서는 안 보이고 로그에서만 보이는 버그

`@Transactional` 붙여놨는데 롤백이 안 된다, `@Cacheable` 붙여놨는데 캐시가 매번 miss 난다, `@Async`인데 호출한 스레드가 그대로 블로킹된다 — 세 증상의 원인이 전부 같은 경우가 실무에서 제일 많다. 같은 클래스 안에서 `this.otherMethod()`로 호출했을 뿐인데, 어드바이스가 통째로 무시된 것이다.

문제는 이게 컴파일 타임은 물론 대부분의 로컬 테스트에서도 안 걸린다는 점이다. 트랜잭션 롤백 안 되는 케이스는 "정상 흐름에서는 예외가 안 나서" 몇 주씩 묻혀 있다가, 운영에서 예외가 터진 날 데이터 정합성이 깨진 걸로 발견된다. 인터뷰에서 "AOP가 안 걸리는 경우를 아는 대로 말해보라"는 질문이 잘 나오는 이유도 이게 신입은 잘 모르고 사고를 쳐본 사람만 아는 지점이기 때문이다.

## self-invocation이 아닌데도 안 걸리는 경우

"같은 클래스 안에서 호출"만 함정이라고 알고 있으면 절반만 아는 것이다. 실제로는 프록시가 아예 만들어지지 않거나, 만들어져도 특정 메서드를 감싸지 못하는 경우가 더 많다.

- **`private` 메서드**: JDK 동적 프록시든 CGLIB든 오버라이드가 불가능해서 애초에 어드바이스를 못 건다. Spring 자체가 `private` 메서드의 `@Transactional`을 조용히 무시한다(예외를 던지지 않는다).
- **`final` 메서드 / `final` 클래스**: CGLIB는 대상 클래스를 상속한 서브클래스를 런타임에 만들어서 프록시로 쓴다. `final`이면 상속 자체가 안 되니 프록시 생성 시점에 실패하거나 어드바이스가 안 걸린다.
- **`static` 메서드**: 인스턴스 프록시 메커니즘 자체가 적용될 여지가 없다.
- **생성자 안에서의 호출**: `this`가 아직 프록시로 감싸이기 전 원본 빈이기 때문에, 생성자에서 부르는 `self` 메서드는 프록시를 절대 못 거친다.
- **내부에서 새로 만든 객체**: `new SomeService()`로 직접 생성한 인스턴스를 호출하면 그건 스프링 빈도 아니고 프록시도 아니다. 당연히 안 걸린다.

> 프록시는 "빈으로 주입받아 호출한 경로"에만 걸린다. 원본 객체 안에서 일어나는 호출은 프록시를 거치지 않는다는 원칙 하나만 정확히 기억하면 위 다섯 가지가 전부 같은 이유로 설명된다.

## JDK 동적 프록시 vs CGLIB, 인터뷰에서 갈리는 지점

"Spring AOP는 인터페이스 기반이다"라고 외워둔 사람이 꽤 있는데, Spring Boot 2.0부터는 기본값이 CGLIB로 바뀌어서 인터페이스가 있어도 클래스 기반 프록시를 쓴다(`spring.aop.proxy-target-class=true`가 기본).

| 구분 | JDK 동적 프록시 | CGLIB |
|---|---|---|
| 전제조건 | 인터페이스 필수 | 인터페이스 없어도 됨 |
| 구현 방식 | 인터페이스 구현체를 런타임 생성 | 대상 클래스를 상속한 서브클래스 생성 |
| `final` 클래스/메서드 | 영향 없음 | 프록시 불가 / 해당 메서드 미적용 |
| 기본값 (Boot 2.0+) | 인터페이스 없을 때만 fallback | 기본 |
| 캐스팅 | 구현 인터페이스로만 캐스팅 가능 | 구체 클래스로도 캐스팅 가능 |

여기서 자주 나오는 후속 질문이 "그럼 인터페이스 있는 빈을 구체 클래스 타입으로 주입받으면?"이다. 기본 설정(CGLIB)에서는 되지만, `proxy-target-class=false`로 JDK 프록시를 강제한 환경이라면 `ClassCastException`이 난다 — 프록시가 인터페이스만 구현한 객체라서 원본 클래스 타입이 아니기 때문이다.

## "그럼 AopContext 쓰면 되잖아요"의 함정

self-invocation을 우회하는 방법으로 `AopContext.currentProxy()`가 종종 언급된다. 동작은 하지만 실무에서는 안티패턴에 가깝다는 걸 알고 써야 한다.

<details markdown="1">
<summary>expose-proxy 방식과 그게 별로인 이유</summary>

`@EnableAspectJAutoProxy(exposeProxy = true)`로 켜두면 현재 요청을 처리 중인 프록시를 스레드 로컬에 노출시켜준다.

```java
@Transactional
public void outer() {
    ((OrderService) AopContext.currentProxy()).inner();
}
```

문제는 세 가지다.

1. AOP 프레임워크(Spring)에 대한 직접 의존이 비즈니스 코드에 그대로 노출된다.
2. `exposeProxy=true`를 깜빡하면 `IllegalStateException`이 나는데, 이게 컴파일 타임에 안 잡힌다.
3. 캐스팅 타입을 프록시 종류에 맞게 정확히 알아야 해서 리팩터링에 취약하다.

실무에서 더 선호되는 해법은 두 가지다. 자기 자신을 필드로 주입받아(`@Lazy` 필요, 순환 참조라서) 그 프록시를 통해 호출하거나, 애초에 `inner()`를 별도 컴포넌트로 분리해서 self-invocation 자체가 발생할 여지를 없애는 것이다. 후자가 더 깨끗하고, 실제로 코드 리뷰에서 "메서드를 다른 클래스로 빼라"는 코멘트로 이어지는 경우가 많다.

</details>

## 한 줄 요약

> `@Transactional`, `@Cacheable`, `@Async`가 안 먹는다면 먼저 의심할 것은 로직이 아니라 "이 호출이 프록시를 거쳤는가"이고, 안 거쳤다면 `private`/`final`/`static`/생성자 호출/self-invocation 다섯 가지 중 하나다.
