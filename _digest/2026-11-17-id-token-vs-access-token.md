## 토큰을 두 개 받았는데, 하나만 쓰고 있었다

OIDC 로그인이 끝나면 보통 토큰이 두 개 돌아온다. 코드 몇 줄로 확인해보면 흔한 구현이 드러난다.

```java
OAuth2AccessToken accessToken = tokenResponse.getAccessToken();
String email = webClient.get()
    .uri(userInfoEndpoint)
    .headers(h -> h.setBearerAuth(accessToken.getTokenValue()))
    .retrieve()
    .bodyToMono(UserInfo.class)
    .block()
    .getEmail();
// id_token은 응답에 들어있지만 어디서도 검증하지 않는다
```

액세스 토큰으로 `/userinfo`를 호출해 이메일을 받아오고, 응답과 함께 온 ID 토큰은 거들떠보지도 않는다. 동작은 한다. 그런데 "사용자가 누구인지"를 확정하는 근거를 **서명도 안 보고 신뢰 확장자도 안 가린 네트워크 호출 하나**에 전부 걸어둔 셈이다.

## 받는 사람이 다르면 쓰는 법도 다르다

[지난 편](/learning-lab/digest/2026-11-16-oauth2-is-delegation-not-login/)에서 액세스 토큰의 `aud`가 우리 앱이 아닐 수 있다는 걸 확인했다. 그 토큰이 애초에 **누구를 향해 발급됐는지**를 보면 두 토큰의 역할이 갈린다.

- **액세스 토큰의 수신자는 자원 서버다.** `aud`는 보통 API나 자원 서버의 식별자이고, 클라이언트는 이 토큰의 내용물을 해석할 필요도 권한도 없다. 형식이 불투명한 문자열이어도 무방한 이유가 이것이다 — **클라이언트는 그냥 전달자일 뿐**이다.
- **ID 토큰의 수신자는 클라이언트 자신이다.** `aud`가 바로 우리 앱의 `client_id`다. 그래서 ID 토큰은 **반드시 JWT이고 서명이 있어야** 한다. 클라이언트가 그 서명을 발급자의 공개키로 직접 검증하고, `aud`가 자기 자신인지, `iss`가 신뢰하는 발급자인지, `nonce`가 자기가 요청에 실어 보낸 값과 같은지까지 확인해야 비로소 "이 사람이 로그인했다"고 말할 수 있다.

> 액세스 토큰은 자원 서버에게 보여주는 출입증이고, ID 토큰은 클라이언트에게 주는 신원 증명서다. 받는 사람이 다르므로 한쪽을 다른 쪽 용도로 쓸 수 없다.

두 토큰을 실제로 디코드해 비교해보면 이 차이가 그대로 보인다.

```json
// id_token — 우리 앱을 위한 것
{"iss": "https://accounts.example.com", "aud": "our-client-id", "sub": "u123", "nonce": "xyz", "exp": 1793000000}

// access_token (JWT 형식인 경우) — 자원 서버를 위한 것
{"iss": "https://accounts.example.com", "aud": "https://api.example.com/userinfo", "scope": "openid email", "exp": 1793000000}
```

`aud`가 `our-client-id`인 쪽만 "우리를 향한" 토큰이다.

## `/userinfo` 호출 자체는 틀리지 않았다

여기서 혼동하기 쉬운 지점이 있다. `/userinfo`를 액세스 토큰으로 호출하는 것 자체는 정상적인 OAuth 사용법이다 — 그 엔드포인트도 결국 "사용자 프로필"이라는 자원을 내어주는 자원 서버의 일부이기 때문이다. 문제는 **그 호출 결과를 신원 확인의 유일한 근거로 삼고 ID 토큰 검증을 생략하는 것**이다.

ID 토큰 검증을 생략하면 두 가지를 잃는다.

- **서명 검증이 빠진다.** `/userinfo` 응답은 TLS로만 보호되고, 중간의 프록시나 로깅 레이어를 거치며 조작될 여지를 ID 토큰만큼 좁게 막지 못한다.
- **`nonce` 검증이 빠진다.** 로그인 요청을 보낼 때 실어 보낸 무작위 값이 응답의 ID 토큰에 그대로 돌아오는지 확인하는 절차인데, 이게 빠지면 공격자가 다른 세션에서 받은 토큰을 끼워 넣는 유형의 공격에 노출된다.

그래서 OIDC 클라이언트 라이브러리를 쓰고 있다면 토큰 교환 직후 **ID 토큰 검증이 자동으로 일어나는지**부터 확인해야 한다. 직접 구현한 코드라면 `/userinfo` 호출과 별개로 ID 토큰의 서명·`aud`·`iss`·`nonce`·`exp`를 명시적으로 검증하는 단계가 있는지 봐야 한다.

## 인터뷰에서 이렇게 나온다

**"ID 토큰과 액세스 토큰을 섞어 쓰면 어떤 문제가 생기나요?"**

<details markdown="1">
<summary>답 확인</summary>

두 토큰은 수신자가 다르다. 액세스 토큰은 자원 서버를 대상으로 발급되어 형식이나 내용이 클라이언트가 해석하도록 보장되지 않고, ID 토큰은 클라이언트 자신을 대상으로 발급되어 서명 검증과 `aud`·`iss`·`nonce` 확인이 명세상 요구된다. 액세스 토큰만으로 신원을 판단하면 이 검증 절차 전체를 건너뛰게 되어, 서명 위조나 토큰 치환 공격을 막을 장치가 사라진다.

</details>

**"왜 ID 토큰은 항상 JWT이고 서명 검증이 필수인가요?"**

<details markdown="1">
<summary>답 확인</summary>

ID 토큰은 클라이언트가 직접 읽고 신뢰 여부를 판단해야 하는 토큰이기 때문이다. 액세스 토큰은 자원 서버만 해석하면 되므로 불투명한 문자열이어도 되지만, ID 토큰은 클라이언트가 중간자나 위조를 거치지 않고 발급자가 직접 서명했다는 것을 스스로 확인할 수 있어야 하므로 서명된 JWT 형식이 명세로 강제된다.

</details>

## 한 줄 요약

> 액세스 토큰은 자원 서버에게 보여주는 출입증이고 ID 토큰은 클라이언트에게 주는 신원 증명서라 받는 사람이 다르므로, `/userinfo` 호출로 받은 데이터를 신원 확인의 전부로 삼고 ID 토큰의 서명·`aud`·`nonce` 검증을 생략하면 그 확인은 처음부터 성립하지 않는다.
