## `@Transactional` 안에 넣었으니 같이 성공할 거라는 착각

주문을 저장하면서 다른 서비스에 알리는 코드는 보통 이렇게 생겼다.

```java
@Transactional
void placeOrder(Order order) {
    orderRepository.save(order);
    kafkaTemplate.send("orders", new OrderPlacedEvent(order));
}
```

`@Transactional` 안에 둘 다 넣어뒀으니 "DB 저장과 메시지 발행이 같이 성공하거나 같이 실패하겠지"라고 기대하기 쉽다. 그런데 `kafkaTemplate.send`는 스프링의 트랜잭션 매니저가 관리하는 자원이 아니다. DB 커밋이 실패해서 롤백돼도 이미 나간 메시지는 돌아오지 않고, 메시지 발행이 네트워크 문제로 실패해도 DB 커밋은 그대로 끝난다.

## 둘은 애초에 하나의 트랜잭션으로 묶을 수 없는 별개의 시스템이다

DB와 메시지 브로커는 서로 다른 리소스다. 분산 트랜잭션(2PC) 없이는 "둘 다 성공 아니면 둘 다 실패"를 보장할 방법이 없고, 실무에서 2PC를 메시지 브로커와 거는 구성은 거의 쓰지 않는다. 그래서 실제로는 네 가지 경우의 수가 전부 열려 있다.

- DB 커밋 성공, 메시지 발행 성공 — 의도한 정상 경로.
- **DB 커밋 성공, 메시지 발행 실패** — 주문은 저장됐는데 다른 서비스는 영원히 모른다. 유실.
- **DB 커밋 실패(롤백), 메시지는 이미 나감** — 존재하지 않는 주문에 대한 이벤트가 돌아다닌다. 유령 이벤트.
- 순서를 바꿔 메시지를 먼저 보내면, 컨슈머가 그 이벤트를 받고 DB를 조회했을 때 아직 커밋 전이라 데이터가 없을 수도 있다.

이 중 하나라도 허용하면 안 되는 흐름(주문·결제처럼 돈이 걸린 경우)이라면, "같이 묶으려는 시도" 자체를 버려야 한다.

## 아웃박스: "둘 다 성공"을 포기하고 "하나만 쓰고 나중에 옮긴다"로 바꾼다

트랜잭셔널 아웃박스 패턴은 두 시스템에 동시에 쓰는 대신, **하나의 DB 트랜잭션 안에 두 테이블을 쓴다.**

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (id, aggregate_id, event_type, payload, published)
  VALUES (..., 'OrderPlaced', '{...}', false);
COMMIT;
```

`orders`와 `outbox`는 같은 DB, 같은 로컬 트랜잭션 안에 있으므로 원자성이 자동으로 보장된다. 메시지 발행 자체는 트랜잭션 밖으로 완전히 빼서, 별도의 프로세스(아웃박스 테이블을 주기적으로 폴링하거나, Debezium 같은 CDC로 테이블 변경을 감지하는 퍼블리셔)가 `published = false`인 행을 읽어 브로커로 보내고 완료 표시를 남긴다.

> 두 시스템에 동시에 쓰는 문제를, "한 시스템에 쓰고 그걸 다른 시스템으로 옮기는" 문제로 바꾼 것이다. 옮기는 작업은 실패해도 재시도하면 되지만, 애초에 두 곳에 동시에 쓰는 작업은 반만 성공한 상태를 되돌릴 방법이 없다.

이렇게 분리된 "하나의 트랜잭션 경계"가 시스템이 둘로 갈라지면 어떻게 깨지는지는 [Spring의 트랜잭션 전파 편](/learning-lab/digest/2026-09-13-transaction-propagation/)과 [JPA의 트랜잭션 전파와 영속성 컨텍스트 편](/learning-lab/digest/2026-09-26-transaction-propagation-persistence-context/)에서 다룬 "경계는 어디까지인가"의 질문이 분산 환경으로 확장된 것이다.

## 공짜는 아니다 — 최소 한 번은 보장하지만 정확히 한 번은 아니다

퍼블리셔가 메시지를 보낸 뒤 `published = true`로 표시하기 **전에** 죽으면, 재시작 후 같은 행을 다시 읽어 또 발행한다. 그래서 아웃박스가 보장하는 건 "최소 한 번은 간다"이지 "딱 한 번만 간다"가 아니다. 유실은 없앴지만 중복은 남는다 — 이 중복을 받는 쪽에서 어떻게 처리하느냐는 또 다른 주제다.

## 인터뷰에서 이렇게 나온다

**"DB 저장과 메시지 발행을 같은 @Transactional 안에 넣으면 왜 안전하지 않나요?"**

<details markdown="1">
<summary>답 확인</summary>

메시지 브로커는 스프링의 트랜잭션 매니저가 관리하는 자원이 아니라서, DB 롤백이 메시지 발행을 취소시키지 못하고 메시지 발행 실패가 DB 롤백으로 이어지지도 않는다. 두 시스템에 각각 쓰는 작업이라 분산 트랜잭션 없이는 원자성이 성립하지 않고, 그 결과로 유실이나 유령 이벤트가 둘 다 열려 있다.

</details>

**"아웃박스 패턴은 이 문제를 어떻게 피하나요?"**

<details markdown="1">
<summary>답 확인</summary>

메시지 브로커에 직접 쓰는 대신 같은 DB의 아웃박스 테이블에 비즈니스 데이터와 함께 같은 로컬 트랜잭션으로 기록한다. 하나의 DB 트랜잭션이므로 원자성이 자동으로 보장되고, 실제 브로커 발행은 별도 프로세스가 트랜잭션 밖에서 비동기로 처리한다. 대신 그 퍼블리셔가 발행 후 표시 전에 실패하면 중복 발행이 생길 수 있어 최소 한 번 전달만 보장된다.

</details>

## 한 줄 요약

> DB 커밋과 메시지 발행은 서로 다른 시스템에 대한 쓰기라서 하나의 트랜잭션으로 묶을 수 없고, 아웃박스 패턴은 이 "둘 다 성공"을 포기하는 대신 같은 DB 트랜잭션 안에 이벤트를 먼저 기록해두고 실제 발행은 그 기록을 나중에 옮기는 별도 작업으로 떼어낸다.
