## "1차 캐시니까 조회가 빨라진다"를 먼저 의심한다

영속성 컨텍스트를 캐시로 이해하고 있으면 자연스럽게 따라오는 기대가 있다. 같은 엔티티를 여러 번 조회하는 코드에서 DB 왕복이 줄어들 거라는 기대다. 실제로 확인해보면 절반만 맞다.

```java
@Transactional
void sameTransaction() {
    Member a = em.find(Member.class, 1L);   // SELECT 나감
    Member b = em.find(Member.class, 1L);   // SELECT 안 나감
    System.out.println(a == b);              // true
}
```

여기까지는 기대대로다. 그런데 이 두 줄을 서로 다른 트랜잭션으로 갈라놓으면 `SELECT`는 두 번 나가고 `a == b`는 `false`가 된다. 웹 애플리케이션에서 요청 하나가 트랜잭션 하나를 쓰고, 그 안에서 같은 엔티티를 두 번 이상 조회하는 코드가 얼마나 되는지 세어보면 — 캐시로서의 적중률은 기대만큼 높지 않다. 성능을 위한 장치라고 보기엔 수명이 너무 짧다.

## 캐시가 아니라 동일성 보장 장치다

영속성 컨텍스트의 본질은 **하나의 트랜잭션 안에서 같은 식별자는 반드시 같은 자바 인스턴스여야 한다**는 보장이다. 내부적으로 식별자 → 인스턴스의 맵(identity map)을 들고 있고, 이미 들고 있는 식별자면 새로 만들지 않고 그 인스턴스를 그대로 돌려준다. `SELECT`가 안 나가는 건 이 보장을 지키는 과정에서 따라오는 부산물이지 목적이 아니다.

이 하나를 잡으면 나머지가 전부 따라온다.

- **왜 `==` 비교가 성립하나** — 같은 트랜잭션 안에서라면 어떤 경로로 조회하든(`find`, JPQL, 연관관계 탐색) 같은 인스턴스가 나온다. 그래서 `equals`를 구현하지 않아도 동일성 비교가 통한다.
- **왜 변경 감지가 가능한가** — 컨테이너가 인스턴스를 붙잡고 있으니 읽은 시점의 상태와 지금 상태를 비교할 대상이 생긴다. 인스턴스를 추적하지 않으면 무엇이 바뀌었는지 알 방법 자체가 없다.
- **왜 트랜잭션이 끝나면 사라지나** — 동일성 보장의 범위가 트랜잭션이기 때문이다. 트랜잭션이 끝난 뒤에도 같은 인스턴스를 유지하면, 그 사이 DB에서 바뀐 값과 어긋난 낡은 객체를 계속 들고 있게 된다.

> 성능 캐시로 쓰려고 만든 물건이 아니라서, 성능 캐시로 기대하면 항상 실망한다. 여러 트랜잭션에 걸쳐 재사용되는 캐시는 별도로 켜야 하는 2차 캐시의 몫이다.

## 준영속 상태가 어려운 이유도 여기서 나온다

트랜잭션이 끝나 컨텍스트에서 떨어져 나온 엔티티(준영속, detached)를 다시 반영하려고 `merge`를 부르면, 많은 사람이 "내가 넘긴 그 객체가 다시 영속 상태가 된다"고 생각한다. 실제로는 다르다.

```java
Member detached = /* 트랜잭션 밖에서 들고 있던 객체 */;
Member managed = em.merge(detached);
System.out.println(managed == detached);  // false
```

`merge`는 넘긴 객체를 관리 대상으로 삼는 게 아니라, **같은 식별자의 관리 대상 인스턴스를 찾거나 새로 만든 뒤 값을 복사해 넣고 그것을 반환**한다. 동일성 보장이 먼저이기 때문에, 이미 컨텍스트가 그 식별자에 대해 들고 있는 인스턴스가 있으면 그게 정답이고 외부에서 온 객체는 값의 출처일 뿐이다. `merge`의 반환값을 안 받고 원본을 계속 쓰는 코드가 조용히 반영 안 되는 이유가 이것이다.

## 인터뷰에서 이렇게 나온다

**"영속성 컨텍스트의 1차 캐시가 애플리케이션 성능에 실제로 얼마나 기여하나요?"**

<details markdown="1">
<summary>답 확인</summary>

수명이 트랜잭션 하나라서 성능 기여는 제한적이라고 답하는 게 정확하다. 1차 캐시는 성능 최적화 장치가 아니라 같은 식별자에 대해 같은 인스턴스를 보장하기 위한 identity map이고, DB 왕복이 줄어드는 건 그 보장의 부산물이다. 트랜잭션을 넘어서는 캐싱이 필요하면 2차 캐시가 별도로 있다.

</details>

**"merge를 호출했는데 원본 객체에는 변경이 반영되지 않는 이유는?"**

<details markdown="1">
<summary>답 확인</summary>

`merge`는 인자로 받은 객체를 영속 상태로 바꾸지 않는다. 같은 식별자의 관리 대상 인스턴스를 찾거나 만들어서 값만 복사한 뒤 그 인스턴스를 반환하므로, 이후 작업은 반환값으로 해야 한다. 동일성 보장 규칙상 한 식별자에 대응하는 관리 인스턴스는 하나뿐이기 때문이다.

</details>

## 한 줄 요약

> 영속성 컨텍스트는 성능을 위한 캐시가 아니라 한 트랜잭션 안에서 같은 식별자에 같은 인스턴스를 보장하는 장치이고, `SELECT`가 줄어드는 것도 변경 감지가 가능한 것도 `merge`가 원본을 관리하지 않는 것도 전부 그 보장에서 따라 나온다.
