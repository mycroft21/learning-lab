## 로그에 OutOfMemoryError가 없는데 메모리로 죽었다

`-Xmx2g`를 주고 `limits.memory`를 `2Gi`로 맞췄다. 힙을 넘지 않게 했으니 안전할 것 같은데 파드가 주기적으로 죽는다. 그런데 애플리케이션 로그에는 `OutOfMemoryError`가 **한 줄도 없다.** 힙 덤프도 안 남는다.

```
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
```

이건 JVM이 "힙이 모자랍니다"라고 던진 예외가 아니다. **커널이 밖에서 프로세스를 죽인 것**이라 JVM은 유언을 남길 기회조차 없었다. 둘은 이름만 비슷할 뿐 완전히 다른 사건이다.

| 구분 | `OutOfMemoryError` | `OOMKilled` |
|---|---|---|
| 판정 주체 | JVM (힙이 부족) | 커널 (컨테이너 한도 초과) |
| 남는 흔적 | 예외 스택, 힙 덤프 | 종료 코드 137, 로그 없음 |
| 기준 | `-Xmx` | 컨테이너 전체 메모리 |

## 한도의 기준은 힙이 아니라 프로세스 전체다

`-Xmx`는 **힙의 상한**이고 컨테이너 `limits`는 **그 프로세스가 쓰는 모든 메모리**의 상한이다. 둘은 재는 대상이 다르다. 메모리 한도 초과가 왜 스로틀링이 아니라 종료로 이어지는지는 [requests/limits 편](/learning-lab/digest/2026-10-23-requests-limits-oomkilled/)에서 다뤘고, 여기서는 그 한도를 채우는 쪽에 힙 말고 무엇이 더 들어가는지를 본다.

- **메타스페이스** — 클래스 메타데이터. 프레임워크와 라이브러리가 많을수록 커진다.
- **스레드 스택** — 스레드 하나에 보통 1MB 안팎. 톰캣 워커 200개에 커넥션 풀, 스케줄러, 컨슈머까지 더하면 수백 MB가 된다.
- **코드 캐시** — JIT가 컴파일한 네이티브 코드.
- **다이렉트 버퍼와 네이티브 할당** — Netty를 쓰는 스택(웹플럭스, gRPC, 카프카 클라이언트)에서 특히 크다. 힙 밖이라 GC 로그에도 안 보인다.
- **GC 자체의 자료구조와 JVM 기본 사용량.**

그래서 `-Xmx`와 `limits`를 같은 값으로 맞추는 것은 **반드시 죽는 설정**이다. 힙을 꽉 채우기 전에 힙 밖 영역이 한도를 먼저 넘긴다.

> `-Xmx`는 천장이 아니라 바닥이다 — 컨테이너가 실제로 필요로 하는 메모리는 항상 `-Xmx`보다 크다.

## 비율로 주고, 실제 사용량을 재서 맞춘다

고정값을 손으로 계산하는 대신 JVM이 컨테이너 한도를 읽어 비율로 잡게 하는 편이 안전하다.

```
-XX:MaxRAMPercentage=70
```

JVM이 cgroup에서 한도를 읽고 그 비율만큼을 힙 상한으로 쓴다. JVM이 애초에 cgroup 한도를 읽을 수 있는 것 자체가 [cgroup 편](/learning-lab/digest/2026-10-20-cgroup-limits-vs-visibility/)에서 다룬 `UseContainerSupport`에 달려 있다. 기본값은 25%로 꽤 보수적이라 그대로 두면 메모리를 남기게 되고, 반대로 90%처럼 올리면 힙 밖 영역이 설 자리가 없어진다. 시작점은 보통 70% 안팎이고, 정확한 값은 재서 맞춰야 한다. `-Xmx`를 명시하면 이 비율 설정은 무시된다는 점도 같이 기억할 만하다.

실제로 힙 밖에서 무엇이 얼마나 쓰는지는 추측하지 말고 측정한다.

```
-XX:NativeMemoryTracking=summary
```

이걸 켜고 아래를 실행하면 힙·메타스페이스·스레드·코드 캐시가 각각 얼마를 쓰는지 나온다.

```bash
jcmd 1 VM.native_memory summary
```
 스레드 항목이 예상보다 크면 풀 크기를, 네이티브 항목이 크면 다이렉트 버퍼 사용처를 보면 된다.

## 인터뷰에서 이렇게 나온다

**"-Xmx를 컨테이너 메모리 한도와 같게 설정하면 어떻게 되나요?"**

<details markdown="1">
<summary>답 확인</summary>

반드시 `OOMKilled`가 난다. `-Xmx`는 힙 상한이고 컨테이너 한도는 프로세스 전체 메모리의 상한인데, 메타스페이스·스레드 스택·코드 캐시·다이렉트 버퍼 같은 힙 밖 영역이 추가로 쌓이기 때문이다. 힙이 상한에 닿기 전에 전체 사용량이 먼저 한도를 넘는다.

</details>

**"OutOfMemoryError와 OOMKilled는 어떻게 다른가요?"**

<details markdown="1">
<summary>답 확인</summary>

`OutOfMemoryError`는 힙이 부족해 JVM이 던지는 예외라 스택과 힙 덤프가 남고, `OOMKilled`는 컨테이너 전체 메모리가 한도를 넘어 커널이 프로세스를 강제 종료한 것이라 종료 코드 137만 남고 애플리케이션 로그에는 아무 흔적이 없다. 로그가 깨끗한데 메모리로 죽었다면 후자를 의심해야 한다.

</details>

## 한 줄 요약

> `OOMKilled`의 기준은 힙이 아니라 프로세스 전체 메모리이고 메타스페이스·스레드 스택·다이렉트 버퍼가 그 위에 쌓이므로, `-Xmx`를 한도에 맞추면 반드시 죽고 비율로 주되 실제 사용량을 재서 맞춰야 한다.
