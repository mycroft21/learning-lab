## 한 줄 켰는데 처리량이 그대로다

`spring.threads.virtual.enabled=true`를 넣고 부하 테스트를 돌렸는데 TPS가 안 움직인다. 가상 스레드는 가벼우니 많이 만들면 많이 처리한다 — 지금 이렇게 알고 있을 텐데, 그 문장에는 처리량이 늘어나는 **이유**가 빠져 있다.

요청 처리 중에 현재 스레드를 찍어보면 빠진 게 뭔지 바로 보인다.

```java
log.info("{}", Thread.currentThread());
// VirtualThread[#84]/runnable@ForkJoinPool-1-worker-3
```

`@` 뒤가 이 가상 스레드를 지금 업고 있는 **캐리어 스레드**다. 기본적으로 CPU 코어 수만큼만 존재하는 진짜 OS 스레드고, 가상 스레드를 백만 개 만들어도 이 숫자는 그대로다. 가상 스레드는 자기 몫의 CPU를 새로 가져오지 않는다.

## 이득이 생기는 자리는 딱 한 곳이다

가상 스레드가 블로킹 호출을 만나면 JVM이 그 스레드를 캐리어에서 **떼어낸다**(언마운트). 캐리어는 즉시 다른 가상 스레드를 업고, 원래 스레드는 I/O가 끝났을 때 아무 캐리어에나 다시 올라탄다. 플랫폼 스레드였다면 응답을 기다리는 동안 OS 스레드 하나가 통째로 묶여 있었을 시간이다.

> 가상 스레드의 이득은 "많이 만들 수 있다"가 아니라 "블로킹될 때 캐리어를 놓아준다"에서만 나온다. 언마운트가 일어나지 않는 구간에서는 이득이 정확히 0이다.

## 기대가 빗나가는 경우가 전부 같은 이유다

이 한 문장을 잡으면 따로 외울 목록이 없어진다. 처음 보는 상황도 "여기서 언마운트가 일어나는가"만 물으면 답이 나온다.

- **CPU 바운드 작업** — 애초에 블로킹을 안 하니 놓아줄 일도 없다. 이미지 리사이징을 가상 스레드로 돌리면 이득이 0인 정도가 아니라, 스케줄링 오버헤드만큼 아주 살짝 손해다.
- **DB 커넥션 풀** — 언마운트는 정상적으로 일어나지만 소용이 없다. 풀 크기가 10이면 동시에 쿼리할 수 있는 건 여전히 10이다. 가상 스레드가 늘리는 건 처리량이 아니라 **풀 앞에서 기다리는 줄의 길이**다. 풀을 함께 키우지 않으면 지연 시간만 늘어난다.
- **가상 스레드를 풀에 넣기** — `newFixedThreadPool`에 가상 스레드를 담는 건 그 자체로 모순이다. 풀은 비싼 자원을 재사용하려고 존재하는데 가상 스레드는 싸다. `Executors.newVirtualThreadPerTaskExecutor()`로 매번 새로 만드는 게 정상이고, 동시성을 제한하고 싶다면 세마포어로 제한한다.
- **`ThreadLocal`** — 스레드 수만큼 복제되므로 요청당 MDC와 컨텍스트를 채우던 코드를 그대로 두고 스레드만 수백만 개로 늘리면, 늘어나는 건 처리량이 아니라 힙이다.

## Java 24에서 답이 바뀌었고, 진단 방법도 같이 바뀌었다

`synchronized` 블록 안에서 블로킹되면 가상 스레드가 캐리어에서 떨어지지 못한다 — 이게 pinning이다. 레거시 JDBC 드라이버 내부의 `synchronized`가 대표적인 원인이었다. 여기까지는 널리 알려져 있는데, **이미 옛날 이야기가 된 부분이 있다.**

| | Java 21~23 | Java 24 이상 (25 LTS 포함) |
| --- | --- | --- |
| `synchronized` + I/O | 캐리어에 pinning | JEP 491로 해소, 정상 언마운트 |
| 남아 있는 pinning | — | 네이티브 프레임(JNI), 클래스 초기화 |
| 진단 방법 | `-Djdk.tracePinnedThreads` | JFR `jdk.VirtualThreadPinned` |

주의할 건 마지막 줄이다. `-Djdk.tracePinnedThreads=short`는 Java 24부터 **에러도 경고도 없이 그냥 무시된다.** 옛 글을 보고 이 옵션을 걸어놓고 아무것도 안 찍히는 걸 "pinning이 없다"로 읽으면 정반대로 오판하게 된다. 지금 확인해야 할 곳은 JFR이다.

```bash
java -XX:StartFlightRecording=filename=app.jfr -jar app.jar
jfr print --events jdk.VirtualThreadPinned app.jfr
```

이 이벤트에는 pinning된 이유와 어느 캐리어에 묶였는지가 함께 찍힌다. Java 24 이상이라면 여기 잡히는 건 대부분 네이티브 프레임이고, 그 경우는 드라이버나 라이브러리를 바꾸는 것 말고는 손쓸 방법이 없다는 뜻이기도 하다.

## 인터뷰에서 이렇게 나온다

**"가상 스레드를 켜면 성능이 좋아지나요?"**

<details markdown="1">
<summary>답 확인</summary>

"블로킹 I/O를 기다리는 시간이 병목일 때만"이라고 조건부로 답한다. 이득은 캐리어 스레드를 놓아주는 데서만 나오므로, CPU 바운드 작업이나 커넥션 풀이 상한인 구조에서는 아무것도 나아지지 않는다. 오히려 커넥션 풀을 그대로 두고 스레드만 늘리면 대기 큐가 길어져 지연 시간이 나빠질 수 있다는 점까지 말한다.
</details>

**"pinning이 무엇이고 어떻게 확인합니까?"**

<details markdown="1">
<summary>답 확인</summary>

가상 스레드가 블로킹됐는데도 캐리어에서 언마운트되지 못하고 묶여 있는 상태다. Java 23까지는 `synchronized` 블록 안의 I/O가 주범이었고 JEP 491로 Java 24부터 해소됐다. 지금 남은 건 네이티브 프레임과 클래스 초기화 정도이며, 진단은 `jdk.tracePinnedThreads`가 아니라 JFR의 `jdk.VirtualThreadPinned` 이벤트로 한다고 답한다.
</details>

**"가상 스레드도 스레드 풀로 관리해야 하나요?"**

<details markdown="1">
<summary>답 확인</summary>

아니라고 답한다. 풀은 생성 비용이 비싼 자원을 재사용하기 위한 장치인데 가상 스레드는 만드는 비용이 싸다. 작업마다 새로 만드는 `newVirtualThreadPerTaskExecutor()`가 정상이고, 동시 호출 수를 제한해야 한다면 풀 크기가 아니라 세마포어 같은 명시적 제한으로 표현한다.
</details>

## 한 줄 요약

> 가상 스레드가 주는 것은 CPU가 아니라 **기다리는 동안 캐리어를 놓아주는 능력**이다. 그래서 "여기서 언마운트가 일어나는가"만 물으면 pinning도, CPU 바운드도, 커넥션 풀 병목도 전부 같은 질문의 답이 된다.
