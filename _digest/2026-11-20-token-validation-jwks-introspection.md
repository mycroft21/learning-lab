## 디코드했다고 검증한 게 아니다

자원 서버가 들어오는 요청의 `Authorization: Bearer <token>`을 처리하는 코드를 보자.

```java
Claims claims = Jwts.parserBuilder().build()
    .parseClaimsJwt(token.split("\\.")[0] + "." + token.split("\\.")[1] + ".")
    .getBody();
```

JWT를 쪼개 페이로드만 디코드하고 있다. 이 코드는 서명을 **확인하지 않는다.** 서명 검증 없이 페이로드를 읽는 건, 봉투를 뜯지 않고 "겉면에 적힌 내용을 믿는" 것과 같다. 공격자가 아무 내용이나 적어 보내도 이 코드는 그대로 믿는다.

## 믿는 방법은 구조적으로 둘뿐이다

자원 서버 입장에서 처음 보는 토큰 하나가 들어왔을 때, 그게 진짜 신뢰할 수 있는 발급자가 만든 것인지 확인하는 방법은 **딱 두 갈래**다.

> 토큰을 믿는 방법은 서명을 내가 직접 검증하거나, 발급자에게 지금 유효한지 물어보거나 둘 중 하나다. 전자는 네트워크 왕복 없이 빠르지만 발급 시점 이후의 폐기를 알 방법이 없고, 후자는 매번 정확하지만 요청마다 왕복 비용이 붙는다.

**서명을 직접 검증하는 방식(로컬 검증)** — 토큰이 JWT라면, 발급자의 공개키로 서명을 검증해 "이 발급자가 쓴 게 맞다"는 것과 "`exp`가 아직 안 지났다"는 것만 확인하면 된다. 네트워크 호출이 필요 없어 빠르다. 발급자의 공개키는 보통 이렇게 가져온다.

```bash
curl https://issuer.example.com/.well-known/openid-configuration | jq .jwks_uri
curl https://issuer.example.com/.well-known/jwks.json
```

JWT 헤더의 `kid`(key id)로 JWKS 목록에서 맞는 키를 골라 검증한다. 다만 이 방식은 **검증 시점에 발급자에게 묻지 않으므로**, 토큰이 발급된 뒤 중간에 폐기됐더라도 서명과 만료 시각이 멀쩡하면 그대로 통과한다.

**발급자에게 직접 물어보는 방식(토큰 내성 검사, introspection)** — RFC 7662가 정의하는 `/introspect` 엔드포인트에 토큰을 보내 "지금 이거 살아있나?"를 매번 묻는다.

```http
POST /introspect
token=eyJ...
```

```json
{"active": true, "scope": "orders:read", "exp": 1793000000}
```

발급자가 실시간으로 답하므로 **방금 폐기된 토큰도 바로 걸러낸다.** 대신 요청마다 왕복이 붙으므로 지연과 발급자 쪽 트래픽이 늘어난다.

## 발급 후 못 거두는 문제의 실질적 해법 중 하나

[JWT 무상태성 편](/learning-lab/digest/2026-11-02-jwt-stateless-tradeoff/)에서 "발급한 토큰은 서버가 기억하지 않으므로 취소할 수 없다"는 거래를 봤다. 그 글이 다룬 건 토큰의 수명 설계 전반이었고, 여기서 보는 건 **지금 들어온 토큰 하나를 어떤 메커니즘으로 신뢰할지**다. 둘은 같은 문제를 다른 각도에서 건드린다 — introspection은 사실 그 "못 거둔다"는 문제를 로컬 검증 대신 매번 발급자에게 물어보는 비용을 치르고 되돌리는 방법이다.

그래서 실무에서는 둘을 섞는다.

- **대부분의 내부 API 호출**에는 로컬 검증을 쓰고, 그 대신 액세스 토큰의 수명을 짧게 잡아 "폐기를 모른 채 통과하는 창"을 최소화한다.
- **결제 승인, 권한 회수 직후의 민감한 동작**처럼 즉시 반영이 중요한 경로에는 introspection을 추가로 건다. 모든 요청에 걸지 않고 **그 경로에만** 걸어 비용을 국소화한다.

## 로컬 검증에서 흔히 빠뜨리는 것

JWKS 응답은 캐시해두고 써야 하지만, 발급자가 키를 교체(rotate)하면 캐시가 낡은 키만 들고 있게 된다. `kid`가 캐시에 없는 키를 가리키면 **캐시를 한 번 강제로 갱신하고 다시 찾는** 절차가 있어야 키 교체 시점에 전체 검증이 끊기지 않는다. 그리고 토큰 헤더의 `alg` 값을 그대로 믿고 그 알고리즘으로 검증하면 안 된다는 점은 서명 알고리즘을 다룬 [JWT 편](/learning-lab/digest/2026-11-02-jwt-stateless-tradeoff/)의 경계 조건이 여기에도 그대로 적용된다 — 검증 쪽에서 기대하는 알고리즘을 고정해두고 대조해야 한다.

## 인터뷰에서 이렇게 나온다

**"JWT 서명 검증과 토큰 내성 검사(introspection)의 차이는?"**

<details markdown="1">
<summary>답 확인</summary>

서명 검증은 발급자의 공개키로 로컬에서 토큰을 확인하므로 빠르지만, 검증 시점에 발급자에게 묻지 않아 발급 후 폐기된 토큰을 걸러내지 못한다. Introspection은 매 요청마다 발급자에게 직접 지금 유효한지 물어보므로 폐기를 실시간으로 반영하지만 요청마다 네트워크 왕복 비용이 든다. 보통은 액세스 토큰 수명을 짧게 하고 로컬 검증을 기본으로 쓰되, 즉시 반영이 중요한 민감한 경로에만 introspection을 추가한다.

</details>

**"JWKS의 kid가 캐시에 없는 키를 가리키면 어떻게 해야 하나요?"**

<details markdown="1">
<summary>답 확인</summary>

발급자가 키를 교체했을 가능성이 높으므로, 캐시된 JWKS를 그대로 실패 처리하지 말고 한 번 강제로 다시 가져와 갱신한 뒤 다시 찾아야 한다. 이 절차가 없으면 키 교체 시점에 그 키로 서명된 모든 토큰의 검증이 끊긴다.

</details>

## 한 줄 요약

> 받은 토큰을 믿는 방법은 서명을 직접 검증하거나 발급자에게 물어보는 것뿐이고, 전자는 빠른 대신 폐기를 모르고 후자는 정확한 대신 매번 왕복하므로 대부분은 로컬 검증에 짧은 토큰 수명을 더하고 민감한 경로에만 내성 검사를 얹는 식으로 절충한다.
