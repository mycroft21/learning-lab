## 1페이지는 빠른데 5000페이지는 느리다

같은 쿼리로 같은 20건을 가져오는데 페이지 번호만 뒤로 갈수록 느려진다. 가져오는 양은 그대로인데 왜 느려지는지는 실제로 읽은 행 수를 보면 바로 드러난다.

```sql
EXPLAIN ANALYZE
SELECT id, title FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

출력의 `actual rows`가 20이 아니라 10만을 넘는다. 20건을 돌려주기 위해 10만 20건을 읽은 것이다.

## `OFFSET N`은 건너뛰는 게 아니라 읽고 버린다

이름 때문에 커서를 N번째로 순간이동시키는 것처럼 느껴지지만, DB에는 "N번째 행으로 바로 가는" 방법이 없다. 정렬된 순서대로 **처음부터 읽어 내려가면서 N개를 세어 버리고**, 그 다음부터 필요한 만큼 돌려준다. 그래서 비용은 가져올 행 수가 아니라 **건너뛸 행 수**에 비례한다.

- 1페이지는 20건만 읽으니 빠르고, 5000페이지는 10만 건을 읽고 버리니 느리다. 페이지 번호에 선형으로 비례해서 느려지는 게 정상 동작이다.
- 인덱스를 잘 타고 있어도 마찬가지다. 인덱스가 정렬 순서를 공짜로 주더라도 세면서 버리는 일 자체는 줄지 않는다.
- 전체 페이지 수를 구하는 `COUNT(*)`도 같은 범위를 훑으므로, 목록 화면 하나가 비싼 쿼리 둘을 부르게 된다.

## 건너뛰는 대신 어디서부터 읽을지를 알려준다

키셋(keyset) 페이지네이션은 "몇 개를 건너뛸까"를 "어디서부터 읽을까"로 바꾼다. 직전 페이지의 마지막 값을 조건으로 넘겨서, 인덱스에서 그 지점으로 바로 진입한다.

```sql
-- 직전 페이지 마지막 행의 created_at, id를 넘겨받는다
SELECT id, title FROM posts
 WHERE (created_at, id) < (:last_created_at, :last_id)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

읽는 행이 항상 20건 안팎이므로 **몇 번째 페이지든 속도가 같다.** 조건이 인덱스 선두 컬럼부터 이어지는 형태라 탐색 범위가 그 자리에서 좁혀지는 것이 핵심이다. 조건이 어떤 형태일 때 인덱스가 범위를 좁혀주는지는 [복합 인덱스 leftmost prefix 편](/learning-lab/digest/2026-09-30-composite-index-leftmost-prefix/)에서 다뤘다.

## 공짜는 아니다 — 포기해야 하는 것들

> 키셋 페이지네이션은 "다음 페이지"를 싸게 만드는 대신 "500페이지로 점프"를 포기하는 거래다.

- **임의 페이지 이동이 안 된다.** 직전 페이지의 마지막 값이 있어야 다음을 구할 수 있으므로 무한 스크롤이나 더보기 형태에는 맞지만, 페이지 번호를 찍어 이동하는 UI에는 그대로 못 쓴다.
- **정렬 키가 유일해야 한다.** `created_at`만으로 자르면 같은 시각의 행들이 경계에서 누락되거나 중복된다. 위 예시처럼 `id` 같은 유일한 값을 **동점 처리용으로 같이 묶어야** 안전하다.
- **정렬 기준을 바꾸면 커서도 같이 바뀐다.** 정렬 컬럼이 여러 개로 늘어나면 비교 조건과 인덱스도 함께 따라와야 한다.

페이지 번호 UI를 꼭 유지해야 한다면 중간 선택지가 있다. 정렬과 `OFFSET`은 인덱스만으로 끝내서 식별자만 먼저 뽑고, 본문은 그 식별자로 조인해서 가져오는 방식이다. 읽고 버리는 일은 남지만 버려질 행의 본문까지 읽는 비용은 사라진다. 인덱스만으로 끝내는 것과 테이블로 돌아가는 왕복 비용의 차이는 [커버링 인덱스 편](/learning-lab/digest/2026-10-02-covering-index-bookmark-lookup/)에서 다뤘다.

## 인터뷰에서 이렇게 나온다

**"OFFSET 기반 페이지네이션이 뒤 페이지로 갈수록 느려지는 이유는?"**

<details markdown="1">
<summary>답 확인</summary>

`OFFSET N`은 N번째 행으로 건너뛰는 게 아니라 정렬 순서대로 N개를 읽어서 버리는 동작이기 때문이다. 비용이 가져올 행 수가 아니라 건너뛸 행 수에 비례하므로 페이지 번호에 선형으로 느려지고, 인덱스를 제대로 타고 있어도 세면서 버리는 일 자체는 줄지 않는다.

</details>

**"키셋 페이지네이션으로 바꾸면 어떤 제약이 생기나요?"**

<details markdown="1">
<summary>답 확인</summary>

직전 페이지의 마지막 값을 기준으로 다음 구간을 읽으므로 임의 페이지로 점프하는 UI를 지원할 수 없고, 정렬 키가 유일하지 않으면 경계에서 행이 누락되거나 중복되므로 기본키 같은 유일한 값을 동점 처리용으로 함께 묶어야 한다.

</details>

## 한 줄 요약

> `OFFSET N`은 N개를 건너뛰는 게 아니라 읽고 버리는 동작이라 비용이 건너뛸 행 수에 비례하고, 키셋 페이지네이션이 페이지 번호와 무관하게 일정한 것도 임의 페이지 점프를 포기해야 하는 것도 "건너뛸 개수" 대신 "시작 지점"을 넘긴다는 차이에서 전부 나온다.
