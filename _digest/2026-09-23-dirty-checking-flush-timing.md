## 바뀐 필드만 업데이트된다고 알고 있다면

이름 하나만 바꿨을 때 어떤 SQL이 나가는지 로그로 확인해본 적이 있는지부터 보자. `spring.jpa.show-sql=true`나 `logging.level.org.hibernate.SQL=DEBUG`를 켜고 필드 하나만 수정하면 이런 게 찍힌다.

```sql
update member set age=?, email=?, name=?, status=? where id=?
```

바뀐 `name`만이 아니라 **매핑된 컬럼 전부**가 `SET` 절에 들어간다. Hibernate의 기본 동작이고, 미리 만들어둔 SQL을 재사용해 파싱 비용을 아끼려는 선택이다. 바뀐 컬럼만 넣고 싶으면 `@DynamicUpdate`를 붙여야 하는데, 그러면 매번 SQL을 새로 만들게 되므로 컬럼이 아주 많거나 인덱스·트리거가 걸린 컬럼을 건드리기 싫을 때만 쓰는 편이 낫다.

## 읽을 때 사본을 떠두고, flush 시점에 비교한다

변경 감지의 실체는 단순하다. 엔티티를 영속 상태로 읽어올 때 그 시점의 값을 **스냅샷**으로 따로 보관해두고, flush 시점에 현재 값과 스냅샷을 비교해서 달라진 게 있으면 `UPDATE`를 만든다. `save()` 같은 호출이 등장하지 않는 이유가 이것이다 — 저장 명령이 필요한 게 아니라, 비교 대상이 이미 있는 것이다.

```java
@Transactional
void rename(Long id, String name) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.setName(name);   // 여기서 끝. save 호출 없음
}                            // 커밋 직전 flush에서 UPDATE 생성
```

이 구조를 잡으면 따라오는 게 셋이다.

- **저장을 안 불러도 반영된다** — 위 코드가 동작하는 이유.
- **저장을 안 불렀는데 반영된다** — 조회만 하려던 메서드에서 엔티티 값을 건드리면 그대로 `UPDATE`가 나간다. 의도치 않은 갱신은 대개 여기서 난다.
- **비교 비용과 메모리를 쓴다** — 영속 상태 엔티티마다 원본 사본을 들고 있어야 한다.

## flush는 커밋이 아니다

flush는 **쌓아둔 변경을 SQL로 만들어 DB에 보내는 것**이고, 커밋은 그 트랜잭션을 확정하는 것이다. flush 후 롤백하면 보냈던 `UPDATE`도 같이 되돌아간다. 자동으로 flush가 일어나는 지점은 두 곳이다.

- **트랜잭션 커밋 직전** — 가장 흔한 경우.
- **JPQL/네이티브 쿼리 실행 직전** — 아직 DB에 안 보낸 변경이 있으면 쿼리 결과가 어긋나므로, 먼저 내보내고 쿼리를 실행한다. "분명 값을 바꿨는데 방금 실행한 JPQL 결과에는 반영돼 있다"가 이상하지 않은 이유다.

`em.flush()`를 직접 부르는 건 이 순서를 앞당기고 싶을 때(예: 생성된 키를 즉시 써야 할 때)뿐이고, 평소엔 부를 일이 없다.

## `readOnly = true`가 실제로 하는 일

조회 전용 메서드에 습관적으로 붙이는 이 옵션은 "실수로 쓰기를 막는 표시" 정도로 알려져 있지만, 실제 효과는 더 구체적이다. Spring 5.1부터 이 플래그가 Hibernate 세션까지 전파되어 `FlushMode`를 `MANUAL`로 낮추고 세션을 읽기 전용으로 만든다. 그러면 **엔티티를 읽을 때 스냅샷 자체를 보관하지 않는다.**

> 변경 감지를 건너뛰는 게 아니라 비교할 사본을 애초에 안 만드는 것이라, 조회량이 많은 경로에서는 CPU보다 메모리 쪽 이득이 먼저 체감된다.

조회 전용 경로에 붙이면 의도치 않은 `UPDATE`도 같이 막힌다. 위에서 본 "저장을 안 불렀는데 반영된다"는 사고에 대한 가장 싼 방어이기도 하다.

<summary>답 확인</summary>

영속 상태로 읽어올 때 그 시점의 값을 스냅샷으로 보관해두고, flush 시점에 현재 값과 비교해 달라진 게 있으면 `UPDATE`를 생성한다. 저장 명령이 필요한 구조가 아니라 비교 대상이 이미 존재하는 구조라서, 반대로 조회만 하려던 코드가 값을 건드리면 의도치 않은 `UPDATE`가 나가는 것도 같은 이유다.

</details>

**"변경 감지로 나가는 UPDATE는 바뀐 컬럼만 포함하나요?"**

<details markdown="1">
<summary>답 확인</summary>

기본값은 전체 컬럼이다. Hibernate가 엔티티별로 SQL을 미리 만들어 재사용하기 때문이며, 바뀐 컬럼만 넣으려면 `@DynamicUpdate`를 붙여 매번 SQL을 생성하게 해야 한다. 컬럼 수가 많거나 특정 컬럼 갱신에 부수 효과가 있을 때만 선택할 만하다.

</details>

## 한 줄 요약

> 변경 감지는 읽는 시점에 뜬 스냅샷과 flush 시점의 현재 값을 비교하는 것이고, `save()` 없이 반영되는 것도 조회 메서드가 몰래 `UPDATE`를 내는 것도 `readOnly = true`가 메모리를 아끼는 것도 전부 "사본을 떠두느냐"에서 갈린다.
