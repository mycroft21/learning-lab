## 결제 완료 통보는 PG사만 보낼 수 있는 게 아니다

PG사가 결제 완료를 알려주는 콜백 엔드포인트를 열어뒀다고 하자. 주소는 대개 짐작 가능한 형태이고, 본문 형식은 연동 문서에 공개돼 있다. 그 말은 **그 주소를 아는 누구나 똑같은 모양의 요청을 보낼 수 있다**는 뜻이다.

```java
@PostMapping("/webhooks/payment")
public void onPaid(@RequestBody PaymentEvent event) {
    orderService.markAsPaid(event.getOrderId());
}
```

이 코드는 "결제가 완료됐다"는 **주장**을 받아서 그대로 사실로 처리한다. 돈을 받지 않고 주문이 결제 완료로 바뀐다.

## 출처를 확인하지 않은 콜백은 사실이 아니라 요청이다

웹훅은 외부 시스템이 보내주는 알림이라 "믿을 만한 쪽에서 온 것"으로 느껴진다. 그런데 서버 입장에서 들어온 것은 **그냥 HTTP 요청 하나**다. 누가 보냈는지는 요청 안에 증거가 있어야만 알 수 있다.

그 증거가 서명이다. 보내는 쪽과 받는 쪽만 아는 비밀키로 본문에 대한 HMAC을 계산해 헤더에 실어 보내고, 받는 쪽이 같은 계산을 해서 일치하는지 본다. 일치한다면 **그 비밀키를 가진 쪽이 이 본문을 보냈다**는 것이 증명된다.

```java
String expected = hmacSha256(secret, rawBody);
if (!MessageDigest.isEqual(
        expected.getBytes(StandardCharsets.UTF_8),
        signatureHeader.getBytes(StandardCharsets.UTF_8))) {
    throw new BadRequestException();
}
```

> 서명 검증이 없는 웹훅 엔드포인트는 인증 없는 공개 API이고, 그 API가 하는 일이 "주문을 결제 완료로 바꾸는 것"이다.

## 검증을 넣고도 틀리는 세 자리

서명 검증은 코드를 넣었다고 끝나지 않는다. 틀리기 쉬운 지점이 정해져 있다.

- **파싱된 객체가 아니라 원문으로 검증해야 한다.** 보내는 쪽은 자기가 만든 **바이트 그대로**에 서명했다. 받아서 JSON으로 파싱한 뒤 다시 직렬화하면 공백·키 순서·숫자 표기가 달라져 서명이 안 맞는다. 그래서 원문 본문을 따로 확보해 검증해야 한다. 스프링이라면 `@RequestBody`로 받은 객체 말고 원문을 읽을 수 있게 필터나 래퍼를 두는 식이다.
- **문자열 비교에 `equals`를 쓰면 타이밍 정보가 샌다.** 일반적인 비교는 다른 문자가 나오는 즉시 멈추므로, 걸린 시간으로 "앞 몇 글자가 맞았는지"를 추정할 수 있다. 자바라면 `MessageDigest.isEqual`처럼 길이에 상관없이 일정 시간이 걸리는 비교를 쓴다.
- **재전송을 막지 않으면 서명이 통째로 재사용된다.** 공격자가 정상 요청 하나를 가로채면, 서명까지 그대로 포함된 그 요청을 몇 번이고 다시 보낼 수 있다. 그래서 서명 대상에 타임스탬프를 포함시키고, 받는 쪽에서 허용 시간(보통 몇 분)을 벗어난 요청은 거절한다.

## 서명과 멱등성은 다른 문제다

재전송 차단과 **멱등 처리**를 같은 것으로 묶으면 둘 다 허술해진다.

- **서명은 "누가 보냈나"에 답한다.** 위조를 막는다.
- **멱등성은 "몇 번 왔나"에 답한다.** 정당한 발신자가 네트워크 문제로 같은 알림을 두 번 보내는 일은 **정상 동작**이고, 그건 서명으로 막을 수 없다. 중복 전달이 왜 예외가 아니라 기본 전제인지, 멱등성 키를 어떻게 잡는지는 [멱등성 편](/learning-lab/digest/2026-10-10-at-least-once-idempotency/)에서 다뤘다.

그래서 서명 검증을 통과한 요청도 이벤트 식별자로 중복을 걸러 한 번만 반영해야 한다. 결제 완료 통보가 두 번 왔다고 잔액을 두 번 올리면 서명이 있으나 마나다.

IP 허용목록만으로 대신하려는 경우도 있는데, 발신 측 IP 대역은 공지 없이 바뀌고 클라우드 환경에서는 공유 대역이라 다른 테넌트도 같은 IP를 쓴다. 보조 수단으로는 쓸 만하지만 서명을 대체하지는 못한다.

## 인터뷰에서 이렇게 나온다

**"웹훅 엔드포인트를 안전하게 만들려면 무엇을 확인해야 하나요?"**

<details markdown="1">
<summary>답 확인</summary>

들어온 요청이 실제로 그 발신자가 보낸 것인지를 서명으로 검증해야 한다. 공유 비밀키로 본문에 대한 HMAC을 계산해 헤더 값과 비교하되, 파싱 후 재직렬화한 문자열이 아니라 원문 바이트로 계산해야 하고, 비교는 타이밍 공격을 피하는 상수 시간 비교를 쓴다. 서명 대상에 타임스탬프를 넣고 허용 시간을 벗어난 요청을 거절해 재전송도 막는다.

</details>

**"서명 검증을 했으면 중복 처리는 신경 안 써도 되나요?"**

<details markdown="1">
<summary>답 확인</summary>

서명은 누가 보냈는지에 답할 뿐 몇 번 왔는지에는 답하지 못한다. 정당한 발신자도 네트워크 문제로 같은 알림을 여러 번 보낼 수 있고 그건 정상 동작이므로, 이벤트 식별자로 중복을 걸러 한 번만 반영하는 멱등 처리가 별도로 필요하다.

</details>

## 한 줄 요약

> 출처를 확인하지 않은 콜백은 사실이 아니라 그냥 요청이므로 결제 완료 통보도 누구나 만들어 보낼 수 있고, 서명은 "누가 보냈나"만 답하므로 "몇 번 왔나"에 답하는 멱등 처리가 항상 함께 있어야 한다.
