## "로그는 남아야 하는데 결제는 롤백돼야 한다"에서 시작되는 사고

결제 실패해도 실패 로그는 DB에 남기고 싶다는 요구사항, 어디서나 한 번쯤 만난다. "그럼 로그 남기는 메서드만 별도 트랜잭션으로 묶으면 되겠네" 하고 `@Transactional(propagation = Propagation.REQUIRES_NEW)`를 붙였는데, 정작 결제가 실패한 케이스에서 로그도 같이 사라지는 걸 나중에 발견하는 팀이 많다. 원인은 대개 두 가지 중 하나다 — 로그 메서드가 같은 클래스 안에서 `this`로 호출돼서 프록시를 안 탔거나(self-invocation), 애초에 전파 옵션 7개의 차이를 대충 알고 있었거나.

전파(Propagation)는 "트랜잭션 메서드가 이미 트랜잭션 안에서 호출됐을 때 어떻게 행동할지"를 정하는 규칙이다. 아는 사람은 REQUIRED 하나로 실무 90%를 해결하지만, 인터뷰에서는 나머지 옵션이 왜 필요한지, 그리고 그 경계에서 뭐가 깨지는지를 묻는다.

## 7가지 옵션, 실전 감각으로 정리

| 옵션 | 기존 트랜잭션 있을 때 | 없을 때 |
|---|---|---|
| `REQUIRED` (기본값) | 그대로 참여 | 새로 시작 |
| `REQUIRES_NEW` | 기존 것을 잠깐 멈추고(suspend) 완전히 새 트랜잭션 시작 | 새로 시작 |
| `NESTED` | 세이브포인트를 찍고 진행, 실패 시 세이브포인트까지만 롤백 | 새로 시작(REQUIRED와 동일) |
| `SUPPORTS` | 참여 | 트랜잭션 없이 실행 |
| `NOT_SUPPORTED` | 기존 것을 멈추고 트랜잭션 없이 실행 | 트랜잭션 없이 실행 |
| `MANDATORY` | 참여 | `IllegalTransactionStateException` |
| `NEVER` | `IllegalTransactionStateException` | 트랜잭션 없이 실행 |

- 실무에서 진짜로 쓰는 건 `REQUIRED`, `REQUIRES_NEW`, 가끔 `SUPPORTS`/`NOT_SUPPORTED` 정도다.
- `MANDATORY`, `NEVER`는 "이 메서드는 반드시 트랜잭션 컨텍스트 안/밖에서만 호출돼야 한다"는 계약을 코드로 강제하고 싶을 때 쓰는데, 실제 사용 빈도는 낮아도 인터뷰에서는 정의를 꼭 물어본다.

## REQUIRES_NEW가 실제로 하는 일

`REQUIRES_NEW`는 "새 트랜잭션을 하나 더 시작한다"가 아니라 정확히는 **기존 트랜잭션을 물리적으로 보류(suspend)하고, 별도의 물리 커넥션으로 완전히 독립된 트랜잭션을 커밋한다**는 뜻이다. 이 말이 중요한 이유는 두 가지 실전 함정으로 이어지기 때문이다.

1. **커넥션을 두 개 물고 있는 순간이 생긴다.** 커넥션 풀 크기가 작은 환경에서 `REQUIRES_NEW`를 남발하면, 같은 스레드가 커넥션 두 개를 동시에 요구하면서 풀 고갈 → 데드락으로 번질 수 있다. 실제로 커넥션 풀을 1~2개로 좁게 잡아둔 배치 서버에서 이런 사고가 난다.
2. **바깥 트랜잭션이 롤백돼도 안쪽은 이미 커밋된 상태로 남는다.** 로그 저장처럼 의도한 경우엔 좋지만, 의도치 않게 일부 데이터만 커밋되는 부분 실패 상태를 만들 수 있다는 뜻이기도 하다.

## NESTED, 알고 있다고 착각하기 제일 쉬운 옵션

`NESTED`를 "REQUIRES_NEW의 가벼운 버전" 정도로 알고 있다가 실무에서 크게 헷갈리는 지점이 있다. **JPA를 쓰는 대부분의 환경에서 `NESTED`는 기대만큼 동작하지 않는다.**

- `NESTED`는 JDBC 세이브포인트(`Savepoint`) 메커니즘으로 구현된다. `JpaTransactionManager`는 이 기능을 지원은 하지만 `nestedTransactionAllowed` 플래그가 **기본값 `false`**라 명시적으로 켜야 한다.
- 켜더라도 세이브포인트는 **JDBC 커넥션 레벨**에서만 동작한다. JPA의 영속성 컨텍스트(1차 캐시에 올라온 엔티티, dirty checking 상태)는 세이브포인트로 롤백되지 않는다. 즉 SQL은 롤백돼도 자바 객체 상태는 그대로 남을 수 있다.
- 그래서 순수 JDBC 코드 조합이 아니라 JPA 엔티티를 다루는 코드에서는 `NESTED`보다 `REQUIRES_NEW`(완전히 분리된 트랜잭션 + 새 영속성 컨텍스트)가 훨씬 예측 가능하다.

> "부분 롤백이 필요하면 NESTED"라고 외운 지식은 순수 JDBC 기준이고, JPA 프로젝트에서는 거의 안 통한다는 게 인터뷰에서 진짜 변별력 있는 포인트다.

<details markdown="1">
<summary>self-invocation과 겹치면 전파 옵션 자체가 무의미해지는 이유</summary>

전파 규칙은 프록시가 어드바이스를 걸어야 작동한다. `serviceA.methodB()`를 외부에서 호출하면 프록시가 개입해서 `REQUIRES_NEW`든 뭐든 판단하지만, `methodB()`를 같은 클래스 안에서 `this.methodB()`로 부르면 프록시를 아예 거치지 않으므로 전파 옵션은 조용히 무시되고 그냥 같은 트랜잭션 안에서 실행된다. 로그 저장이 안 남았던 사례의 실제 원인이 대부분 이거다 — 옵션을 잘못 골라서가 아니라, 옵션이 적용될 기회 자체가 없었던 것.

</details>

## 한 줄 요약

> `REQUIRED`는 참여, `REQUIRES_NEW`는 물리적으로 분리된 새 트랜잭션, `NESTED`는 JPA 환경에서는 세이브포인트가 JDBC 레벨에만 걸려 기대와 다르게 동작한다 — 그리고 셋 다 self-invocation 앞에서는 무력하다.
