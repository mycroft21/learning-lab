## 기능 명세가 그대로 취약점이 되는 자리

"가맹점이 콜백 URL을 등록한다", "상품 이미지 주소를 입력하면 서버가 가져와 저장한다", "링크를 주면 미리보기를 만들어준다" — 전부 평범한 요구사항이고, 전부 **사용자가 지정한 주소로 서버가 요청을 보내는** 기능이다.

```java
@PostMapping("/merchants/callback")
public void register(@RequestBody String callbackUrl) {
    restTemplate.getForObject(callbackUrl, String.class);  // 연결 확인
}
```

여기에 `http://169.254.169.254/...` 같은 주소를 넣으면 어떻게 될까. 사용자의 브라우저에서는 닿지 않는 주소지만, **서버에서는 닿는다.**

## 공격자가 못 가는 곳에 서버를 대신 보낸다

SSRF의 본질은 데이터 유출이 아니라 **출발지 변경**이다. 같은 요청이라도 인터넷에서 출발하면 방화벽에 막히고, 애플리케이션 서버에서 출발하면 내부망 안에서 시작된다.

> 공격자는 서버에게 심부름을 시킨다. 자기 이름으로는 들어갈 수 없는 문을, **이미 안에 있는 서버의 이름으로** 두드리게 하는 것이다.

그래서 닿을 수 있는 대상이 인터넷 서비스가 아니라 **내부 자산**이 된다.

- 클러스터 안에서만 열려 있는 내부 API와 관리자 엔드포인트
- 인증 없이 떠 있는 내부 도구(모니터링 대시보드, 메시지 브로커 관리 화면)
- 클라우드 인스턴스 메타데이터 엔드포인트 — 여기서 임시 자격증명이 나오면 피해가 애플리케이션 밖으로 번진다
- `localhost`에 바인딩돼 "외부에서 접근 불가"라고 안심하고 있던 것들

응답을 돌려주지 않는 구조라도 끝이 아니다. 응답 시간이나 에러 메시지의 차이만으로도 내부에 무엇이 떠 있는지 훑을 수 있다.

## 차단 목록으로는 막히지 않는다

가장 먼저 떠오르는 대응이 "내부 주소를 거르자"인데, 거의 항상 뚫린다. 같은 목적지를 가리키는 표현이 너무 많기 때문이다.

- 10진수가 아닌 표기, 축약 표기, IPv6 표기, 끝에 점이 붙은 도메인
- 공격자가 소유한 도메인이 내부 IP를 가리키도록 DNS를 설정해둔 경우
- 검사는 통과시키고 **리다이렉트로 내부 주소에 보내는** 경우
- 검사 시점과 실제 연결 시점 사이에 DNS 응답을 바꾸는 경우

마지막 두 가지가 특히 중요하다. **검사한 주소와 실제로 연결되는 주소가 다를 수 있다**는 뜻이라, 문자열만 보는 검증은 구조적으로 불완전하다.

## 허용 목록과 네트워크 차원의 차단

문자열 검사 대신 두 겹으로 막는 쪽이 현실적이다.

- **허용 목록으로 좁힌다.** 가맹점 콜백이라면 등록 가능한 스킴을 `https`로 고정하고, 호스트는 등록·심사된 도메인만 허용한다. 이미지라면 사내 스토리지나 지정 CDN만 허용한다. "무엇을 막을까"가 아니라 "무엇만 허용할까"로 질문을 뒤집는 것이다.
- **리다이렉트를 따라가지 않는다.** 꼭 필요하다면 매 홉마다 목적지를 다시 검증해야 한다. 기본값으로 따라가는 HTTP 클라이언트가 많으므로 명시적으로 꺼야 한다.
- **나가는 쪽을 네트워크에서 막는다.** 외부 호출이 필요한 컴포넌트를 내부망에 접근할 수 없는 곳에 두거나, 이그레스 프록시를 거치게 해 허용된 목적지만 나가게 한다. 애플리케이션 코드의 실수를 한 겹 아래에서 받아주는 안전망이다. 쿠버네티스 클러스터 안에서 서비스끼리 어떻게 서로 닿는지는 [cgroup 편](/learning-lab/digest/2026-10-20-cgroup-limits-vs-visibility/)과 [Service 편](/learning-lab/digest/2026-10-27-service-kube-proxy-load-balancing/)에서 다뤘다 — 그 내부 접근성이 여기서는 그대로 공격면이 된다.
- **메타데이터 접근을 강제로 잠근다.** 클라우드마다 세션 토큰을 요구하는 방식 등으로 단순 요청을 막는 설정이 있지만, 계정·인스턴스에 따라 기본값이 다르므로 **켜져 있다고 가정하지 말고 실제 설정을 확인해야 한다.**

## 인터뷰에서 이렇게 나온다

**"SSRF가 위험한 이유를 설명해보세요."**

<details markdown="1">
<summary>답 확인</summary>

공격자가 지정한 주소로 서버가 대신 요청을 보내므로 요청의 출발지가 인터넷이 아니라 서버 자신이 된다. 방화벽 안쪽에서 시작되기 때문에 외부에서는 닿을 수 없는 내부 API, 인증 없이 떠 있는 내부 도구, 클라우드 인스턴스 메타데이터 같은 자산에 접근할 수 있고, 메타데이터에서 임시 자격증명이 노출되면 피해가 애플리케이션 밖으로 번진다.

</details>

**"내부 IP를 차단 목록으로 거르면 되지 않나요?"**

<details markdown="1">
<summary>답 확인</summary>

같은 목적지를 가리키는 표기가 너무 많고, 무엇보다 검사한 주소와 실제 연결되는 주소가 달라질 수 있다. 공격자 도메인이 내부 IP를 가리키게 하거나 검사를 통과한 뒤 리다이렉트로 내부로 보낼 수 있기 때문이다. 허용 목록으로 스킴과 호스트를 좁히고 리다이렉트를 따라가지 않으며, 네트워크 차원에서 나가는 경로를 제한하는 쪽이 맞다.

</details>

## 한 줄 요약

> SSRF는 서버가 사용자 입력으로 요청을 보내는 순간 그 요청의 출발지가 방화벽 안쪽으로 바뀌는 문제이고, 검사한 주소와 실제 연결 주소가 달라질 수 있으므로 차단 목록이 아니라 허용 목록과 네트워크 차원의 제한으로 막아야 한다.
