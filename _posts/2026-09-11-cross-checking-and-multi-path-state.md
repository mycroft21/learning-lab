사내 배포 승인 문서를 자동화하는 작업을 하면서, 같은 하루 안에 "문서에 적힌 것과 실제가 다른" 상황을 세 번 연속으로 만났다. 처음엔 우연이라고 생각했는데, 세 번째쯤 되니 패턴이 보였다. 몇 주 뒤 다른 도메인(차지백 케이스)을 정리하다가 또 같은 함정에 두 번 걸렸다. 이번엔 문서가 아니라 "이 값이 언제 세팅되나"라는 질문 자체가 반쪽이었다.

## 공식 규정 vs 실제 제출 관행

배포 전 작성하는 보안성 검토 문서에 정적 분석 점검 결과를 넣는 항목이 있었다. 사내 위키엔 "로컬에서 돌린 결과는 증적으로 인정하지 않는다, 실제 CI 스캔 스크린샷이 필수"라고 명확히 적혀 있었다.

그런데 동료 두 명이 최근 실제로 제출한 문서를 열어보니, 둘 다 스캔 스크린샷 없이 그냥 "해당없음"으로 표시하고 넘어갔다. 규정과 관행이 대놓고 어긋나 있었던 것. 공식 문서만 읽고 판단했으면 실제 조직 문화와 안 맞는 산출물을 만들 뻔했다.

## MR 설명 vs 실제 diff

release 브랜치를 main으로 승격하는 MR을 조사할 때, MR 설명엔 티켓 하나만 적혀 있었다. 그런데 실제로 그 MR에 포함된 커밋을 base부터 head까지 전부 diff해보니, 설명에 없는 기능이 9개나 더 섞여 있었다. release 브랜치는 여러 작은 feature 브랜치가 누적되는 곳이라, 마지막에 main으로 승격할 때 "대표 티켓 하나"만 제목에 남고 나머지는 설명에서 빠지는 일이 실제로 벌어진다.

## 레거시 컨벤션 문서 vs 실제 소스

레거시 프로젝트의 컨벤션 문서엔 특정 URL 패턴을 설정 파일에서 매핑한다고 적혀 있었다. 그런데 실제로 해당 서블릿 소스를 열어보니, 요청을 같은 이름의 화면 파일로 단순 치환해서 넘기는 방식이었다 — 별도 매핑을 추가할 필요가 전혀 없는 구조였다. 예전엔 진짜 매핑 방식이었다가 나중에 리팩터링됐는데 문서만 안 갱신된 케이스로 보인다.

## 운영 분석 문서 vs 코드

정산 도메인의 한 흐름표가 차감 상태를 특정 코드로 적어놓았는데, 실제 코드와 공통 코드 테이블은 다른 코드였다. 규정 문서나 컨벤션 문서와 다르지 않았다. 운영·분석 목적으로 작성된 문서라도 작성 시점 이후 코드가 바뀌면 그대로 틀린 채 남는다.

## "언제 세팅되나"가 반쪽 질문이었던 두 번

몇 주 뒤, 성격이 다른 도메인 정리에서 또 같은 함정에 걸렸다. 이번엔 대조 대상이 문서가 아니라 "값을 만드는 경로가 몇 개인가"였다.

케이스 상태와 정산행 성격 값이 서로 다른 테이블에 사는 도메인이었다. 채팅으로 "그 값은 정산 확정 때 들어간다"고 답했는데, 절반만 맞았다. 화면에서 만든 행은 생성 시점에 바로 값이 들어가고, 취소 경로로 생긴 행만 확정 시점에 나중에 붙었다. 경로가 두 개인데 하나만 보고 답한 것.

같은 도메인의 자동 판정 로직도 마찬가지였다. "같은 묶음에 선행 행이 있으면 무조건 이 상태로 분류한다"는 조건이었는데, 성격이 전혀 다른 실물 취소 건에도 똑같이 붙어서 오분류가 났다. 담당자 의견은 "이 취소 경로로 생긴 거라면 애초에 그 값이 비어 있어야 한다"는 것 — 판정 조건이 "지금 상태가 뭔가"만 보고 "그 상태를 만든 경로가 뭔가"를 안 본 게 문제였다.

이 로직은 다른 저장소에도 복제돼 있었는데, 한쪽엔 몇 년 전 날짜가 적힌 패치 주석("특정 상태는 유지, 예외 처리")이 있고 다른 쪽엔 그 예외가 아예 없었다. 실제 거래를 재현해서 동작 차이를 확인하는 대신, 같은 블록을 나란히 놓고 주석에 남은 패치 날짜부터 비교하니 바로 드러났다. 복제된 로직에서 동작이 다르다는 의심이 들면, 재현 환경을 만들기 전에 먼저 날짜부터 대조하는 게 더 빠르다.

## 결과적으로 중요한 건 실제 구현이었다

두 인사이트를 나란히 놓고 보면, 결국 같은 결론으로 수렴한다. 규정·설명·과거 답변·기존 로직 — 전부 "누군가 특정 시점에 적어놓은 것"이고, 실제로 중요한 건 지금 코드가 뭘 하는지다. 문서는 코드가 바뀌는 순간 자동으로 따라 바뀌지 않고, 상태값도 그걸 만드는 경로가 여러 개면 하나만 보고 답하면 틀린다. 대조 대상은 매번 달랐다: 실제 제출 사례, 실제 커밋 diff, 실제 소스 코드, 실제 데이터가 지나간 경로. 다음에 "이게 언제/왜 이런가"라는 질문을 받으면, 답부터 하지 않고 그 값·그 판단을 만드는 경로가 몇 개인지부터 센다.
