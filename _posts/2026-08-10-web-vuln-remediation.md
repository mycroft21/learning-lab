> 한 줄 요약: 웹 취약점 진단에서 가장 많이 터지는 건 "인가(authorization)를 클라이언트/화면에 의존한 것"이다.
> 화면 마스킹·메뉴 숨김·클라이언트 검증은 전부 통제가 아니며, 검증은 반드시 서버가·리소스 소유권 기준으로·
> 모든 진입점에서 해야 한다.

## 배운 맥락

외부 보안업체의 웹·API 취약점 진단(모의해킹) 결과를 여러 회차에 걸쳐 받아 조치하며 정리한 것.
항목별로 "공격이 실제로 어떻게 성립하는가 → 왜 기존 코드가 뚫렸나 → 올바른 대책"을 익혔다.
점검 유형은 국내 웹 취약점 점검 체계 기준이지만, 내용은 **OWASP Top 10과 그대로 대응**된다.
회차가 반복되면서 같은 유형이 계속 재발한다는 것 자체가 핵심 통찰이었다.

---

## 1부. 취약점 유형별 원리와 대책

### 1. 부적절한 이용자 인가 (Broken Access Control) — 제일 많이 터짐

OWASP Top 10 1위. 진단에서 압도적으로 빈번한 계열. 세부 패턴:

**(a) IDOR (Insecure Direct Object Reference)**

- 증상: `/api/v1/files/121`처럼 리소스 ID를 URL에 그대로 노출 → ID를 121→122로 바꾸면
  **타인의 리소스가 그대로 조회됨.** 요청 내 소속 식별자를 변조하면 다른 조직의 데이터까지 조회.
- 근본 원인: 인증(로그인했는가)만 보고 **인가(이 리소스가 이 사람 것인가)를 서버에서 안 봄.**
- 대책: 모든 리소스 접근에 **소유권 검증**을 서버측에서. "로그인 사용자 == 리소스 소유자/권한자"를
  DB 기준으로 확인. 접근용 임시 URL(presigned)은 유효기간 최소화 + 소유권 재검증.

**(b) 기능 단위 권한 미검증 (메뉴 숨김에만 의존)**

- 증상: 화면 메뉴엔 안 보이지만 **등록 페이지 URL로 직접 접근하면 페이지가 뜨고 기능이 동작.**
- 근본 원인: **"메뉴 숨김 = 권한 통제"라는 착각.** 프론트에서 안 보여줄 뿐 서버는 아무나 받아줌.
- 대책: 메뉴 노출 여부와 무관하게 **모든 기능(조회·등록·수정·삭제)에 서버측 RBAC** 적용. 권한 없으면 403.

**(c) 인증 절차 우회 (2차 인증 무력화)**

- 증상: 1차 인증 후 OTP 요구 상황에서, **응답의 이동 로직을 "OTP 신규 등록"으로 바꾸면**
  서버가 기존 OTP 소유 여부를 재검증 안 하고 새 OTP 등록을 허용 → 공격자 단말에 OTP 등록해 2차 인증 우회.
- 근본 원인: 다음 단계 결정을 **클라이언트가 보낸 값/응답 스크립트**에 맡김.
- 대책: 다음 단계는 **서버가 계정 상태·세션 기준으로 결정.** 기존 OTP 재등록은 기존 OTP 확인/추가 본인확인/
  승인된 복구절차를 거친 경우만. 사용자·용도·만료에 묶인 1회성 토큰 사용.

**(d) 엔드포인트 유추**

- 증상: 응답 코드(200/403/404) 차이로 유효한 경로·메서드·Content-Type 조합을 식별.
- 대책: 오류 응답 **일반화**(존재/비존재를 응답으로 구분 못 하게), 프론트 JS·JWT에 API 정보 미포함.

**(e) 민감 페이지 재인증 (불충분한 이용자 인증)**

- 증상: 인증 필요한 경로/민감정보 페이지에 미인증·우회 접근 가능. 클라이언트 스크립트 삭제로 우회.
- 대책: 민감정보(개인정보 변경 등) 페이지는 **재인증**(다른 factor/channel). 로그인+권한 체크를 **공통 모듈로**
  강제(다중 페이지 프로세스에서 체크 누락 방지). 인증/필터링은 반드시 Server Side.

### 2. 시스템 운영정보 노출 — JWT에 민감정보 넣지 마라

- 증상 1: **JWT를 디코딩하면 API Key가 평문으로.** JWT는 서명(무결성)만 보장, **내용은 누구나 Base64 디코딩 가능**(암호화 아님).
- 증상 2: 오류 시 SQL 문법·스택트레이스·내부 경로·테스트 페이지 노출.
- 대책:
  - JWT claim은 **인증·인가 최소 정보만**(주체 식별자, 세션 ID, 만료 등). API Key·내부 식별자·설정값 금지.
  - 이미 노출된 키는 **즉시 폐기 후 재발급**(코드 고쳐도 유출된 키는 살아있음).
  - 에러는 사용자에게 일반 메시지, 상세는 서버 로그로만. 별도 에러 페이지 지정(400/401/403/404/500).

> 핵심 오해 교정: **JWT는 암호화가 아니라 서명이다.** "토큰에 넣었으니 안전"은 틀림. 민감정보는 별도 암호화(JWE)가 필요하고, 대개는 안 넣는 게 답.

### 3. 세션정보 재사용 — 로그아웃해도 토큰이 살아있다

- 증상: 로그아웃 후에도 기존 Access/Refresh Token으로 API 호출이 계속 됨. 또는 탈취한 세션/토큰을 다른 단말에서 재사용.
- 근본 원인: JWT는 기본적으로 **stateless** → 발급하면 만료 전까지 유효. 로그아웃은 클라이언트가 토큰을 버릴 뿐, 서버는 여전히 받아줌.
- 대책: 서버측 세션/토큰 상태 관리.
  - 로그인 시 session_id 발급 → 서버 저장소(Redis 등)에 등록. API 호출마다 세션 존재 여부 검증(인증 Aspect/필터).
  - 로그아웃 시 세션 삭제 → 이후 그 토큰 거부(토큰 블랙리스트/세션 저장소 방식).
  - 다중세션 vs 단일세션 정책 분리. 필요 시 IP/User-Agent 등 단말정보 바인딩(단, 모바일 IP 변동 오탐 주의).
- 함정: 하위호환용 "session claim이 null이면 통과"는 **구형 토큰의 무한 우회 통로** → 구형 토큰 만료 후 반드시 차단으로 전환.

> 트레이드오프: JWT의 stateless 확장성을 세션 검증으로 일부 포기하는 것. 즉시 무효화는 결국 서버 상태가 필요하다.

### 4. 악성파일 업로드 — 클라이언트 검증은 검증이 아니다

- 증상: 화면에선 확장자 제한하지만, 업로드 요청의 multipart filename을 실행 가능 확장자로 **변조**하면 서버가 저장 → 웹쉘 가능.
- 근본 원인: **확장자 검증을 클라이언트(JS)에만 의존.** 프록시로 요청 조작하면 통과.
- 대책(다층): 서버측 **allowlist**(확장자 + MIME + 파일 시그니처), 실행 가능/이중/대소문자 변형 확장자 차단,
  파일명 난수화 + **웹 루트 외부 저장** + 저장 경로 **스크립트 실행 권한 제거**, 크기·개수 제한, 악성코드 검사, 업로드 로깅.

### 5. XSS — 저장형과 반사형

- 저장형(Stored): 본문에 스크립트를 넣으면 저장됐다가 **조회하는 관리자 브라우저에서 실행** → 세션 탈취/권한 기능 요청.
- 반사형(Reflected): 파라미터 검증 미흡으로 입력이 응답에 그대로 반사돼 실행.
- 대책: **출력 시 컨텍스트 기반 인코딩**(HTML/attr/JS/URL 위치별)이 기본. 리치 텍스트 허용 시 **서버측 HTML Sanitizer + 허용목록**
  (script/iframe/object/svg/이벤트핸들러/`javascript:` 스킴 제거). **저장 전 + 출력 시 이중 검증.** CSP를 심층 방어로. 기존 저장분도 점검.

### 6. 입력값 조작 계열 — Path Traversal & Open Redirect

- **파일 다운로드(Path Traversal)**: `../` 등 경로 조작으로 저장 디렉터리 밖 시스템 파일 다운로드.
  → 경로 조작 문자 필터링(WAF+앱), **파일명을 DB에 저장해두고 요청값과 대조**, 특정 디렉터리 한정, 웹 루트 상위 접근 금지.
- **리다이렉트 피싱(Open Redirect)**: 리다이렉트 파라미터에 임의 외부 URL을 넣어 악성 사이트 유도.
  → 목적지 계산 파라미터 금지. **화이트리스트 방식**(허용 URL 배열을 서버에 두고 파라미터는 인덱스 숫자로만). 인증된 사용자만.

### 7. 인증정보 / 계정 보호

- **약한 비밀번호**: 모든 진입점(회원가입·정보변경·비번변경)에 **동일 비번 정책** 서버측 검증. 정책 예: 2종 10자+ / 3종 8자+,
  개인정보·아이디 유사 금지, 주기 변경, 재사용 금지. 실패 메시지는 일반화(ID 존재 여부 노출 방지).
- **초기화 비밀번호(Forgot Password)**: OWASP Cheat Sheet 기준 — Hard Data 수집 → 보안질문(추측 제한) →
  **부채널(SMS 등, 이메일과 무관한 채널)로 1회성 코드**(짧은 유효) → 기존 세션 내 변경. **초기화 성공 시 다른 모든 세션 무효화.**
- **인증 오류 횟수 제한**: 로그인 실패 최대 5회 권고 후 계정 잠금(무작위 대입 방어).

### 8. 전송/설정 보안

- **취약 TLS/암호군**: TLS 1.0/1.1 비활성, **TLS 1.2+만 허용**, 약한 cipher(RC4/DES/3DES/NULL) 제거, AEAD(AES-GCM) 계열 사용. 종단(웹서버/LB)에서 설정.
- **세션 타임아웃**: 적절한 종료 시간(권고 10분). 미설정/과도 설정 금지.
- **불필요 웹 메서드**: 운영상 필요한 메서드만 허용(보통 GET/POST). PUT/PATCH/DELETE/TRACE 차단.
- **브라우저 내 중요정보 노출**: 화면은 마스킹인데 **응답 HTML의 input/hidden/JS 변수에 평문**이면 무의미.
  → **서버가 마스킹된 값만 응답.** 전체값 필요 시 별도 권한+재인증+명시적 조회 + 조회 이력 로깅. 저장 암호화(예: AES-256/GCM) 병행.

## 2부. 관통 교훈

1. **"클라이언트/화면은 통제가 아니다"가 전부를 관통한다.**
   메뉴 숨김·화면 마스킹·JS 확장자/입력 검증·응답 스크립트 분기 — 전부 프록시/DevTools로 우회됨.
   **모든 검증은 서버에서.** 이 한 문장이 진단 항목의 절반 이상을 설명한다.

2. **인증(누구냐) ≠ 인가(권한 있냐).** 로그인만 확인하고 "이 리소스가 이 사람 것인가"를 안 보면 IDOR로 다 뚫린다. 인가는 리소스 소유권 기준.

3. **JWT는 암호화가 아니라 서명.** payload는 공개된다고 가정. 민감정보 금지, 즉시 무효화는 서버 상태 필요.

4. **노출된 비밀은 코드 수정으로 안 사라진다.** 유출된 키/시크릿은 코드 고쳐도 살아있으니 반드시 폐기·재발급.

5. **하위호환용 예외가 우회 통로가 된다.** "null이면 통과" 같은 완충장치는 구형 데이터 소멸 후 반드시 닫아야 완결.

6. **취약점 유형은 회차마다 반복된다 (= 커버리지 문제).** 한 시스템 한 경로만 고치면 다른 진입점/유사 API가 남아 재점검에서 다시 열린다.
   같은 유형을 **모든 진입점에 일괄** 적용해야 끝난다. 신규 개발 시 코드 리뷰 항목/공통 모듈로 내재화하지 않으면 매번 되풀이.

7. **점검 체계 ≈ OWASP Top 10.** 부적절 인가=Broken Access Control, XSS=Injection, 약한 비번/세션=Identification & Auth Failures,
   TLS/암호군=Cryptographic Failures, 정보노출=Security Misconfiguration. 용어만 다를 뿐 본질은 같다.

8. **인프라 설정 항목(TLS/메서드/에러페이지/세션타임아웃)은 코드가 아니라 웹서버·WAS 설정에서 끝난다.** 개발자가 코드만 보다 놓치기 쉬운 계열.

## 정리

- 웹 취약점 조치의 8할은 **"서버측 · 소유권 기준 · 모든 진입점"** 인가 검증으로 수렴한다.
- 유형 지도: 인가(IDOR/기능권한/인증우회/재인증) · 정보노출(JWT/에러) · 세션(무효화/재사용) · 파일업로드 · XSS ·
  입력조작(Path Traversal/Open Redirect) · 인증정보(약한 비번/초기화/잠금) · 전송·설정(TLS/메서드/타임아웃/응답 내 평문).
- 예방책: 신규 개발 때 "입력은 서버에서 검증, 민감정보는 토큰/응답/HTML에 안 싣기, 권한은 기능마다 서버 체크"를 기본값으로 두고,
  이 유형 지도를 자가 체크리스트로 쓰면 다음 진단의 재발 항목을 크게 줄일 수 있다.
