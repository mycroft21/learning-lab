# 정보보호 인증(ISMS 계열) 대응 실무 — 개인정보·계정이력·웹취약점을 처리하며 배운 것

> 한 줄 요약: 정보보호 인증 대응은 "어려운 기술"이 아니라 "같은 통제항목을
> 모든 시스템에 빠짐없이·일관되게 반영하는" 반복·누락 관리 싸움이다. 난도보다 커버리지와 문서-구현 정합성이 핵심.

## 배운 맥락

여러 웹 시스템(백오피스 여러 개 + API + 레거시)을 대상으로
정보보호 인증(개인정보보호 + 웹 취약점 점검) 결함을 조치하며 겪은 것.
막상 손대보니 개별 항목은 대부분 표준적이고, 진짜 부담은 "같은 요구사항 × 시스템 수" 였다.

---

## 통제항목은 크게 3덩어리

### 1. 개인정보 보호 (가장 반복됨)

- **마스킹 정책**: 화면·다운로드에 노출되는 개인정보(이름/연락처/계좌 등)를 부분 마스킹.
  함정 — 마스킹 규칙이 화면마다 제각각이면 결함. 공통 유틸/정책으로 통일해야 감사에서 안 걸린다.
- **개인정보 접속 로그**: 누가·언제·어떤 개인정보를·왜 조회했는지 로그 적재.
  개인정보보호법상 접속기록 보관 의무(통상 최소 1년, 유형에 따라 더 길게)와 연결됨.
  단순 조회뿐 아니라 다운로드/출력까지 남겨야 함.
- **접속기록 관리 메뉴**: 쌓은 로그를 관리자가 조회·점검할 수 있는 화면.
  로그만 쌓고 볼 수단이 없으면 "관리하지 않음"으로 결함 처리됨.
- **다운로드 시 사유 등록**: 개인정보 포함 엑셀/파일 다운로드 시 사유 입력 강제 + 그 사유를 로그화.
  대량 유출 방지 통제. UX는 번거롭지만 감사에서 요구되는 전형적 항목.
- **저장 시 암호화**: 계좌번호 등 민감정보 DB 컬럼 암호화.
  이미 평문으로 쌓인 기존 데이터 마이그레이션이 진짜 일. 신규만 암호화하면 과거 데이터가 결함으로 남음.

### 2. 계정/인증 이력 (시스템마다 동일 세트)

- **비밀번호 정책**: 최소 길이(예: 12자 이상), 주기적 변경(예: 90일), 복잡도.
  → 같은 정책을 모든 시스템에 개별 반영. "한 곳만 바꾸면 되는 게 아니라 전부".
- **중복 로그인 처리**: 동일 계정 동시 세션 차단/후입자 우선 등. 세션 관리와 직접 연결.
- **OTP / 2차 인증**: 관리자·민감 기능 접근에 추가 인증.
- **사용자 인증 조치**: 인증 강도·실패 잠금·세션 타임아웃 등 종합.

### 3. 웹 취약점 점검항목 (표준 웹 취약점 체크리스트 계열)

표준 웹 취약점 체크리스트에 대응. 대표 항목:

- **무제한 요청 차단** (rate limiting) — 자동화/무차별 대입 방어
- **취약한 HTTPS 프로토콜 제한** — 구형 TLS(1.0/1.1)·약한 cipher 비활성
- **부적절한 이용자 인가** — 권한 없는 사용자의 기능/데이터 접근(수평·수직 권한상승) 차단
- **세션정보 재사용 제한** — 로그아웃/만료 후 세션 무효화, 세션 고정 방어
- **시스템 운영정보 노출 방지** — 에러 스택트레이스·서버 헤더·경로 노출 제거
- **XSS** — 입력 검증 + 출력 인코딩
- **악성파일 업로드** — 확장자/MIME/시그니처 검증, 실행권한 분리
- **브라우저 내 중요정보 노출 방지** — 자동완성 off, 캐시 제어, URL 파라미터에 민감정보 금지

> 이 계열의 유형별 상세 원리·대책은 별도 노트("웹 취약점 진단(모의해킹) 조치 실무")에 정리했다.

## 겪어서 안 것 (진짜 교훈)

1. **난도보다 "누락 관리"가 본질.**
   개별 항목은 대부분 표준적이다. 문제는 같은 요구사항이 시스템 수만큼 곱해진다는 것.
   비밀번호 최소 길이 하나를 여러 시스템에 각각 반영하는 식. 하나라도 빠지면 그게 결함.
   → 통제항목 × 시스템 매트릭스를 만들어 커버리지로 관리하는 게 정석. 작업이 잘게 쪼개지는 이유도 이것.

2. **"막상 닥쳐야 손대는" 항목이 대부분 = 평소 설계에 안 녹아있음.**
   접속로그·마스킹·다운로드 사유는 기능 만들 때 같이 넣었으면 결함이 안 됐을 것.
   사후에 전 시스템에 소급 적용하려니 부담이 커진다. → 신규 개발 시 개인정보 취급 지점에
   로그/마스킹을 기본으로 끼워넣으면 나중 인증 부담이 급감.

3. **기존 데이터가 진짜 일.**
   암호화·마스킹은 "앞으로 들어올 데이터"는 쉽다. 이미 평문으로 쌓인 과거 데이터 마이그레이션이
   위험하고 오래 걸린다(무중단, 복호화 키 관리, 검증). 일정 산정 시 이걸 빼먹으면 안 됨.

4. **로그는 "쌓기 + 볼 수단 + 보관기간"이 한 세트.**
   로그만 적재하고 조회 화면이나 보관정책이 없으면 여전히 결함. 세 개가 같이 가야 통제로 인정.

5. **문서(정책)와 구현의 정합성.**
   심사는 "정책 문서대로 시스템이 실제 동작하는가"를 본다. 정책은 90일인데 시스템은 무제한이면 결함.
   반대로 시스템은 됐는데 문서에 없어도 지적. 개발자 입장에선 이 갭을 메우는 게 반복 작업.

6. **재점검 시 다시 열리는(REOPEN) 일이 잦다.**
   "조치했다"고 닫아도 심사/재점검에서 커버리지 구멍(특정 시스템 누락, 예외 케이스)이 나와 다시 열린다.
   → 처음 조치할 때 "이 항목이 적용돼야 할 모든 경로"를 넓게 잡는 게 재작업을 줄인다.

---

## 정리

- 정보보호 인증 대응 = 기술 난도 싸움이 아니라 **커버리지(모든 시스템·경로) + 문서-구현 정합성 + 기존데이터 소급** 싸움.
- 3덩어리로 기억: **개인정보(마스킹·접속로그·다운로드사유·암호화) / 계정이력(비번정책·중복로그인·OTP) / 웹취약점(점검 체크리스트)**.
- 예방책: 신규 개발 때부터 개인정보 취급 지점에 로그·마스킹을 기본 탑재하고, 정책을 공통 유틸로 통일해
  "시스템마다 제각각"을 원천 차단. 그게 다음 인증 때 결함·재작업을 줄이는 유일한 길.
