> 한 줄 요약: 겉보기 문법이 비슷한 두 하네스라도, 판단 로직은 재사용 가능해도 "이벤트에 훅을 거는 틀" 자체는 새로 짜야 할 수 있다. 그리고 "치환될 것이다"라고 믿지 말고 자식 프로세스가 실제로 받는 값을 찍어서 확인해야 한다.

## 배운 맥락

한 코딩 에이전트 하네스에서 다른 하네스로 스킬·서브에이전트·훅·MCP 설정을 옮기는 작업을
했다. 겉보기엔 둘 다 "스킬", "훅", "MCP 서버" 같은 비슷한 개념을 쓰지만, 실제 이식해보니
호환성이 항목마다 크게 달랐다.

## 이식 난이도는 "설정 파일 vs 실행 로직"으로 갈린다

- **거의 그대로 이식**: 스킬 정의(이름/설명 frontmatter), MCP 서버 정의(JSON 스키마) — 둘 다
  사실상 동일한 포맷을 썼다.
- **재작성 필요**: 훅(extension)은 개념은 같지만(이벤트에 반응해서 차단/로깅) 구현 방식이
  완전히 달랐다. 한쪽은 이벤트 API 객체에 콜백을 등록하는 방식이고, 다른 쪽은 그냥 **shell
  커맨드/실행파일**이 stdin으로 JSON 이벤트를 받고 exit code나 stdout JSON으로 응답하는
  방식이었다. 판단 로직(정규식, 위험 패턴 등)은 그대로 재사용 가능했지만 "이벤트에 훅을
  건다"는 틀 자체는 새로 짜야 했다.

## "차단"과 "확인 요청"은 다른 메커니즘이다

처음엔 위험한 명령을 완전 차단으로 만들었는데, 나중에 "너무 빡빡하니 매번 물어보는 정도로
풀어달라"는 요청을 받고 고쳤다. 새 하네스의 훅은 "차단(deny)"과 "매번 확인(ask)"을 분리해서
표현할 수 있었다 — "위험하지만 막지는 말고 매번 확인만"이라는 중간 강도의 요구를 만족시킬
수 있었다. 이전 하네스는 이 중간 단계가 없었다(한 번 승인하면 세션 내내 재확인 안 함, 아니면
완전 차단 둘 중 하나).

## 시크릿은 `${VAR}` 문법으로 런타임 치환된다 — 근데 직접 확인했다

MCP 서버 등록 시 토큰을 평문으로 박는 대신 참조 문자열(`${MY_TOKEN}`)을 쓰면, 하네스가 자기
프로세스 환경변수에서 찾아 치환해서 자식 프로세스(MCP 서버)에 넘겨준다. 이걸 문서나 추측으로
믿지 않고 직접 검증했다:

```bash
# 셸 확장을 막기 위해 반드시 싱글쿼트
some-cli mcp add -s user _test -e TESTVAR='${MY_VAR}' -- sh -c 'env > /tmp/check.txt'
# 자식 프로세스가 실제로 받은 값 확인
cat /tmp/check.txt | grep TESTVAR   # → 진짜 값이 찍힘 (플레이스홀더 문자열이 아니라)
```

이 방식으로 실제 값이 설정 파일엔 절대 남지 않고, 셸 로그인 시 별도 secrets 파일에서 소싱된
프로세스 환경변수를 통해서만 흘러간다는 걸 확인 후 확신을 갖고 적용했다.

## 스코프(scope)를 처음에 잘못 골랐다

처음엔 홈 디렉토리에 프로젝트 스코프로 MCP 서버를 등록했는데, 이건 **작업 디렉토리가 정확히
그 경로일 때만** 적용되는 설정이었다. 다른 프로젝트 폴더에서 작업할 땐 안 잡히는 걸 나중에
알아챘다. 전역(user) 스코프로 다시 등록하니 어느 프로젝트에서 실행하든 적용됐다. "설정이
등록됐다"와 "어디서든 적용된다"는 다른 문제이고, 스코프 개념이 있는 도구는 반드시 스코프를
확인해야 한다.

## 트러블슈팅

- 예외 패턴 매칭 버그: 도구 이름에서 서버 prefix를 뗀 채로 예외 정규식을 만들었는데, 원래
  정규식은 prefix가 붙은 형태를 기준으로 짜여 있어서 매칭이 안 됐다. 실제 입출력을 직접
  찍어보고서야 발견했다 — 로직을 코드로만 보고 맞다고 넘어가지 말고 실제로 돌려서 확인하는
  게 여기서도 유효했다.
- 훅이 실제로 발동하는지 증명할 때, 위험 패턴에 걸리는 명령을 실제로 실행할 순 없으니(그
  자체가 위험) sentinel 파일에 기록만 남기는 방식으로 우회 검증했다.

## 정리

- 겉보기 문법이 비슷한 두 시스템이라도, 판단 로직은 재사용 가능해도 "이벤트에 훅을 거는 틀"
  자체는 새로 짜야 할 수 있다.
- "차단"과 "확인 요청"을 분리해서 제공하는 도구라면, 요구사항의 강도에 맞는 걸 골라야 한다.
- 시크릿을 참조 문법으로 넣을 때는 "치환될 것이다"라고 믿지 말고, 자식 프로세스가 실제로
  받는 값을 찍어서 확인한다.
- 스코프 개념이 있는 설정은 등록 성공 여부와 별개로 적용 범위를 반드시 확인한다.
