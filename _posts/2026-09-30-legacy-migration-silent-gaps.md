이 글에 적은 네 건은 "같은 실수를 반복했다"고 깨달으며 모은 것이 아니다. 취약점 조치와 레거시 이관 티켓을 처리하다가 각각 따로 걸린 버그들이고, 노트를 정리하면서 보니 모양이 같았다. 넷 다 화면이나 로그에서는 정상이었다. 레거시 저장 프로시저가 쓰던 테이블 중 하나만 저장하고 끝난 일, 오래된 JDBC 드라이버가 글자를 '?'로 바꿔 보내서 몇 년치 손실이 숨어 있던 일, 이력 행을 삭제 대신 닫기로 바꾸다 경계 조건 다섯 개가 나온 일, 값을 안 바꾸고 저장했는데 저장된 글자가 줄어든 일이다.

나는 보통 성공 화면과 데이터까지는 확인하려고 노력하는 편이다. 설계 의도대로 진행되면 문제없다고 보고, 거기까지 맞으면 끝낸다. 이번에 잡힌 건들은 전부 그 지점에서 정상 동작이라고 착각한 부분이었다. 그리고 넷 중 셋은 내가 찾은 게 아니라 다른 곳에서 이상을 알려 와서 확인해 본 결과였다.

## 성공 화면이 떴는데 결제가 안 됐다

간편결제 가맹점 설정을 저장하는 화면을 레거시 JSP에서 새 화면과 새 API로 옮겼다. 저장을 누르면 "정상 변경"이 떴고, 화면용 테이블에 행도 들어갔다. 거기까지 보고 끝냈다.

이상을 알려 온 건 다른 쪽이었다. 테스트 가맹점에서 간편결제를 고르면 바로 오류가 났고, 간편결제사 응답은 카드 목록이 비어 있으면 안 된다는 내용이었다. 결제 서버는 설정 테이블 A의 묶음 식별자와 같은 값을 가진 인증 테이블 B의 행들로 카드 목록을 만든다. 레거시 저장 프로시저는 세 가지를 했다. 이전 묶음의 행을 정리하고, 카드사별 인증 행을 등록하고, 설정 테이블의 식별자를 갱신한다. 새 API는 화면용 테이블 하나만 저장하고 return했다.

테이블 A의 컬럼 값으로 테이블 B의 행을 찾는 연결은 눈에 띄지 않는다. 외래키 제약도 없고 화면에도 안 보인다. 저장 프로시저를 열어서 INSERT, UPDATE, DELETE가 어디로 가는지 하나씩 대조하지 않으면 빠진다.

연결 컬럼이 비어 있던 동안의 부작용 때문에 배포 순서도 문제가 됐다. 일반카드 조회 쿼리는 간편결제 묶음에 속한 식별자를 NOT IN으로 거른다. 수동으로 간편결제 식별자에 일반카드 값을 넣어 보정하면 일반카드 행이 화면에서 사라지고, 새 코드가 이전 묶음 행을 닫을 때 일반카드 설정까지 닫는다. 코드를 배포하기 전에 데이터부터 바로잡아야 했다.

비슷한 일이 설계 문서 단계에서도 있었다. PayPal 분쟁 수집기를 새 서비스에 붙이면서 "파라미터화만 하면 자동으로 기록된다"고 전제했는데, 이건 insert 경로만 본 판단이었다. 같은 테이블을 쓰는 다른 경로(재온보딩의 update)가 있었다. 또 계정 정보를 가맹점 속성으로 정규화했는데, 그 값을 읽는 쪽(백오피스 재조회, 책임 귀속)은 분쟁 건 단위로 읽고 있었다. "이 값은 X의 속성이다"라는 주장은 그 값을 누가 언제 읽는지로 검증해야 했다.

## 레거시가 멀쩡해 보였던 이유

같은 PayPal 분쟁 수집기 이야기다. 레거시와 같은 테이블에 쓰게 했더니 test에 배포하자마자 웹훅 적재가 계속 실패했다. 오류는 `Incorrect string value: '\xE2\x80\x93 ...'`였고, 문제의 바이트는 en dash(U+2013)였다. 컬럼 문자셋이 euckr이라 변환할 수 없다는 뜻이다. 이상한 건 레거시가 같은 컬럼에 몇 년째 문제없이 쓰고 있었다는 점이었다.

차이는 드라이버였다. 레거시의 Connector/J 5.x는 접속 문자셋을 지정하지 않으면 서버 문자셋(euckr)을 따른다. 표현할 수 없는 문자는 클라이언트가 '?'로 바꿔서 보내니 서버는 유효한 바이트만 받는다. 오류는 없고 손실만 있다. 새 서비스의 Connector/J 8.x는 지정이 없으면 UTF-8을 쓴다. 서버가 euckr로 변환하려다 거부하고 1366을 던진다.

그러니까 "레거시는 멀쩡하다"는 사실은 문제가 없다는 증거가 아니었다. 오류를 삼키고 있다는 신호였다. 신규 시스템이 오류를 낸 덕분에 기존 손실이 드러난 셈이다. 외부에서 들어오는 값은 기대하던 모양이 아닐 때가 많고, 그걸 알아챈 것도 결국 기록된 결과값이 일반적으로 기대하던 값이 아니었기 때문이었다.

컬럼을 utf8mb4로 바꾸기로 했는데 테이블 전체 변환은 두 군데서 막혔다.

- 행 크기 한도. 이력 테이블의 varchar 길이 합이 16,363자였다. euckr은 문자당 2바이트, utf8mb4는 4바이트라 환산하면 65,452바이트가 되어 MySQL 행 크기 한도 65,535바이트에 걸린다. 컬럼 단위로만 바꿀 수 있었다.
- 조인 키의 collation. 레거시 목록 화면이 분쟁 테이블의 거래 ID와 거래 테이블의 거래 ID를 조인한다. 한쪽만 utf8mb4로 바꾸면 `Illegal mix of collations`로 화면이 죽는다. 식별자 컬럼은 euckr로 남겨야 했다.

그래서 "PayPal이 만든 텍스트가 그대로 들어가는 컬럼만 바꾼다"는 기준을 세워 7개로 좁혔다. 처음에는 9개를 골랐는데 그중 둘은 우리가 URL 인코딩해서 저장하거나 우리가 만든 고정 문자열이라 비ASCII가 들어갈 수 없었다. 기준 없이 관련 있어 보이는 컬럼을 모으면 공유 테이블을 필요 이상으로 건드리게 된다. 레거시 컬럼에 이미 '?'가 박힌 행이 얼마나 쌓였는지는 확인하지 않았다.

## 선형 로그인데 삭제?

다시 간편결제 설정 화면이다. 새 설정을 저장할 때 이전 묶음의 인증 행을 어떻게 처리할지 정해야 했다. 레거시는 프로시저가 둘이었는데 서로 달랐다. 등록 프로시저는 이전 행을 상태나 기간과 상관없이 물리 삭제했고, 수정 프로시저는 상태를 종료로 바꾸고 새 기간 행을 INSERT했다. 새 화면은 수정 성격이라 닫는 쪽을 택했는데, 사실 "선형 로그인데 삭제?"라는 한마디로 정리됐다. 이력 테이블을 지우는 쪽은 처음부터 맞지 않았다.

닫는 방식 자체는 단순하다. 상태를 종료로, 사용 여부를 N으로 바꾸고 종료 시각을 새 시작 시각 빼기 1초로 둔다. 입력 시작일을 그대로 새 행의 시작으로 쓰면 과거 날짜일 때 이력이 다시 쓰이므로 시작은 입력값과 현재 시각 중 큰 값으로 잡는다.

단순한 건 거기까지였고, 리뷰를 세 번 돌리는 동안 경계가 다섯 개 나왔다.

- 과거 시작일은 위처럼 이력 덮어쓰기가 된다.
- 아직 시작 전인 행은 "유효" 판정이 현재 시각 기준이라 중복 INSERT가 났다. 종료 시각이 새 시작 이후인지로 판정해야 했다.
- 종료일이 이미 지난 입력은 시작이 종료보다 큰 행이 계속 쌓였다. 반영하지 않는다.
- 카드사 매핑이 없는 묶음은 이전 행만 닫히고 새 행이 0건이 되었다. 매핑 조회를 닫기보다 먼저 한다.
- 이미 만료된 행까지 종료 시각이 늘어났다. 종료 시각이 닫는 시각보다 뒤인 행만 닫는다.

모두 "지금 유효한 행 하나"를 가정하고 짠 코드가 기간이 겹치거나 비는 입력을 만났을 때 생긴 문제다. 레거시 두 프로시저가 삭제와 닫기로 갈라져 있었는데 어느 쪽이 원래 의도였는지는 끝내 확인하지 못했다.

## 702자가 616자가 됐다

마지막 건은 이관이 아니라 테스트에서 나왔다. 온보딩 화면의 저장 경로만 확인하려고 "값을 바꾸지 않고 저장"을 눌렀다. 저장 전후를 비교하면서 보고 있었는데, 첫 저장 직후 조회 화면의 글자 수가 702자에서 616자로 줄었다. 저장 전 값을 따로 남겨 두지 않아서 원래 값은 복구하지 못했다.

원인은 두 가지였다. 폼이 서버가 표시용으로 내려 준 placeholder("-", "null" 문자열)를 그대로 입력값으로 보냈고, 행이 없던 정산 정보가 "-" 값으로 새로 생겼다. 그리고 폼의 선택 목록은 코드 테이블의 버전 2만 갖고 있어서, 버전 1 값을 가진 예전 데이터는 선택이 비었고 빈 값이 저장됐다. 둘 다 표현 계층의 값이 데이터 계층으로 되돌아오는 경로의 문제다. 화면에 보이는 값이 곧 저장해도 되는 값이라는 보장은 없었다.

코드 테이블 버전이 공존하면 경로마다 다른 진실을 갖는다. 같은 중분류 코드가 버전 1과 버전 2에서 이름이 쉼표 뒤 공백 하나만큼 다르고 소분류 체계도 달랐다. 조회 API는 저장된 행(버전 1)을 그대로 보여 주는데 수정 폼과 저장 로직은 버전 2만 본다. 고친 방식은 저장 시 전달된 코드를 버전 2에서 찾지 못하면 기존 값을 유지하는 것이었다. 예전 데이터와 코드 목록이 어긋난 행이 얼마나 되는지는 세어 보지 않았다.

## 되돌아보면

넷 다 "의도대로 동작하는지"를 파악하는 게 생각보다 어렵다는 이야기였다. 특히 외부 통신이 끼면 더 그렇다. 성공 응답이 왔다는 것과 상대가 기대한 값을 받았다는 것은 다른 일이고, 그 차이는 결과 기록값을 들여다봐야 보였다.

다시 하면 순서를 이렇게 잡을 것 같다. 이관을 시작할 때 원본 코드에서 INSERT, UPDATE, DELETE를 전부 grep해서 대상 테이블과 컬럼 목록을 만들고, 새 API가 각각을 어디서 처리하는지 표로 맞춘다. 같은 테이블을 쓰는 다른 진입점(배치, 다른 화면, update 경로)도 같은 표에 넣는다. 같은 테이블에 쓰는 시스템이 둘 이상이면 드라이버 메이저 버전과 접속 문자셋부터 비교하고, 테이블 변환 전에는 varchar 길이 합에 문자당 바이트 수를 곱해 행 크기 한도를 먼저 계산한다. 기간 이력을 만지는 코드는 시작이 과거, 시작이 미래, 종료가 과거, 대응 행이 없음, 이미 만료된 행이 섞인 경우를 테스트 케이스로 먼저 만든다. 화면에서 쓰기 테스트를 하기 전에는 대상 항목의 스냅샷을 남기고, 폼이 보내는 전송 본문에 서버가 표시용으로 만든 값이 섞여 있는지 본다.

다만 이 목록을 다 지켰어도 셋은 여전히 다른 곳에서 알려 와야 알았을 것 같다. 성공 화면과 데이터까지 확인하는 습관은 이미 있었고, 그 뒤에 있는 것을 보려면 "정상"이라는 말을 한 번 더 의심해야 하는데, 그게 매번 되는 일인지는 아직 모르겠다.
