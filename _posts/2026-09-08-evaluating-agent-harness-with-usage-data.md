4개월간 써온 코딩 에이전트 하네스의 사용법/장단점을 회고로 정리하는 작업을 했다. 설계
의도(도입 당시 발표자료)와 실제 운영 데이터(세션 로그, 서브에이전트 실행 이력, 계측 로그)를
둘 다 놓고 비교하는 방식으로 접근했는데, 그 과정에서 손에 잡히는 소수 샘플만 보고
정반대 결론을 낼 뻔한 것이 이 글의 발단이다.

## 표본 편향 함정을 실제로 겪음

리뷰 서브에이전트가 실제로 쓸만한지 확인하려고 디스크에 남아있는 개별 실행 아티팩트를 먼저
봤는데, 공교롭게 남아있던 3건이 **전부 실패 사례**였다(인증 에러 1건, 대용량 토큰 소모 후
타임아웃 강제종료 1건, 단순 스모크테스트 1건). 이것만 보고 "서브에이전트 위임이 실무에서
잘 안 먹힌다"고 결론 낼 뻔했다.

그런데 별도로 남아있던 위임 이력 전체 기록(25건)을 마저 확인하니 완전히 다른 그림이 나왔다:

- 완료 22건 / 실패 3건 (실패율 12%)
- 완료된 것 중 20건이 실제로 유의미한 지적(보안 취약점, 로직 버그 등)을 담고 있었음
- "이상 없음"만 나온 완전 클린 케이스는 2건뿐

디스크 표본 3건(전부 실패)만 봤을 때와, 전수 25건(실패율 12%)을 봤을 때의 결론이 정반대였다.

왜 이렇게 갈렸나 되짚어보니, 디스크에 개별 파일로 남는 아티팩트는 저장 정책이나 우연에
따라 표본이 왜곡된다. 반면 실행 이력을 남기는 로그/인덱스는 전수를 담고 있어서 표본 편향이
없었다. 둘을 다 가진 상황이면 개별 아티팩트에 먼저 손대기 전에 전수 로그를 먼저 봤어야
했다는 게 이번에 얻은 교훈이다.

## 계측 데이터 자체도 의심해야 한다

세션별로 "작업 시간(duration)"을 자동 기록하는 필드가 있었는데, 세션 35개의 평균이 15시간을
넘게 나왔다. 말이 안 되는 수치라 파봤더니, 세션을 며칠씩 열어둔 채 간헐적으로 이어 쓰는 사용
패턴 때문에 "세션 시작 ~ 마지막 턴" 사이의 경과 시간이 잡힌 것이었다 — 실제 집중 작업
시간이 아니었다.

자동 계측 시스템이 만들어낸 숫자라고 해서 그 숫자가 측정하려던 걸 실제로 측정하고 있다는
보장은 없었다. 평균 15시간짜리 세션이 35개라는 수치처럼 상식과 어긋나는 값이 나오면, 이젠
숫자 자체보다 "이 숫자가 대체 뭐를 재고 있는가"를 먼저 의심하게 됐다.

## 설계 의도 vs 실측 데이터를 나란히 놓는 평가 프레임

"이 도구가 왜 만들어졌는가"(설계 문서)와 "실제로 어떻게 쓰였는가"(로그, 실행 이력)를 같이
놓고 비교하면, 둘이 일치하는 지점(진짜 강점)과 어긋나는 지점(과대평가된 약속, 또는 몰랐던
문제)이 자연스럽게 드러난다. 이번 회고에서 나온 지점들:

일치하는 쪽은 "투명성/커스터마이징"이라는 설계 목표였다. 안전장치를 직접 설계·검증한
사례로 실제 달성된 게 확인됐다. 어긋나는 쪽은 둘이었다. 하나는 정교하게 설계한 판정
규칙이 실사용에선 단순 기본값에 압도당한 것 — 계측 로그 895건 중 내가 만든 키워드 기반
판정이 실제로 발동한 건 2%뿐이었고 나머지는 전부 기본값 경로였다. 또 하나는 "안전장치를
만들었다"고 해도 실제 작업 경로를 보면 범용 셸 호출이 830회인 데 비해 전용 안전 도구 경유는
144회에 그쳐서, 우회 가능성이 생각보다 컸다는 점이었다.

설계자의 의도와 실제 사용자 행동은 늘 일치하지 않는다는 걸 데이터로 확인하는 과정이었다.

## 병렬 조사로 컨텍스트 확보하기

여러 개의 독립적인 읽기 전용 조사(로그 분석, 시스템 구조 조사, 타임라인 재구성)를 병렬로
진행할 때, 각 조사를 별도 에이전트에 위임하고 요약만 받으면 메인 작업 컨텍스트를 로그
원문으로 채우지 않고도 깊은 조사가 가능했다. 조사 대상이 서로 겹치지 않게 미리 나눠주는
게 중복 작업을 막는 핵심이었다.

## 되돌아보면

세 가지가 남는다. 신뢰성이나 성공률을 볼 때는 손에 잡히는 샘플보다 전수를 담은
로그/인덱스를 먼저 찾는 게 안전했고, 자동 계측 지표가 상식과 어긋날 때는 지표의 정의부터
다시 봤다. 그리고 설계 의도 문서와 실측 데이터를 나란히 놓았을 때 일치/불일치 지점에서
가장 쓸만한 인사이트가 나왔다. 조사 자체도 서로 겹치지 않는 읽기 전용 작업으로 나눠 병렬로
위임하니 깊이와 컨텍스트 효율을 동시에 가져갈 수 있었다.
