쿠키로 로그인을 공유하는 SSO를 만들어 운영한 지 꽤 됐다. 요구사항은 다 맞췄지만 이게 최선인지는 계속 의문이었다. 그러던 중 ISMS 점검에서 계정 분리 항목이 다시 확인됐고, 내부 관리자 계정과 파트너 계정을 나눠야 한다는 요구가 생겼다. 계정을 나누면 SSO도 다시 봐야 한다. 그 김에 표준인 OIDC를 처음부터 다시 팠다.

막상 파 보니 용어부터 헷갈렸고, 알고 있다고 생각한 것 중 꽤 많은 게 틀려 있었다. 틀렸던 순서대로 적어 둔다.

## SSO, OAuth, OIDC는 같은 층의 단어가 아니다

| 용어 | 정체 | 답하는 질문 |
|------|------|-------------|
| SSO | 목표이자 사용자 경험. 프로토콜이 아니다 | 한 번 로그인으로 여러 서비스를 쓰는가 |
| OAuth 2.0 | 인가 위임 프로토콜 | 이 앱이 내 대신 API를 불러도 되는가 |
| OIDC | OAuth 2.0 위에 얹은 인증 계층 | 지금 로그인한 사람이 누구인가 |
| SAML 2.0 | XML 기반 SSO 프로토콜 | OIDC와 같은 질문 |

"OAuth로 로그인했다"는 엄밀히 틀린 말이다. access token은 누구에게, 어느 앱을 위해 발급했는지를 보장하지 않아서, 다른 앱용으로 받은 토큰을 이 앱에 들이밀면 통과해 버린다. OIDC는 ID Token에 `aud`(이 토큰을 받기로 정해진 쪽)를 넣어서 이걸 막는다. 그래서 ID Token을 API 인가에 쓰는 것도 틀린 설계다. ID Token의 `aud`는 API가 아니라 로그인한 앱이기 때문이다. ID Token은 앱이 읽는 신분증이고, access token은 API가 읽는 출입증이다.

## IdP가 처음 주는 건 code다

처음에는 IdP가 로그인을 확인하면 토큰을 준다고 생각했다. OTP처럼 사용자가 받은 코드를 입력하면 토큰이 나오는 그림을 떠올렸다. 둘 다 틀렸다.

1. 앱이 state, nonce, PKCE verifier를 만들어 **자기 세션에 저장**하고, verifier의 해시(challenge)만 붙여 브라우저를 IdP로 보낸다.
2. IdP는 로그인을 확인하고 code를 만든다. 이때 code를 challenge, nonce, client_id와 연결해 둔다.
3. 브라우저가 리다이렉트를 따라 code를 앱으로 옮긴다. 사용자는 이 code를 보지도 입력하지도 않는다.
4. 앱 서버가 code와 verifier를 IdP에 **직접** 보내 토큰으로 바꾼다.
5. 앱은 ID Token의 서명, `iss`, `aud`, `exp`, `nonce`를 검증하고 자기 세션 쿠키를 발급한다.

토큰이 브라우저 URL을 한 번도 거치지 않는 게 핵심이다. 토큰을 URL로 바로 주던 Implicit flow가 폐기된 이유가 여기 있다. 사용자가 코드를 직접 입력하는 흐름은 TV 로그인 같은 Device Authorization flow라는 별도 흐름이었다.

state, nonce, PKCE를 매 요청마다 쓰는 줄 알았던 것도 틀렸다. 셋 다 로그인 과정에서 한 번 쓰고 버린다. 로그인이 끝난 뒤의 요청은 앱이 발급한 평범한 세션 쿠키로 처리한다.

## state, nonce, PKCE는 같은 일을 한다

셋을 따로 외우다가 헷갈렸는데, 공통점을 찾고 나서 정리가 됐다. 요청을 시작할 때 세션에 값을 하나 남기고, 결과가 돌아왔을 때 그 값에 묶인 결과인지 확인한다. 결과물(code, 토큰)만 손에 넣은 쪽은 그걸 다른 세션으로 옮길 수 없다. 차이는 무엇을 묶고 누가 확인하느냐뿐이다.

| 장치 | 결과물과 묶이는 방식 | 확인하는 쪽 |
|------|---------------------|-------------|
| state | 콜백 URL로 그대로 돌아온다. code와는 묶이지 않는다 | 앱 |
| nonce | IdP가 ID Token 안에 넣어 서명한다 | 앱 |
| PKCE | IdP가 code를 challenge에 연결한다 | IdP |

이 표를 놓고 보니 헷갈렸던 질문들이 풀렸다.

state가 없으면 IdP가 code 발급을 막을 거라고 생각했다. 아니었다. IdP는 앱의 세션을 모르니 state를 검증할 수 없고, 받은 값을 그대로 돌려줄 뿐이다. 표준에서도 필수가 아니다.

state만으로 code 바꿔치기를 막을 수 있는지도 물었다. 막지 못한다. 공격자는 피해자의 state가 필요 없다. 자기 브라우저로 정상 앱에 로그인을 시작해 자기 세션의 state를 얻은 다음, 콜백 URL의 code만 피해자 것으로 바꾸면 state 검증을 통과한다. state와 code가 묶여 있지 않기 때문이다.

client secret이 있는 서버 앱에도 PKCE가 필요한 이유는, 처음에 "세션을 서버에 두기 힘들어서 클라이언트로 넘기는 것"과 섞어서 이해했다. 그건 stateless 토큰 이야기였다. secret은 "교환하는 쪽이 진짜 앱 서버인가"만 증명하고 "이 code가 이 세션이 시작한 요청의 code인가"는 증명하지 못한다. 그래서 RFC 9700(OAuth 2.0 Security BCP)은 secret을 가진 앱에도 PKCE를 권한다.

반대로 PKCE만 있어도 login CSRF가 막힌다는 건 의외였다. 공격자의 code는 공격자의 verifier에 묶여 있어서 피해자 세션의 verifier로는 교환되지 않는다. 다만 IdP가 PKCE를 **강제**해야 한다. challenge 없이 받은 code를 verifier 확인 없이 바꿔 주면 그대로 뚫린다.

## SSO는 토큰을 나눠 써서 되는 게 아니었다

여러 앱이 토큰 하나를 공유해서 SSO가 된다고 생각하고 있었다. 실제로 공유되는 건 IdP 도메인에 있는 IdP 세션 쿠키 하나다. 앱 B에 처음 들어가면 B는 브라우저를 IdP로 보내고, 브라우저는 IdP 도메인으로 가니 IdP 쿠키를 IdP에게 보낸다. IdP는 화면 없이 B 전용 code를 발급한다. 쿠키가 도메인을 넘지 않는다는 원칙은 그대로이고, 리다이렉트로 브라우저를 IdP 도메인에 데려갈 뿐이다.

저장소도 세 곳으로 나뉜다. IdP 세션 쿠키는 브라우저의 IdP 도메인에, 앱이 받은 토큰은 앱 서버 세션에, 브라우저의 앱 도메인에는 세션 ID만 둔다. 토큰을 브라우저에 내리지 않는 게 권장인데, SPA도 얇은 백엔드(BFF)를 두어 이 구조를 따른다.

## 로그인보다 로그아웃이 어렵다

IdP 세션만 끊기면 이미 로그인한 앱은 계속 쓸 수 있다. 앱 세션만 끊기면 다음 로그인 버튼에서 IdP 세션 덕에 비밀번호 없이 다시 들어간다. 로그아웃은 하나의 동작이 아니라 IdP 세션과 앱 세션 각각을 정리하는 여러 동작이다.

표준은 세 가지를 둔다. 앱이 IdP 로그아웃 주소로 보내는 RP-Initiated Logout, IdP가 각 앱 서버에 서명된 logout token을 보내는 Back-Channel Logout, iframe으로 각 앱을 부르는 Front-Channel Logout이다. 마지막은 서드파티 쿠키 차단으로 점점 동작하지 않는다. Back-Channel Logout을 받으려면 앱이 세션을 만들 때 `sub`와 `sid`로 자기 세션을 찾는 역방향 인덱스를 둬야 한다. logout token에는 앱의 세션 ID가 없기 때문이다.

## 솔트 없는 해시 한 줄

공부하는 김에 비밀번호 저장도 다시 봤다. 솔트 없는 SHA-256은 같은 비밀번호가 같은 해시가 되고, 빠른 해시라 무차별 대입에 약하다. 표준은 느리게 설계된 솔트 포함 해시(Argon2id, bcrypt)다. 옮길 때는 기존 해시를 통째로 감싸면(`argon2(sha256값)`) 전 계정을 한 번에 보호할 수 있다. 다만 감싼 저장소만 보호된다는 걸 놓치기 쉽다. 옛 컬럼이 남아 있고 거기서 로그인을 판정하면 감싼 효과는 없다.

되돌아보면 OIDC의 뼈대는 한 문장이었다. IdP가 교환권을 브라우저 편에 주고, 앱이 그 교환권을 서버끼리 자기 전용 토큰으로 바꾼다. 나머지 장치는 이 과정에 끼어드는 공격을 하나씩 막는 것이었다. 아직 구현해 본 적이 없어서 세부가 흐린 부분은 로컬에 IdP를 띄우고 위 다섯 단계를 직접 보내 보며 채울 생각이다. SAML은 왜 아직 기업 SSO에서 쓰이는지, 서명 키를 회전할 때 무슨 일이 생기는지도 다음에 볼 질문으로 남겨 둔다.
