> 한 줄 요약: 대규모 트래픽 대응은 "무슨 기술을 쓰나"가 아니라 "수직→수평 확장을 강제하는 이유(처리량·가용성) → Stateless라는 전제 → 상태를 어디 두나 → DB 병목을 싼 해법부터 푸는 순서"라는 사고 흐름으로 쌓아야 한다.

## 배운 맥락

"초당 10만 TPS를 어떻게 감당하나"라는 질문에서 출발.
처음엔 로드밸런서/샤딩/Redis/Kafka 같은 기술 목록으로 접근했으나,
기초부터 "왜 이 해법이 필요한가"를 층층이 쌓는 방식으로 다시 정리했다.
기술 나열보다 각 해법이 어떤 병목을 푸는지 매칭하는 게 핵심.

## 1층. Scale-up vs Scale-out — 왜 수평 확장인가

- **Scale-up(수직)**: 서버 사양 ↑. 주로 latency(빠르기) 개선. 단순하지만 한계 명확.
- **Scale-out(수평)**: 서버 대수 ↑. 주로 throughput(처리량) 개선.

두 축을 구분하는 게 첫 뼈대:

- **Latency(지연시간)**: 요청 1건 처리 시간 = "얼마나 빠른가"
- **Throughput(처리량, TPS)**: 단위 시간당 처리 건수 = "한 번에 몇 건인가"

10만 TPS는 latency 문제가 아니라 throughput 문제 → Scale-out이 답.

Scale-up의 한계 3가지:

1. **물리적 한계** — 코어/RAM 상한이 있고, 2배 올려도 2배 성능 아님(병목이 이동).
2. **비용 곡선** — 고사양일수록 가격이 기하급수적. 평범한 서버 여러 대가 더 쌈.
3. **가용성(SPOF)** — 1대면 죽는 순간 전체 정지. Scale-out은 1대 죽어도 나머지가 버팀.

> 핵심: Scale-out은 처리량뿐 아니라 "한 대 죽어도 안 죽는다"는 가용성을 같이 얻는다. 대규모가 수평 확장을 택하는 이유의 절반이 이 가용성.

## 2층. 요청을 어떻게 나누나 — 3가지 장치 구분

역할이 다른 셋을 혼동하면 안 됨:

- **로드 밸런서**: 동기 요청을 여러 서버에 즉시 분배. 사용자는 응답을 기다림.
  - L4(IP/포트만) vs L7(HTTP 내용까지 보고 라우팅)
  - 알고리즘: Round Robin / Least Connections / Hash 기반
- **API Gateway**: 공통 관문(인증·인가·rate limit·로깅). 분배가 목적이 아니라 "거르기"가 목적. LB와 경쟁이 아니라 역할 분담.
- **메시지 큐**: 비동기 작업 분배. 큐에 쌓고 워커가 나중에 처리. 요청자는 안 기다림("접수됐습니다"만 받음).

비유: LB = 즉시 창구 배정 안내원 / MQ = 번호표 뽑고 문자 기다리는 접수 시스템.

흐름:

```text
사용자 → 로드밸런서 → API Gateway → 앱 서버 여러 대
                                        ↓ 무거운 작업
                                   메시지 큐 → 워커(비동기)
```

> 동기 처리의 대기 딜레이 문제를 푸는 한 방법 = 무거운 작업을 동기에서 비동기(메시지 큐)로 빼는 것.

## 3층. Stateless — Scale-out의 진짜 전제

문제: 사용자 세션이 3번 서버 메모리에 있는데 LB가 다음 요청을 7번으로 보내면? → 세션 불일치(로그아웃/에러). 근본은 **상태(state)를 어디 두나** 문제.

해법:

- **Sticky Session** (임시방편): LB가 같은 사용자를 늘 같은 서버로 고정(Hash 분배). 하지만 부하 불균형 + 그 서버 죽으면 세션 소실 + Scale-out 무력화 → 권장 안 됨.
- **Stateless(무상태)** (정석): 상태를 서버 밖으로 빼면 어느 서버로 가든 동등. Scale-out의 진짜 전제.

상태를 뺄 곳 2가지:

| | JWT(클라이언트) | Redis 세션(공용 저장소) |
|---|---|---|
| 서버 무상태 | 완전 | 완전 |
| 세션 저장소 | 불필요 | 필요(Redis) |
| 강제 로그아웃 | 어려움 | 쉬움 |
| 요청당 비용 | 서명검증만 | Redis 왕복 1회 |
| 탈취 시 | 만료 전까지 유효 | 즉시 무효화 |

> JWT의 결정적 함정: 발급 후 강제 로그아웃(무효화)이 어렵다. "JWT 쓰면 됨"으로 끝내면 안 되고, 무효화가 필요하면 Redis blacklist 병용 등을 고려. 상황에 맞춰 선택(정답 하나 아님).

## 4층. DB 병목 — 싼 해법부터

앱 서버는 Stateless라 무한 확장했지만 결국 DB 한 대를 같이 바라봄.

DB에서 터지는 3가지:

1. **커넥션 한계** — 동시 연결 수 상한. 앱 서버 × 커넥션풀이 넘으면 대기/고갈.
2. **디스크 I/O** — DB는 결국 디스크에 씀. 특히 write는 fsync 때문에 느림.
3. **락 경쟁** — 같은 데이터 동시 수정 시 락 대기 폭발(`SELECT FOR UPDATE`가 대표).

핵심 관찰: **읽기와 쓰기는 성격이 다르다.**

- 읽기: 여러 곳에서 동시에 해도 안 부딪힘(복사 가능)
- 쓰기: 원본이 하나여야 정합성 유지

해법 순서(싼 것 → 비싼 것):

1. **캐싱(읽기)** — 자주 읽는 데이터를 Redis에 복사, DB 대신 Redis에서 읽기. 읽기 80~90% 서비스면 이것만으로 DB 부하 대부분 제거. **가장 먼저 쓰는 첫수.**
2. **읽기 복제(Read Replica)** — 쓰기 전용 Primary 1 + 읽기 전용 Replica N. 읽기는 복사해도 되니 분산 가능. (CQRS의 물리적 기반 → 여기서 복제 지연 문제 발생)
3. **큐 버퍼링(쓰기)** — 쓰기를 메시지 큐에 쌓고 DB가 감당할 속도로 소비. 쓰기 평탄화.
4. **샤딩(쓰기, 최후)** — DB를 user_id 등으로 물리 분할. 강력하지만 JOIN 불가 + 분산 트랜잭션 지옥으로 개발 난이도 폭발 → **마지막 수단.**

> 교정: "10만 TPS니까 샤딩이 메인" = 틀림. 샤딩은 최후의 보루. 먼저 읽기/쓰기 비율을 나눠보고 캐싱→읽기복제→큐버퍼링을 소진한 뒤 샤딩. 가장 놓치기 쉬운 첫수는 캐싱(읽기 부하 제거).

## 정리 (takeaway)

- 스케일링은 기술 목록이 아니라 **"병목의 정체 → 그걸 푸는 해법" 매칭**으로 이해한다.
- Scale-out의 목적은 처리량 + 가용성 두 가지. 그 전제는 Stateless.
- DB 부하는 읽기/쓰기를 나눠서, **싼 해법(캐싱)부터** 순서대로. 샤딩은 마지막.
