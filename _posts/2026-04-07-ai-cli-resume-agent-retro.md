개인 사이드로 "AI CLI + 스킬/MCP/프롬프트로 내 경력·직무 경험을 정리하고 이력서를 쓰는" 에이전트를
하루 만에 해커톤처럼 바짝 만들었다. 하루 만에 돌아가는 걸 목표로 속도를 낸 턴이라, 지금 다시 보면
구조가 불안하고 급하게 붙인 티가 난다. 잘 만든 자랑보다, 만들면서 뭘 잘못 판단했고 다음엔 어떻게
할지를 남기려고 쓴다.

## 왜 팠나

이력서를 쓸 때마다 매번 경력을 다시 떠올려 적는 게 비효율이라, 경험을 한 번 정리해두고 계속 재활용하고 싶었다.
GitHub를 저장 공간으로 써서 어느 기기에서 접속하든 작업을 이어가는 "연속성"이 목표였다.
동기를 굳이 나누면, 실제 불편 해소 반, AI 에이전트 패턴을 직접 만들어보고 싶은 연습 반이었다.

## 무엇을 시도했나

만든 것 자체는 규모가 꽤 나왔다. 9단계 파이프라인(파싱 → 공고 분석 → 데이터 충분도 판단 → 선택지 제시 →
초안 생성 → 신뢰도 검증 → 사용자 검토 → 저장 → 정리), 작업 종류별 LLM 라우팅(구조화 작업과 문장 작업을 다른
모델에), RAG로 경력 데이터 검색, 그리고 소스에 없는 내용은 이력서에 못 넣게 막는 신뢰도 검증 단계까지.

방향은 하루 안에서 한 번 크게 틀었다. 처음엔 일반 웹 프로젝트처럼 생각해서 API를 기능별로 따로 짜고, MCP에 가까운
형태로 만든 다음 UI를 붙일 생각이었다. 그런데 그렇게 가니 정작 내가 원했던 "CLI에서 자연어로 작업하는" 맛이
없었다. 그래서 AI를 스킬·MCP·프롬프트로 튜닝해서 CLI에서 직접 쓰는 쪽으로 갈아탔다. 이 전환은 커밋
순서에도 그대로 남아 있다 — 파이프라인을 한 번에 올린 뒤, mock interview MCP·FastMCP 서버·resume MCP tools가
줄줄이 붙으면서 무게중심이 CLI/MCP로 옮겨가는 게 보인다.

이력서가 주목적이라 환각 방지가 제일 중요했다. 그래서 내용 검증 장치를 이것저것 붙이는 것부터 시작했다.
도구는 Kiro(AI 코딩 CLI)를 썼다. Kiro의 steering(에이전트 행동 지침) 기능으로 경력 관리·인터뷰·이력서 생성 등
작업별 지침 파일을 두고, MCP 서버와 프롬프트를 얹어 CLI에서 자연어로 돌리는 구성이었다. 구현 전에 설계 스펙
문서를 먼저 길게 썼다(이력서 파이프라인 스펙 + 인터뷰 MCP 스펙). 하루짜리 작업치곤 스펙을 앞세운 건 잘한 편이었다.

## 걸렸던 지점 / 안 됐던 것

- **"어디서나 연속성" 목표가 컨텍스트 한계에 막혔다.** GitHub에 데이터를 두면 될 줄 알았는데, 실제로는
  세션마다 그 데이터를 다 물고 갈 수 없어서 연속성이 기대만큼 살지 않았다. 저장소 문제가 아니라 컨텍스트 문제였다.

- **AI CLI 특성상 오차가 많았다.** 결과물은 뽑아내는데 MCP 호출을 빼먹거나 지정해둔 스킬을 까먹는 일이 잦았다.
  "결과가 나온다"와 "시킨 대로 정확히 한다"는 다른 얘기라는 걸 여기서 체감했다.

- **환각 방지의 진짜 병목은 컨텍스트 용량이 아니었다.** 검증이 흔들린 원인은 당시 쓰던 도구가 작업마다 모델을
  바꿔 선택하는 특성 쪽이었다. 같은 검증 프롬프트라도 어느 모델이 받느냐에 따라 결과가 달라졌다. 이건 모델을
  고정해서 쓰면 풀릴 문제이긴 했다.

- **도구(Kiro) 자체의 코딩 제약에 당황했다.** 옵션 설정으로 결국 풀긴 했지만 여기서 시간을 꽤 썼다. 내가 만들려는 것
  이전에, 쓰는 도구의 제약을 파악하는 데 드는 비용을 얕봤다. 커밋에 "Kiro API 제약 우회"라는 흔적이 남을 정도로,
  본 작업보다 도구 제약 푸는 데 시간을 썼다.

## 다시 만들면

기초가 부족한 채로 생각나는 대로 붙이다 보니, 솔직히 뭔가 제대로 굴러간다는 느낌이 부족했다. 돌아보면 두 가지다.

첫째, CLI의 장점을 살리고 싶었다면 오케스트레이션을 제대로 잡고, 기능별로 프롬프트를 따로 명확히 지정하고,
하네스(에이전트가 정해진 절차를 벗어나지 않게 잡아주는 틀)를 더 빡세게 짰어야 했다. 결과만 뽑는 게 아니라
"시킨 순서대로 빠짐없이" 하도록 강제하는 부분이 약했다.

둘째, 이게 제일 큰데 — AI 프로덕트에 대한 이해가 부족했다기보다, **기존 애플리케이션 구조를 너무 부수면서
작업한 게 패착**이었다. 웹 API로 시작한 걸 CLI 에이전트로 갈아탈 때 기존 구조를 살려서 얹었어야 했는데,
갈아엎다 보니 안정적인 뼈대 없이 계속 흔들렸다.

셋째, 둘째보다 더 밑에 있는 원인이 하나 더 있다 — 처음 쓴 스펙을 계속 쌓아가는 게 아니라 생각나는대로
기능을 붙여나가다 방향도 즉흥적으로 바꿔버렸다. 스펙은 초반 잠깐 쓰고 그 뒤로는 붙들지 않았다. 방향을
틀 때 스펙을 먼저 고쳤어야, 어디까지 살리고 어디까지 부술지가 문서 위에서 계산됐을 텐데, 그걸 안 하니
구조를 부수는 데 거리낌이 없었다.

## 이후에 이런 것들을 공부해서 다시 이해했다

이 회고를 하고 난 다음, 위에서 낸 진단들을 감상에서 그치지 않도록 하네스와 오케스트레이션을
따로 파서 다시 익혔다.

- **MCP 호출 누락·스킬 망각** — LLM은 절차를 지키는 기계가 아니라 확률적으로 다음 토큰을 뽑는
  모델이다. 프롬프트로 절차를 "부탁"하는 대신 코드가 도구 호출을 직접 실행하고 검증하는
  하네스로 옮겨야 했다.
- **구조를 부순 패착** — 스펙을 방향 전환의 계약으로 붙들지 않은 게 근본 원인이었다. 스펙이
  불변식·경계·범위를 명시하고 개발 내내 주인 역할을 했다면, 전환의 영향 범위를 스펙에서
  먼저 계산해 필요 이상으로 부수지 않았을 것이다.
- **환각 방지 장치가 흔들린 이유** — 그라운딩은 소스 제약 프롬프트만으론 부족하고 출처 추적·
  분리된 검증 단계·신뢰도 임계치를 층으로 쌓아야 한다는 걸 알았다. 그리고 신뢰도 점수 자체가
  과신하는 경향이 있어(캘리브레이션 문제) 그대로 믿으면 오히려 환각을 인증해주는 꼴이 된다는
  것도.
- **RAG를 대충 넘긴 것** — 개인 경력처럼 자료가 작은 경우 RAG(검색)가 오히려 전체 맥락을
  놓치게 만들 수 있고, 이력서(종합 작업)와 경력기술서(기점 집중 작업)는 필요한 데이터 단위
  자체가 다르다는 걸 나중에야 알았다. RAG 기법보다 먼저 이 도메인 모델링이 있어야 했다.
- **인터뷰가 페르소나 놀이에 그친 것** — 면접관 말투(페르소나)와 정보 수집 절차(프로토콜)는
  다른 축이다. 페르소나만 있으면 LLM이 대화가 자연스럽게 끝나는 지점에서 마무리 지어버리고
  정보가 채워졌는지는 아무도 확인하지 않는다. 완료 조건을 코드로 정의하고 미완료면 재질문을
  강제하는 프로토콜이 먼저였어야 했다.
- **경력 데이터를 계속 덮어쓴 것** — 인터뷰마다 필드를 덮어쓰면 이전 답변의 세부와 출처가
  사라진다. 원문은 지우지 않고 새 정보를 이벤트처럼 계속 쌓아야 나중에 검증이 실제로 의미가
  있다는 것도 뒤늦게 이해했다.

(자세한 개념 정리는 별도 노트 "AI 에이전트를 만들 때 절차는 코드가, 표현은 LLM이"에 있다.)

## 한 줄

AI 에이전트를 만들 때 어려운 건 모델이 아니라, 절차를 벗어나지 않게 잡는 하네스와 기존 구조를 함부로 부수지
않는 절제였다. 도구의 제약(모델 선택 방식, 코딩 제한)을 먼저 파악하는 비용도 생각보다 크다.
