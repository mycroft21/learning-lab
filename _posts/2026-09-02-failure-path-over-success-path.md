> 한 줄 요약: 10만 TPS 아키텍처의 난이도는 잘 돌아갈 때가 아니라 장애·롤백·데이터 유실 시나리오에 있다. AI가 주는 기술 목록은 성공 경로 위주라, 실무에선 실패 경로(장애 내성·정합성·관측성)를 스스로 채워야 한다.

## 배운 맥락

"10만 TPS 서버 스케일링" 개념을 정리한 뒤, AI 어시스턴트의 답변을 검증하는 과정에서 얻은 관점.
AI 답변은 큰 그림(LB → Stateless → 캐시 → 샤딩 → MQ)은 정확했지만,
실무에서 정작 밤새우게 만드는 "실패 시나리오"를 대부분 빠뜨렸다.
개념 학습과 별개로, "무엇이 빠지기 쉬운가"라는 경험적 체크리스트로 정리.

## AI 기술 목록에서 빠지기 쉬운 것들

### 1. 장애 내성 (성공 경로만 있고 실패 경로가 없음)

- **Graceful Degradation** — 스파이크가 예측을 넘으면 전체가 죽는 것보다 비핵심 기능을 의도적으로 끈다(추천→인기순, 리뷰/찜→503). "다 처리한다"는 전제가 위험.
- **Circuit Breaker** — 외부 의존(외부 API 등)이 느려질 때 연쇄 장애(cascading failure)를 끊는다. 외부 호출이 많은 구조엔 필수.
- **Rate Limiting** — 매크로 방지용이 아니라 모든 레이어의 기본 방어. Gateway에서 Token Bucket/Sliding Window로 첫 방벽.

### 2. 데이터 유실 리스크 (캐시를 저장소처럼 믿는 함정)

- Redis Write-Back(캐시에 먼저 쓰고 배치로 DB 반영)은 "샤딩 대안"처럼 제시되지만, Redis는 메모리 DB라 노드가 죽으면 마지막 fsync 이후 데이터가 날아간다.
- 금융/결제처럼 유실이 치명적인 데이터에 이 패턴 단독 사용은 위험. Write-Ahead Log를 Kafka 등 다른 곳에도 남겨야 복구 가능.
- **읽기 캐시 최적화와 쓰기 버퍼링은 별개 문제.** 쓰기 자체가 10만 TPS면 버퍼링만으론 한계, 결국 샤딩/NoSQL 필요.

### 3. 이벤트 발행의 원자성

- TTL 만료로 자동 복구할 때 Redis Keyspace Notifications는 Pub/Sub 기반이라 "fire and forget" — 컨슈머가 잠깐 죽으면 이벤트 유실. 신뢰 불가.
- 실무 정석은 배치 스케줄러(주기적으로 방치된 작업 조회) + **Outbox Pattern**: DB 상태 기록과 같은 트랜잭션으로 outbox에 이벤트를 쓰고, 별도 폴러가 읽어 발행 → DB 트랜잭션과 이벤트 발행의 원자성 보장.

### 4. Backpressure (배압)

- "Kafka에 쌓고 DB가 감당할 속도로 소비"는 좋지만, 유입 속도 > 소비 속도가 지속되면 consumer lag이 무한히 늘어난다.
- 대응: 컨슈머 수평 확장(파티션 수 = 컨슈머 수) 또는 프로듀서 쪽 reject 전략.

### 5. 관측성 (Observability)

- 설계가 훌륭해도 "어디가 병목인지" 모르면 장애 대응 불가. AI 답변에 거의 항상 빠짐.
- Distributed Tracing(Jaeger/Zipkin), Metrics(Prometheus/Grafana, p99 레이턴시·에러율), Alerting(Redis 메모리, consumer lag, DB 커넥션 풀 고갈).

## 정리 (takeaway)

- "성공 경로 20% : 실패 경로 80%" — 대규모 시스템의 클래스는 실패 케이스를 얼마나 우아하게 처리하느냐로 갈린다.
- AI가 주는 아키텍처 답변은 성공 경로 위주의 기술 목록이다. 검증할 때 **"이게 실패하면? 노드가 죽으면? 이벤트가 유실되면?"**을 스스로 물어야 실무 수준이 된다.
- 분산 시스템은 단일 트랜잭션의 자동 롤백이 사라지므로, 보상 트랜잭션 + 멱등성 + 최종 일관성을 직접 설계해야 한다.
