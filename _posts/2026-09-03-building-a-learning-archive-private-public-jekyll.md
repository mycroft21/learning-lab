> 한 줄 요약: 저장(git에 쌓기)과 노출(사이트로 발행)은 완전히 다른 문제다. 그리고 유출 리스크가 있는 환경에서 기록을 남기려면 "원본은 자유롭게, 공개는 게이트"로 분리하는 게 정답이다.

## 배운 맥락

회사 코드가 섞이는 환경에서 학습한 내용을 개인 GitHub에 기록하고 싶었다. 문제는 대부분의
작업이 회사 코드/도메인 로직이라 그대로 공개하면 유출이라는 점이었다. 처음엔 2-repo 구조로
이 문제를 풀었고, 몇 달 뒤엔 "이걸 git에 md로 쌓아두는 정도로 괜찮은가"라는 의문이 들어
실제 사이트로 옮겼다. 그 두 단계를 함께 정리한다.

## 1단계 — private/public 2-repo 분리

- private repo: 원본. 회사 맥락이 섞여도 OK. 절대 공개로 전환 안 함.
- public repo: 정제본. 회사 식별정보 0. 포트폴리오.

**자동화와 사람 게이트의 위치**: private에 쓰는 건 자동으로 반영한다(어차피 비공개라
리스크가 낮다). 공개로 승격하는 건 **반드시 사람 확인 1단계**를 거친다. 자동화의 안전장치는
되돌리기 어려운 지점(공개)에만 두고, 리스크가 낮은 지점(비공개 저장)은 마찰 없이 흘러가게
한다는 원칙이다.

기존에 "자동으로 커밋/푸시하지 않는다"는 규칙이 있었는데, 이 자동 저장은 그 규칙의 명시적
예외로 두되 특정 두 경로에만 한정했다. 기존 안전 규칙에 예외를 둘 땐 예외의 범위를 명시적으로
좁혀야 한다.

## 2단계 — md 파일 더미에서 Jekyll 사이트로

몇 달 노트를 쌓다 보니 두 가지가 걸렸다. 첫째, git repo의 md 파일은 발견 가능성이 거의
없다 — 링크를 아는 사람만 본다. 둘째, 목차를 수동으로 갱신하는 방식이라 노트가 늘수록
관리가 밀린다. "발견되고 싶다"는 욕구에서, 있는 repo에 정적 사이트 생성기(Jekyll +
GitHub Pages)를 얹는 쪽으로 방향을 잡았다.

### 폴더 구조를 블로그 표준으로

기존 구조(카테고리별 폴더)를 Jekyll 관례(날짜가 파일명에 들어가는 포스트 형식)로 옮겼다.
여기서 첫 실수: 파일 날짜를 승격한 날짜로 그냥 몰아 넣었더니 포스트가 한 시점에 몰려
있었다. **적당히 분산시키는 것과 실제 근거(원래 작업/학습 날짜)에 맞춰 배치하는 것은
완전히 다른 신뢰도를 만든다.** 전자는 "그냥 채워넣은 것"이 보이고, 후자는 진짜 타임라인이
된다.

### 테마의 암묵적 동작에 걸린 것들

- 정적 사이트 생성기는 `index` 파일이 없으면 README를 자동으로 홈으로 승격시키는 동작이
  있다. `index` 파일을 명시적으로 만들어 해결했는데, 레이아웃 이름을 잘못 고르면 테마가
  자체적으로 글 목록을 또 그려서 내가 짠 섹션과 중복 렌더링되는 문제도 있었다. 테마의
  기본 레이아웃 이름이 어떤 암묵적 동작을 갖는지 모르고 쓰면 이런 중복이 난다.
- 커스텀 데이터 파일 이름을 업계 표준 스키마가 있는 이름(예: "resume")으로 지었더니, 정적
  분석 도구가 파일명만 보고 표준 스키마를 강요해서 내가 만든 커스텀 필드가 전부 위반으로
  잡혔다. 실제 문법 오류가 아니라 파일명 기반 스키마 추론의 오탐이었다. 커스텀 데이터
  파일은 표준 스키마가 있는 이름을 피하는 게 낫다.

### 표지 문구가 "AI 티" 나던 문제

처음 홈 문구를 정형화된 설명문으로 썼다가 "너무 기계적이다"라는 피드백을 받았다. 이후 문체
문제를 여러 번 되짚었다:

- 자기소개가 정형화된 자기 PR 문구("~하는 편입니다")로 반복되는 걸 구체적 태도 서술로
  바꿨다.
- 숫자로 포장된 성과 문구("N배 개선" 같은)도 걷어냈다 — AI 생성 텍스트의 전형적 패턴이라는
  지적을 받았다.
- 정확한 숫자(연차 등)도 approximate 표현으로 풀었다.

관통하는 교훈: **AI가 쓴 글은 정형화된 자기 PR 문구와 정밀한 숫자를 좋아한다.** 사람이 쓴
글처럼 보이려면 오히려 그 정밀함을 흐리고, 태도를 구체적 행동으로 서술해야 한다.

### 페이지 역할을 몇 번 오락가락하며 정리한 과정

소개 페이지 하나에 자기소개+연혁+관심사+기술스택을 다 넣었다가, 이력서 페이지를 따로
만들면서 둘의 역할이 겹쳤다. 시행착오 끝에 "누가 뭘 보러 오는가"로 역할을 나눴다 — 소개는
"이 사이트가 뭔지" 궁금한 사람용, 이력서는 "이 사람 경력이 뭔지" 궁금한 사람용. **페이지를
나눌 때는 내용보다 먼저 이걸 먼저 정하지 않으면 계속 역할이 섞인다.**

### 데이터를 한 곳에 모아 동기화

역할을 나누고 나니 두 페이지가 같은 데이터(경력 등)를 담고 있어서 나중에 손으로 맞춰야
하는 문제가 보였다. 공통 데이터 파일 하나로 몰아서, 각 페이지가 그 데이터를 필요한 만큼
(요약 vs 상세) 렌더링하게 바꿨다. 콘텐츠(데이터)와 표현(템플릿)을 분리하는 게 왜 정석인지
실제로 체감한 지점이다.

### 회사 정보를 어디까지 공개할지

이력 데이터를 채우면서, 퇴사한 회사의 세부는 그대로 둬도 괜찮은데 **현재 재직 중인 회사의
내부 시스템 구조**는 다른 층위의 리스크라는 걸 짚어야 했다. 판단 기준: 회사명·재직
기간·역할 한 줄은 공개해도 됨(이미 다른 채용 플랫폼에도 있는 정보), 퇴사한 회사의 프로젝트
세부는 상대적으로 안전, **재직 중인 회사의 내부 아키텍처 세부는 기술 스택/성과는 유지하되
구체적 시스템 구성 요소를 한 단계 더 일반화**한다. 이건 노트 콘텐츠의 유출 검사 규칙과는
다른 결이라, 콘텐츠 기준과 이력서 페이지 기준을 서로 다른 잣대로 구분해야 했다.

### 하이라이트 글을 어떻게 관리할지

글이 쌓이면 "최근 글 N개"만 보여주는 방식으론 서사가 강한 글이 시간이 지나며 밀려난다.
완전 자동(최신 N개 고정)과 완전 수동(매번 판단) 사이에서, **"판단 기준만 사람이 정해두고
적용은 매번 일관되게"**로 정리했다 — 승격하는 글이 실패담·판단 과정·인식 전환이 뚜렷하거나
여러 개념을 하나로 꿰는 결론이 있으면 자동으로 하이라이트에 올리고, 총 개수는 캡을 두고
넘으면 가장 오래된 것부터 뗀다. 매번 사람이 판단하기엔 번거로운 반복 작업이면, 기준을
명시적으로 적어두고 그 기준을 일관되게 적용하는 쪽이 맞다.

## 정리

- 저장(git)과 노출(사이트)은 분리해서 생각해야 한다 — md 파일을 쌓아두는 것과 실제로
  발행하는 것 사이엔 "발견 가능성"이라는 결정적 차이가 있다.
- 유출 리스크가 있는 환경의 기록은 "원본은 자유롭게, 공개는 게이트"로 분리한다.
- 페이지를 나눌 때는 내용보다 먼저 "누가 왜 이 페이지에 오는가"를 정해야 역할이 안 섞인다.
- 같은 데이터를 여러 페이지에서 쓰면 반드시 한 곳으로 모으고, 페이지는 그 데이터를 렌더링만
  한다.
- 공개 정보의 기준은 콘텐츠 유출 검사 기준과 다르다 — 재직 여부에 따라 리스크 등급이 달라진다.
- 반복 판단(하이라이트 선정 같은)은 사람이 기준만 정해두면 그다음부터는 일관되게 적용하는
  분업이 맞다.
