관리자 시스템에 신규 서비스를 얹으면서 로그인을 공유해야 했다. 기존은 톰캣 세션 방식이라 서버를 이중화해도 인증이 공유되지 않았고, 우회하려면 시스템마다 전용 엔드포인트를 여는 수밖에 없었다. n개 시스템이면 n개 엔드포인트가 필요한 구조였다.

처음에는 간단히 아이디를 넘겨 돌려보고 있었다. 돌아가긴 했지만 더 나은 방법이 있을 것 같아서 쿠키에 토큰을 공유하는 쪽으로 바꿨다. 실제로 터진 문제가 있어서가 아니라 대안을 보고 싶었다.

JWT 기반으로 돌리다 보니 세션 관리라는 게 사실상 없어졌는데, 결국 그걸 강제로 다시 붙이게 됐다. 그 과정을 다시 점검하며 정리한다.

## 쿠키 속성을 잠그는 것으로는 부족했다

쿠키 속성이 각각 무엇을 막는지부터 정리했다.

| 속성 | 막는 위협 | 막지 못하는 것 |
|------|-----------|----------------|
| `HttpOnly` | 자바스크립트가 `document.cookie`로 값을 읽는 것 | 서버 사이드 코드가 요청에 실려 온 쿠키를 읽는 것 |
| `Secure` | 평문 HTTP로 쿠키가 전송되는 것 | HTTPS를 쓰는 다른 서브도메인이 읽는 것 |
| `SameSite=Strict` | 외부 사이트에서 시작된 요청에 쿠키가 실려 가는 것 | 같은 사이트 안에서 일어나는 공격 |
| `Domain=.example.com` | 막는 것이 아니라 여는 것이다 | 지정한 도메인 아래 모든 서브도메인이 읽게 된다 |

`Domain`을 루트 도메인으로 주면 그 아래 어떤 서브도메인이든 쿠키를 읽는다. 이벤트 페이지 하나에 XSS가 있으면 관리자 세션도 함께 노출된다. `HttpOnly`는 자바스크립트만 막고 서버 사이드로 읽어 가는 경로는 열려 있다.

그래서 쿠키 이름에 `__Host-` 접두사를 붙였다. 이 접두사가 있으면 브라우저가 세 가지를 강제한다. `Secure`가 반드시 있어야 하고, `Path`가 반드시 `/`여야 하고, `Domain` 속성을 지정할 수 없다. 세 번째 때문에 그 쿠키는 발급한 호스트에서만 전송되고 서브도메인끼리도 공유되지 않는다. 애플리케이션이 실수로 Domain을 붙이는 일 자체가 막힌다. `__Secure-`는 `Secure`만 강제하고 Domain은 허용하므로, 공유를 막으려면 `__Host-`를 써야 한다.

쿠키를 셋으로 나눴다. 액세스 토큰과 리프레시 토큰은 `__Host-` 접두사를 붙여 호스트에 묶고, 시스템 간 공유용 SSO 토큰만 루트 도메인에 뒀다.

여기까지 보면 자체 세션을 잠근 것처럼 보인다. 그런데 인증 필터의 순서를 보면 판단이 뒤집힌다.

```java
// 0. SSO 토큰 검증 (마스터) — 없으면 즉시 인증 실패
if (!isSsoTokenValid(request, response)) { ... }
// 1. __Host-AT 검증
```

SSO 토큰이 없으면 액세스 토큰이 유효해도 인증이 실패하고, 반대로 SSO 토큰만 있으면 세션을 새로 발급받는다. 가장 강한 권한을 가진 토큰이 가장 넓은 범위에 놓여 있었다. 공격자는 `__Host-` 쿠키를 읽을 이유가 없다. 마스터 하나만 가져가면 정식 경로로 세션을 받는다.

`__Host-` 접두사는 방어를 한 겹 더한 것이지 서브도메인 위험의 해결책이 아니었다. 쿠키 속성표보다 어느 토큰이 마스터인지가 노출 범위를 결정한다.

## 쿠키 만료는 토큰 유효기간이 아니다

SSO 쿠키의 `maxAge`는 브라우저가 쿠키를 보관하는 시간이다. 탈취한 값을 공격자가 자기 브라우저에 심으면 그 숫자는 아무 의미가 없다.

토큰이 유효한지는 발급자가 판단한다. 매 요청마다 발급자 API에 토큰을 보내 세션이 살아 있는지 확인하고, 로그아웃했거나 만료되었으면 그 시점에 거부된다. 애플리케이션 DB에 저장해 둔 세션 레코드의 만료값은 조회 경로가 없는 기록용이었다. 값이 코드에 보인다고 해서 그것이 인증 판단에 쓰인다는 뜻은 아니다.

## 매 요청에 실제로 일어나는 일

1. SSO 토큰을 발급자 API로 보내 세션 유효성 확인. 원격 호출이고 발급자는 Redis를 조회한다
2. 유효하면 갱신된 토큰으로 쿠키를 다시 내려준다. 슬라이딩 세션이다
3. 그 다음에 액세스 토큰의 서명을 검증한다

원격 호출이 한 번 더 있으므로 stateless가 아니다. 이 지점이 계속 걸렸다. 매번 세션을 확인하려고 호출하는 것 자체가 비효율로 느껴졌고, 중복 세션을 막으려고 Redis까지 붙으면서 더 그랬다.

검증 주기는 시스템마다 다르게 구현됐다. 레거시는 톰캣 세션 어트리뷰트에 마지막 검증 시각을 넣어 1분 간격으로만 호출한다.

```java
Long lastValidated = (Long) session.getAttribute("_lastSessionValidated");
if (lastValidated == null || (now - lastValidated) > 60_000L) {
    ... validateSession 호출 ...
    session.setAttribute("_lastSessionValidated", now);
}
```

세션을 걷어내려던 구조인데 검증 비용을 줄이는 데 그 세션을 쓰고 있는 셈이다. 새로 만든 쪽은 stateless 필터라 그런 자리가 없어 매 요청 호출로 남았다. 억제 장치를 둘 자리가 시스템마다 다르면 같은 정책도 다르게 구현된다.

인메모리 캐시로 맞출 수는 있지만 슬라이딩 갱신과 충돌한다. 검증을 건너뛰면 갱신된 토큰을 받지 못해 쿠키가 연장되지 않는다. 억제 주기가 쿠키 만료보다 충분히 짧아야 성립한다.

## 그러면 여기서 JWT는 왜 쓰나

"서버에 묻지 않으려고"가 아니다. 매 요청 중앙 검증이 있으니 그 설명은 성립하지 않는다.

여러 시스템이 하나의 신원을 나눠 쓰기 위해서다. 관리자 시스템, 신규 서비스, 토큰 서버가 같은 사용자를 다루는데, 토큰이 식별자와 권한을 싣고 다니므로 각 시스템이 매번 사용자 정보를 조회하지 않아도 된다. 신원과 권한은 토큰이 나르고, 세션의 생사는 중앙이 판단하는 분담이다.

JWT의 payload는 Base64 인코딩일 뿐이라 토큰을 가진 사람은 내용을 읽을 수 있다. 시크릿으로 하는 것은 서명이고, 서명이 보장하는 것은 위변조되지 않았다는 사실이지 내용이 감춰졌다는 사실이 아니다. 그래서 토큰 발급 모듈에 필드 단위 암호화를 넣어, 지정한 클레임만 AES로 암호화해서 넣고 검증 시 복호화하도록 했다. "JWT에 민감정보를 넣지 마라"는 원칙은 여전히 맞지만, 넣어야만 하는 값이 있다면 클레임 단위 암호화가 선택지가 된다.

한 가지 더. `HttpOnly` 쿠키에 담은 토큰은 브라우저의 자바스크립트가 읽지 못한다. 클라이언트에서 토큰 유효성을 미리 확인하는 설계는 `HttpOnly`와 동시에 성립하지 않는다.

## 기존 토큰 인프라를 재사용한 대가

이 구조를 빠르게 만들 수 있었던 이유는 토큰 발급 서버가 이미 있었기 때문이다. 다만 그 서버는 원래 서버 대 서버 API 인증용이었고, 사람이 쓰는 세션을 얹으면서 원래 토큰의 성질을 함께 물려받았다. 토큰 타입 목록에 세션용이 없다는 것이 그 흔적이다.

수명 설정도 공유한다. 설정값 하나를 서로 다른 단위로 쓰고 있었다.

```java
Duration.ofDays(duration)      // 세션 토큰 → 30일
Duration.ofMinutes(duration)   // OTP 토큰  → 30분
```

지금은 둘 다 적절한 값이지만, 세션을 7일로 줄이려고 값을 바꾸면 OTP 토큰이 7분이 된다. 용도가 다른 두 토큰이 설정 하나에 묶여 있으면 한쪽만 조정할 수 없다. Spring Boot는 `Duration` 타입 바인딩을 지원하므로 `P30D`, `PT30M`처럼 값에 단위를 넣어 혼동 자체를 없앨 수 있다.

재사용은 속도를 주지만 원래 용도의 정책도 함께 온다. 무엇을 물려받는지 먼저 확인해야 한다.

## 동시접속 제한을 키 구조로 풀었다

중앙 세션 저장소는 이렇게 생겼다.

```
session:{env}:{loginId}              → sessionId  (TTL 만료까지)
admin-session:{env}:{loginId}:{sid}  → "active"
otp-attempt:{env}:{loginId}          → 시도 횟수 (TTL 5분)
```

`loginId` 하나에 `sessionId` 하나만 저장한다. 새로 로그인하면 덮어써지므로 이전 세션이 자동으로 무효가 된다. 동시접속 제한을 별도 로직이 아니라 키 구조로 푼 것이다. 관리자는 조합 키를 따로 두어 다중 세션을 허용한다. 일반 사용자는 단일, 관리자는 다중이라는 정책이 키 구조로 갈린다.

OTP 시도 횟수는 Lua 스크립트로 `INCR`과 `PEXPIRE`를 원자적으로 처리한다. 증가시킨 뒤 만료를 거는 두 명령 사이에 프로세스가 죽으면 TTL 없는 키가 남아 영구히 잠기기 때문이다.

## 가용성을 위해 검증을 통과시키는 선택

세션 검증 호출이 실패하면 통과시킨다. 레거시와 신규 양쪽에 같은 판단이 들어가 있다.

```java
} catch (Exception e) {
    log.warn("세션 검증 API 호출 실패 (통과 처리): {}", e.getMessage());
    return true;
}
```

발급자가 죽으면 서비스 전체가 멈추는 것을 막으려는 의도다. 다만 뒤에 액세스 토큰 검증이 있어야 완전히 뚫리지 않고, 로그아웃한 사용자의 액세스 토큰이 만료 전이면 그 창 동안은 통과한다.

통과 범위를 HTTP 메서드로 좁힐 수 있다. HTTP 스펙이 GET, HEAD, OPTIONS를 안전한 메서드로 규정하므로 검증 실패 시 통과시켜도 되는 범위와 정확히 겹친다. 발급자가 죽어도 조회는 되고 금액이 움직이는 요청은 막힌다. 단, GET으로 상태를 바꾸는 엔드포인트가 레거시에 남아 있으면 이 방어는 무력해진다.

## 표준과 비교하면

목표만 보면 OIDC의 Authorization Code 흐름이 표준 답이다. 마스터 토큰이 IdP 도메인 쿠키에만 있으므로 서브도메인 위험이 구조적으로 사라지고, 각 서비스는 자체 세션만 확인한다.

그런데 OIDC는 로그아웃 전파가 약하다. 각 RP가 자체 세션을 갖기 때문에 IdP에서 로그아웃해도 RP 세션이 남는다. Back-Channel Logout이 스펙에 있지만 모든 RP가 수신 엔드포인트를 구현해야 하고, 통지가 실패하면 세션이 남으며, 레거시에 붙이기 어렵다. 동시접속 제한은 더 어렵다. 결국 각 RP가 중앙에 물어야 한다.

| 방식 | 로그아웃 즉시성 | 매 요청 비용 | 탈취 표면 | 신규 시스템 추가 |
|------|----------------|--------------|-----------|------------------|
| 톰캣 세션 | 즉시 | 낮음 | 좁음 | 불가 |
| 쿠키 공유 + 중앙 검증 | 즉시 | 높음 | 넓음 | 쉬움 |
| OIDC 표준 | 불확실 | 낮음 | 좁음 | 표준 등록 |
| OIDC + 선택적 중앙 검증 | 선택적 즉시 | 중간 | 좁음 | 표준 등록 |

현재 구조는 성능을 포기하고 일관성을 샀다. 규제 점검 항목에 세션 종료와 동시접속 제한이 들어 있으므로 요구사항에 맞춘 선택이기도 하다.

## 되돌아보면

보안을 생각하면 SSO 토큰을 일회용 교환 토큰으로 만드는 쪽이 정석이다. 세션을 발급한 뒤 즉시 폐기하면 탈취 표면이 줄어든다. 그런데 그렇게 바꿔도 실질적인 비효율은 거의 그대로일 것 같다. 페이지에 접속하거나 API를 호출한 뒤에도 일정 시간마다 세션이 살아 있는지는 확인해야 하기 때문이다. 교환 토큰은 탈취 표면을 줄이지 검증 호출을 없애지는 않는다.

결국 매 요청 검증의 비용을 실제로 재 본 적이 없다는 데로 돌아온다. 레거시가 쓰는 1분 간격이 적절한 수치인지, 중요 경로만 즉시 검증하고 나머지는 늦춰도 되는지 측정한 적이 없다. 갱신할 때 세션 식별자까지 회전시키면 이전 토큰이 즉시 무효가 되는데, 여러 탭이 동시에 요청할 때 경쟁이 생기므로 짧은 유예가 필요하고 그 길이도 아직 정하지 못했다.

구조를 판단할 때는 설정값보다 어느 토큰이 마스터인지, 매 요청에서 무엇을 조회하는지를 먼저 봐야 한다. 만료 시간이나 쿠키 속성만 보면 실제 노출 범위를 잘못 읽는다.
