인증이 깨져서 코딩 에이전트를 재설치했더니 설정 디렉터리가 통째로 새로 만들어져 있었다. 글로벌 지침, 스킬 18개, 훅, 서브에이전트, 그리고 자동 메모리 수십 개가 한 번에 사라졌다. 처음 한 일은 "일단 글로벌 지침 검토해줘"였는데, 검토할 파일이 없다는 답이 돌아왔다.

## 왜 다시 짜지 않고 복구했나

설정 파일은 다시 쓰면 된다. 아까웠던 건 메모리와 피드백 기록이었다. 몇 달 동안 "이건 이렇게 하지 마라", "커밋은 내가 말할 때만", "이 코드는 특정 방식으로 편집하지 마라" 같은 교정이 쌓인 것인데, 이건 다시 겪어야 다시 쌓인다. 설정보다 그게 자산이었다.

## 어디에 남아 있었나

- 공개 백업 저장소. 한 번 올린 뒤로는 갱신이 없었다. 그 사이 일주일치 수정분이 통째로 비어 있었다.
- 이전에 쓰던 하네스의 스킬 폴더. 업무 스킬은 여기 프롬프트를 도구 이름만 바꿔 이식했다.
- 메모리 덤프 문서. 예전 세션에서 메모리를 텍스트로 뽑아둔 것이 있어 업무 지식 열일곱 건을 여기서 다시 만들었다.
- 글로벌 지침 원본은 어디에도 없었다. 결국 기억과 대화 기록을 근거로 다시 썼다.

머신 전체 백업은 켜 두지 않았다. 켜져 있었으면 위 네 가지를 뒤질 필요가 없었다.

네 곳을 다 뒤져서 짜맞춘 복구본은 원본과 완전히 같지 않았다. 업무 스킬 프롬프트는 이식하면서 도구 이름을 바꿔야 했고, 메모리 덤프는 텍스트 형태라 다시 구조화된 항목으로 만드는 손이 갔다. "복구했다"는 말이 "예전과 똑같이 돌아왔다"는 뜻이 아니라 "그나마 있는 조각을 모아 비슷하게 재구성했다"에 가까웠다.

## 내가 잘못해 둔 것

백업이 특정 날짜에 멈춰 있었다. 글로벌 지침 원본은 어디에도 없었다. 백업 저장소를 만든 것까지는 했는데, 그 뒤로 설정을 고칠 때마다 동기화하는 절차가 없었다. 백업은 만드는 순간이 아니라 바뀔 때마다 해야 의미가 있다는 당연한 사실을, 일주일치 수정분을 잃고서야 확인했다.

## 다시 하면

- 설정을 바꿀 때 백업 저장소에 바로 싱크한다. 손으로 복사하는 게 아니라 스케줄로.
- 공개 백업과 업무 백업을 분리한다. 복구하면서 나눴는데, 원래 의도는 "개인용으로 쓰던 설정과 업무 정보가 담긴 설정을 분리하고 싶었던 것"이었다. 공개 저장소에는 프로젝트 이름과 티켓 번호가 그대로 들어 있었고, 업무 설정은 백업 자체가 없었다.
- 머신 자체 백업을 켠다. 그것조차 설정 안 해뒀던 건 아쉬울 뿐이다.
- 재설치나 인증 재설정 전에 설정 디렉터리를 통째로 복사해 둔다. 인증 문제 해결이 설정 삭제를 수반할 수 있다는 걸 이제 안다.

## 복구하면서 덤으로 알게 된 것

- 자동 메모리는 세션을 시작한 디렉터리별로 따로 쌓인다. 홈에서 복구한 메모리는 레포 안에서 세션을 열면 하나도 보이지 않았다. 홈 쪽을 허브로 두고 레포 쪽을 심볼릭 링크로 연결하는 훅을 만들어 해결했다.
- MCP 서버는 local 스코프 등록이 user 스코프를 덮는다. 두 서버가 각각 "연결 실패"로 보였는데, 둘 다 원인은 홈 디렉터리에 남아 있던 오래된 local 등록이었다.
- 세션 로그에는 토큰이 남는다. 예전 세션 로그 여러 개에 API 토큰이 평문으로 있었고, 그 토큰이 여전히 쓰이는 토큰이었다. 회전하면서 토큰은 환경 변수 한 곳에만 두고 나머지 설정은 참조하게 바꿨다.

## 되돌아보면

백업 싱크는 결국 훅이 아니라 하루 한 번 도는 일일 잡으로 걸었다. 매 변경마다 커밋하면 이력이 지저분해서, 정해둔 한 시간에 하루 한 번으로 정했다. 원격도 목적별로 두 곳(설정 전체 미러, 업무 문서)으로 나눠 생겼다. 아직 남은 질문은 머신 자체 백업을 실제로 켰는지다.
