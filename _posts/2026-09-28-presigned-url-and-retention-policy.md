보안 감사에서 NFS와 EFS 사용 금지를 요구받아 공유 스토리지를 S3로 옮겼다. 개인정보가 포함된 파일이 공유 스토리지에 섞여 있는 구조를 분리하는 것이 목적이었다. 사용처가 열일곱 곳인데 저장 방식과 보존 기간 관리가 제각각이라, 저장소만 바꿔서는 같은 문제가 반복될 상황이었다.

얼마 전 내가 만든 구조인데, 다른 작업으로 다시 들여다보면서 두 가지를 잘못 읽고 있었다는 걸 알았다. 접근 제한이 실제로 걸리는 위치와, 생명주기 규칙이 대상을 고르는 방식이다. 둘 다 이름만 보면 다르게 읽힌다.

## 접근 제한은 두 층으로 나뉜다

프리사인드 URL은 서버가 서명해서 만들어 주는 임시 접근 링크다. 이 구조에서 접근 제한을 말할 때는 두 가지를 구분해야 한다.

첫째는 URL을 발급하는 API에 대한 제한이다. 애플리케이션이 제공하는 엔드포인트이므로 인증을 걸거나, 보안 그룹과 VPC로 내부 호출만 받도록 막을 수 있다. 여기까지는 평소 하던 대로다.

둘째가 함정이었다. 발급된 URL 자체에는 그 제한이 걸리지 않는다. 프리사인드 URL은 클라이언트가 S3 엔드포인트로 직접 요청하는 방식이라 애플리케이션을 거치지 않기 때문이다. 발급 API를 아무리 잠가도, URL이 한 번 밖으로 나가면 그것을 손에 넣은 누구나 인터넷 어디서든 쓸 수 있다.

URL 자체를 제한하려면 버킷 정책에 조건을 걸어야 한다. `aws:SourceVpce`로 특정 VPC 엔드포인트를 거친 요청만 받거나, `aws:SourceIp`로 대역을 한정하는 식이다. 이것이 없으면 "내부 호출만 허용하도록 설계했다"는 말은 발급 경로에만 해당한다.

URL은 생각보다 쉽게 샌다. 브라우저 히스토리, 액세스 로그, 리퍼러 헤더, 스크린샷, 채팅으로 공유된 링크가 전부 경로다. 그래서 만료 시간이 실질적인 노출 창이 된다.

## 만료 시간의 상한은 서버가 정한다

만료를 호출하는 쪽이 정하도록 파라미터로 열어 두었다. 기본값은 있었지만 상한이 없어서 호출자가 원하는 값을 그대로 쓴다. 내부 시스템끼리만 부른다는 전제였는데, 전제가 깨지는 순간 방어가 없다.

파라미터를 받는 것 자체는 문제가 아니다. 용도마다 필요한 시간이 다르기 때문이다. 받되 서버가 정한 최대값으로 잘라 내면 된다. 개인정보가 포함된 파일이라면 특히 그렇다.

같은 맥락에서 업로드용과 다운로드용은 만료를 다르게 가져가는 편이 자연스럽다. 업로드는 사용자가 파일을 고르고 전송을 마칠 시간만 있으면 되므로 짧아도 된다.

저장 시 암호화도 비슷한 성격이다. `PutObjectRequest`에 서버 사이드 암호화를 지정하지 않으면 버킷의 기본 암호화 설정이 적용된다. 버킷에 기본값이 걸려 있으면 동작하지만, 코드만 봐서는 무엇이 적용되는지 알 수 없다. 감사 대응처럼 증빙이 필요한 상황이라면 코드에서 명시하는 편이 확인하기 쉽다.

## 태그를 붙였다고 생명주기 규칙이 따라오지는 않는다

S3 Lifecycle 규칙은 대상을 고르는 필터를 갖는다. 이 필터를 prefix로 줄 수도 있고 태그로 줄 수도 있는데, 둘은 성격이 다르다.

prefix 기반은 키 경로로 대상을 정한다. 파일이 어느 폴더에 들어가는지가 곧 보존 정책이 되므로, 업로드 시점에 경로를 정하면 그 뒤로는 손댈 것이 없다. 다만 이미 올라간 파일의 정책을 바꾸려면 객체를 옮겨야 한다.

태그 기반은 객체에 붙은 태그로 대상을 정한다. 경로와 무관하게 정책을 바꿀 수 있지만, 태그를 붙이는 API 호출이 별도로 필요하고 태그에도 개수 제한이 있다.

내 구현은 규칙 필터를 prefix로 두고, 태그는 보존 기간이나 만료 예정일 같은 메타데이터를 객체에 남기는 용도로 따로 쓰고 있었다. 다시 보면서 한동안 그 태그가 생명주기와 연결돼 있다고 읽었는데 아니었다. 태그를 붙인다고 해서 그것이 곧 필터로 동작하지 않는다. 규칙 쪽에서 태그를 필터로 지정해야 연결된다.

## 보존 정책의 출처를 테이블에 뒀다

이 구조에서 스스로 괜찮았다고 생각하는 부분은 보존 정책의 출처를 애플리케이션 DB에 둔 것이다.

파일 유형별 보존 기간과 스토리지 클래스를 테이블에 정의해 두고, 정책이 바뀌면 이벤트를 받아 S3의 Lifecycle 규칙으로 다시 맞춘다. 테이블이 단일 출처이고 S3 규칙은 파생물이다.

콘솔에서 규칙을 직접 관리하는 방식과 비교하면 차이가 분명하다. 누가 언제 무엇을 바꿨는지가 애플리케이션 쪽 이력으로 남고, 파일 유형이 늘어날 때 인프라 담당자에게 요청하지 않아도 되며, 정책 변경이 코드 배포와 분리된다.

보존 기간 같은 값은 업무 규칙이지 코드 상수가 아니라는 판단이 깔려 있다. 분기문으로 처리하면 유형이 늘 때마다 코드를 고쳐야 한다.

## 되돌아보면

파생물을 두는 구조를 만들어 놓고 정작 어긋났을 때를 정하지 않았다. Lifecycle 규칙과 테이블 정책이 맞지 않으면 무엇을 신뢰할 것인지, 동기화가 실패한 상태를 어떻게 감지할 것인지가 비어 있다.

prefix 기반이라 이미 저장된 파일의 보존 정책을 바꾸기 어렵다는 것도 남은 숙제다. 지금까지 그런 요구가 없었을 뿐이고, 생기면 객체를 옮기는 작업이 필요하다.

업로드가 중간에 끊긴 건은 배치로 정리하도록 해 두었다. 메타데이터를 먼저 만들고 URL을 발급하므로 실제 업로드가 없으면 대기 상태로 남는데, 주기적으로 S3에 객체가 있는지 확인해 상태를 맞춘다. 반대 방향은 다루지 않았다. S3에는 있는데 메타데이터가 없는 객체는 아무도 보지 않는다.
